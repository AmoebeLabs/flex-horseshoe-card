# Reduce Redundant Tool Methods

## Scope

Review repeated one-line methods and duplicated method bodies in the layout tools. The goal is to remove boilerplate where the same behavior is already provided by a shared owner, without flattening functions that implement distinct geometry, rendering, lifecycle, or state-transition behavior.

This is an audit item only. No implementation is included here.

### Size distribution and rendering

The 19 modules above 500 lines contain 22,365 lines, or 68.5% of the total. The remaining 52 modules contain 10,306 lines, or 31.5%. The four Sparkline modules in this inventory account for 10,362 lines, or 31.7% of the total.

Within `sparkline-graph-tool.js`, Acorn identified 53 methods whose names start with `render`. Their method spans contain 2,272 physical lines, or 37.6% of the module. The narrower `renderSvg` prefix identifies 27 methods containing 1,172 lines, or 19.4%. These counts include comments and blank lines inside the methods, but exclude preceding JSDoc and presentation helpers with other names. The `renderSvg` count is a subset of the `render` count.

The different chart types need their own rendering. Audit the surrounding configuration and processing code for repeated work; module size alone does not establish that code can be removed.

## Confirmed Candidates

### Shared SVG coordinate conversion

Ten tools define the same `calculateSvgDimensions(config = this.config)` method, each delegating directly to `cardLayout.calculateSvgCoordinatesInGroup(config)`. Examples include `name-tool.js`, `text-tool.js`, `state-tool.js`, `area-tool.js`, and several control tools.

Check whether `BaseTool` can provide this common implementation once. Keep overrides only for tools that add shape-specific dimensions, such as a radius, line endpoints, or sparkline margins and size.

### Repeated measured-text getters

`NameTool`, `TextTool`, `StateTool`, and `AreaTool` each define the same four methods:

- `getWidth()` selects measured width or its estimate.
- `getHeight()` selects measured height or its estimate.
- `getXpos()` selects the measured center or configured SVG position.
- `getYpos()` selects the measured center or configured SVG position.

Review whether these belong once in their existing common owner. Avoid introducing another base class unless it clearly reduces total code and preserves the current measurement contract used by `CardTools` and controls.

### Icon group-transform forwarding

`IconTool` has `getGroupScaleTransform(item)` and `getGroupScaleStyle(item)` methods that only forward to `CardLayout`. `BaseTool` already provides the same operations for `this.config`.

Check whether the base methods can accept an optional item config, allowing `IconTool` to use the inherited methods and removing its forwarding copies.

## Configuration Validation Review

`SparklineGraphTool` contains explicit user-facing checks for numeric y-axis bounds and supported chart settings. Static radial and day/night validation also appears in the runtime configuration path. JavaScript-backed values require validation after evaluation, so trace the configuration boundary before deciding which repeated checks can be removed.

For each candidate, establish where its input becomes valid and whether later code repeats that validation. Keep configuration validation with its owner and let downstream code consume the accepted values directly. Count removable lines before estimating the saving: the suggested 500-1,000 lines in GraphTool have not been established by this inventory.

## Review Boundaries

- Configuration and constructors remain the validation boundary. Do not repeat checks for already-validated arrays, objects, or values in downstream rendering code.
- Keep direct indexing and ordinary array operations when their inputs are guaranteed by that boundary.
- Retain checks for real runtime transitions, such as stale asynchronous results, retries, connection state, and changing history ranges.
- Do not remove small methods mechanically. Some accessors and adapters preserve ownership boundaries or a shared interface even when their bodies are short.
- Prefer the smallest edit that removes duplicate behavior. Do not add abstraction layers merely to make individual functions shorter.

## Expected Result

The candidates above appear to represent roughly 150 lines of repeated boilerplate, depending on where the shared implementations belong. This is a targeted simplification opportunity, not an explanation for the full source-size increase and not a claim that thousands of lines can be removed from these examples alone.

Any implementation should preserve existing behavior and run focused tests for tool dimensions, text measurement, group transforms, and controls that consume measured state geometry.
