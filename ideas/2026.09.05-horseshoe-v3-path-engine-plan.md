# Horseshoe V3 - Generic Path Engine and Rendering Architecture

## Status of this document

This document is the reviewed English successor to the original Dutch design
draft. It preserves the central idea of that draft, but tightens the contracts,
corrects assumptions that are not universally valid for arbitrary SVG paths,
and adds the lifecycle and proof-of-concept gates required before implementation.

The proposal is deliberately not a final public configuration reference. New
path configuration must remain experimental until the browser-based geometry
and rendering proofs have succeeded.

Proven SAK path code does not need to be rewritten merely to make it look new.
Generators, calculations, and names may be copied directly when they satisfy the
new contracts and repository conventions. Reuse is decided per cohesive piece:
retain recognizable, proven logic; exclude the monolithic SAK tool structure,
tool lifecycle, defaults, unfinished branches, diagnostics, and workarounds.

## Objective

The current Flexible Horseshoe Card (FHS) horseshoe is a rich arc-based gauge.
Swiss Army Knife Card (SAK) also contains a `ProgressPathTool` that demonstrates
progress rendering on several SVG path shapes. Horseshoe V3 should combine the
strong parts of both approaches without copying the SAK tool or replacing the
horseshoe with a separate progress-path product.

The central design rule is:

> Geometry defines one stable centerline path. Value mapping defines semantic
> ranges on that path. Renderers paint those ranges without recalculating the
> geometry for each feature.

During development, `horseshoes_v3` is a temporary entry point that allows the
new implementation and the current horseshoe to render side by side. The new
underlying modules must not use `V3` in their names. After complete parity, the
normal `horseshoes` entry points to the new implementation and the temporary
entry point is removed.

# 1. Evaluation

## 1.1 Overall conclusion

The proposed path-engine direction is sound, but the original draft is not yet
an implementation-ready contract.

The following parts are well-founded:

- a centerline SVG path can be reused by background, state, range, mask, marker,
  tick, and label layers;
- `pathLength="100"` provides a useful normalized space for dash-based rendering;
- `getTotalLength()` and `getPointAtLength()` provide actual path geometry in SVG
  user units;
- ranges and value mapping can be independent of path shape;
- multiple renderer strategies can share one geometry source;
- a temporary parallel adapter is a safe way to compare old and new output.

The following assumptions require correction or proof:

- browser geometry measurements are not available from a plain path string;
  they require an SVG geometry element and therefore introduce a render lifecycle;
- a centerline stroke is generic, but an exact closed band around every arbitrary
  Bezier path is not automatically generic;
- `inside` and `outside` have no universal meaning for open paths, waves, spirals,
  or self-intersecting paths;
- mixed caps, transparent fill with a separate border, and path-following
  gradients require browser proofs on more than an arc;
- sharp corners, closed seams, cusps, and self-intersections need deterministic
  behavior before labels and markers can be called path-independent;
- six path types should not all be implemented before the measurement and basic
  renderer contracts have been proven.

The architecture should proceed, but only through explicit proof-of-concept
gates. A failed proof must change the contract rather than introduce scattered
shape-specific workarounds.

# 2. Evidence from the existing implementations

## 2.1 What SAK proves

SAK generates a single SVG `d` path for circle, line, rectangle, and spiral
shapes. It then reuses that path for several visual layers. It also demonstrates:

- browser measurement through `getTotalLength()`;
- coordinate lookup through `getPointAtLength()`;
- normalized progress strokes using `pathLength="100"`;
- dash arrays and offsets for range visibility;
- marker placement based on sampled path direction;
- masks and half-circle markers for asymmetric caps.

These techniques are useful evidence, not a reusable architecture as a whole.
The same source contains unfinished user-path support, disabled scale behavior
for some shapes, direction and flip comments, crash notes, hard-coded
measurements, and an SVG performance warning. Horseshoe V3 may copy generators,
calculations, and naming that already meet the new contracts, but it must not
copy the complete class with its historical lifecycle and configuration.

## 2.2 The rendering lineage already exists

The horseshoe used dash-array progress before the V2 closed-band implementation.
That earlier FHS generation already proved basic dash-based state progress in
this product. At that time, the design did not yet establish multiple independent
segments or mixed `butt` and `round` endpoints.

The three sources therefore contribute different proven parts:

- the earlier FHS horseshoe proves basic dash-based progress and compatibility
  with the card lifecycle;
- SAK proves that one centerline can support several shapes, multiple segments,
  gaps, masks, markers, and mixed endpoint treatment;
- the current V2 horseshoe defines the richer visual and configuration behavior
  that the replacement must preserve.

V3 combines that lineage behind explicit contracts. It is not a new rendering
idea introduced without product history.

## 2.3 What the current FHS horseshoe must preserve

The current FHS implementation supports behavior beyond the SAK progress path:

- linear and spline value mapping;
- normal, absolute, and bidirectional bar modes;
- numeric and ranked/string states;
- fixed colors and hard color-stop segments;
- full-scale and current-value gradients;
- configurable gaps and independent start/end caps;
- separate scale, state, background, tick, badge, and label layers;
- inactive-state opacity;
- targeted state animation without rerendering every static layer;
- geometry and path-item caches keyed by the inputs that affect them.

This behavior is the functional reference. V3 is successful only when it can
preserve these semantics through more general contracts.

## 2.4 Verified SVG length behavior

Two length spaces are both required and must never be mixed implicitly.

### Normalized render space

The master path is rendered with:

```svg
<path d="..." pathLength="100" />
```

SVG scales distance-along-a-path operations such as stroke dashes against this
author length. Therefore a semantic range from `20` to `47` can be rendered as a
27-unit dash beginning at 20 without converting it to the physical path length.

### Actual geometry space

`getTotalLength()` returns the browser's own computed path length in SVG user
units and explicitly does not take `pathLength` into account. Likewise,
`getPointAtLength(distance)` accepts a distance in that actual geometry space.

For a coordinate at 37 percent:

```js
const distance = 0.37 * pathElement.getTotalLength();
const point = pathElement.getPointAtLength(distance);
```

The normalized `0..100` space is for values, ranges, dashes, gaps expressed as
progress, and semantic animation. Actual length is only for coordinate,
direction, and physical-distance calculations.

# 3. Architecture

```text
Home Assistant state and normalized configuration
                         |
                         v
                Value / scale mapping
                         |
                  Semantic ranges
                         |
                         v
                   Path definition
                         |
                stable SVG centerline
                         |
                         v
              Browser geometry binding
                         |
       actual length + point/tangent/normal sampling
                         |
             +-----------+-----------+
             |                       |
             v                       v
       Feature layout          Painted ranges
      ticks/labels/marker     gaps/caps/colors/width
             |                       |
             +-----------+-----------+
                         v
                     Renderers
                         |
                         v
                         SVG
```

Each layer owns one kind of decision. No renderer may derive value semantics,
and no value mapper may derive SVG coordinates.

## 3.1 Source layout

The implementation keeps the existing flat `src/` layout. New general-purpose
modules use a `path-` prefix so their ownership is immediately visible without
introducing directory trees.

The expected module grouping is approximately:

```text
src/path-generators.js
src/path-geometry.js
src/path-ranges.js
src/path-renderer.js
src/path-gradient-renderer.js
src/path-layout.js
src/path-animator.js
src/horseshoe-v3.js          temporary adapter only
```

These names are directional, but the layout rule is fixed: no `src/path/`,
`renderers/`, `generators/`, or similarly nested hierarchy. Closely related
logic stays in cohesive, sequential modules rather than one small file or class
per shape or operation.

The SAK source is one approximately 1,500-line tool class and therefore does not
provide the desired module architecture. Its compact size nevertheless
demonstrates the leverage of the centerline approach: that one source already
covers several shapes, segments, dashes, masks, and markers. Suitable generators,
calculations, and names may be retained inside the flat FHS modules. The class
structure and unrelated tool responsibilities are not retained.

## 3.2 Normalized configuration adapter

Only the adapter understands the existing horseshoe configuration. It validates
and normalizes all required values before the path, mapping, layout, and renderer
layers receive them.

The rest of the implementation trusts this normalized contract. Defaults,
fallbacks, and defensive repairs must not be repeated in downstream functions.

During development:

```text
layout.horseshoes     -> current implementation
layout.horseshoes_v3  -> new adapter and path engine
```

The adapter must initially accept existing horseshoe configuration. Shape
configuration shown during the proof-of-concept is illustrative and is not a
public compatibility promise.

## 3.3 Value and scale mapping

The existing `GaugeScale` behavior should be retained or extracted without
adding path knowledge. Its output is one or more semantic ranges in normalized
progress space.

Example continuous state:

```js
{
  start: 0,
  end: 63,
}
```

Example bidirectional state:

```js
{
  start: 50,
  end: 72,
}
```

Semantic ranges describe meaning, not paint. A suitable contract contains:

```js
{
  id: 'state',
  start: 20,
  end: 47,
  active: true,
  sourceValue: 37,
  role: 'state',
}
```

Colors, stroke widths, caps, opacity, masks, and SVG path data do not belong in
this layer.

## 3.4 Path definition

A path generator synchronously converts normalized shape configuration into a
stable path definition.

Conceptual output:

```js
{
  d: 'M ...',
  closed: false,
  direction: 'forward',
  signature: '...',
}
```

The generator does not measure the path and does not know about values, colors,
styles, ticks, labels, or animation.

Initial proof shapes:

```text
arc
line
rectangle
wave
```

These are sufficient to expose arc assumptions, straight segments, corners,
curves, and changing tangents. After these contracts pass, add:

```text
spiral
infinity
```

Spiral tests long curved paths and performance. Infinity tests crossings and the
absence of a globally meaningful inside/outside side.

Potential later shapes such as stadium or steps are admitted only when they need
one generator and contract tests, without renderer branches.

## 3.5 Bound browser geometry

The path definition alone cannot answer browser geometry queries. The geometry
engine must bind to the rendered measurement `SVGPathElement` and then expose:

```js
getPathDefinition()
getTotalLength()
pointAtProgress(progress)
tangentAtProgress(progress)
normalAtProgress(progress, side)
```

`pointAtProgress()` converts normalized progress to actual length exactly once
inside this layer. Callers never perform their own conversion.

Tangents are derived from nearby samples in actual geometry space. Sampling must
use a stable physical epsilon and handle the path boundaries with forward or
backward samples. At a segment boundary, cusp, or sharp corner, V3 follows one
documented rule consistently rather than allowing each feature to choose.

The low-level normal contract is `left` or `right` relative to path direction.
Those concepts exist for every directed path. `inside` and `outside` may be
translated by a shape adapter only for shapes where enclosure is meaningful.

## 3.6 Geometry lifecycle

Browser geometry creates an unavoidable two-stage render lifecycle:

1. Build the synchronous path definition.
2. Render one invisible but measurable master path.
3. Bind the resulting `SVGPathElement` after DOM creation.
4. Read and cache its actual length and required samples.
5. Request one controlled render for geometry-dependent features.
6. Reuse the cached measurements for state-only updates.

The measurement path must be non-visible without being placed in a state where
the browser cannot compute its geometry. The proof-of-concept must establish the
exact SVG structure that works consistently in supported browsers.

The user must never see an intermediate misplaced marker, tick, label, or
gradient. Until geometry is bound, dependent layers remain hidden. Static layers
that only need `d` may render immediately if doing so cannot cause a visible
layout change.

Geometry is invalidated only when its signature changes. Entity state, active
range, color, or opacity changes must not trigger remeasurement.

## 3.7 Painted ranges

The paint/layout stage combines semantic ranges with normalized visual config:

```js
{
  id: 'state',
  start: 20,
  end: 47,
  color: '#ff9800',
  width: 6,
  opacity: 1,
  startCap: 'butt',
  endCap: 'round',
}
```

This stage owns gap semantics. One rule applies everywhere:

- internal gaps are divided equally between adjacent ranges;
- the first range keeps the true path start unless an outer gap is explicitly
  part of the public configuration;
- the final range keeps the true path end under the same rule;
- ranges remain clamped to `0..100`;
- a range with no visible length produces no painted output.

The exact existing FHS gap semantics must be captured by tests before extraction.
The implementation must not silently redefine existing cards.

## 3.8 Feature layout

Ticks, labels, and markers consume only measured path operations and normalized
progress positions.

```text
point   = pointAtProgress(progress)
tangent = tangentAtProgress(progress)
normal  = normalAtProgress(progress, side)
```

Offsets are applied along the chosen normal. Marker rotation follows the tangent.
No feature-layout code may use radius or angle directly.

Closed paths need an explicit seam policy. A full ring cannot allow progress 0
and 100 to create duplicate labels, overlapping caps, or an unstable tangent.
Rectangle corners and infinity crossings must have deterministic test fixtures.

# 4. Rendering capabilities

One geometry contract does not imply one rendering technique. Renderers are
selected by visual capability, never by shape type.

## 4.1 Stroke and dash rendering

The primary renderer repeatedly paints the same complete centerline `d` and
reveals normalized ranges through `stroke-dasharray` and `stroke-dashoffset`.
This is the expected basis for:

- background tracks;
- continuous state progress;
- hard color-stop ranges;
- ranked and string-state ranges;
- gaps;
- fixed-width outlines;
- simple reveal animation.

This renderer must not call `getTotalLength()` for ordinary range painting.

## 4.2 Caps and masks

Native `stroke-linecap` is sufficient when both ends use the same cap. Different
start and end caps require a generic mask or equivalent composition.

The proof must cover:

```text
butt / butt
round / round
round / butt
butt / round
```

It must work on open, curved, cornered, and closed paths. A shape-specific cap
branch is a failed proof.

## 4.3 Width, fill, and border

The master geometry is a centerline, not a closed band outline.

An opaque gauge band can usually be represented by layered strokes: a wider
border beneath a narrower fill. This does not reproduce every mathematical
offset curve, especially around sharp corners, but it may reproduce the visual
contract needed by FHS.

Transparent fill cannot simply be drawn over an opaque border because the border
would show through the fill. The proposed generic composition is:

1. paint the border stroke;
2. mask its center away;
3. paint the narrower fill separately;
4. apply final layer opacity after internal composition.

This remains a hypothesis until browser screenshots prove it on arc, rectangle,
wave, and infinity. If it does not match the current horseshoe visually, the
scope must be narrowed or the renderer contract revised. An arbitrary exact
offset-band engine is not part of V3 unless separately designed and justified.

## 4.4 Gradients along a path

SVG does not provide a general gradient that follows an arbitrary path. Preserve
the current FHS approximation by dividing a normalized range into adaptive
micro-ranges. Each micro-range uses sampled start/end points and a local linear
gradient.

The generic version segments by progress/distance, not arc angle. It must define:

- adaptive segment count based on rendered path length and curvature;
- local gradient direction from sampled geometry;
- overlap sufficient to remove anti-aliasing seams;
- group opacity so overlapping micro-ranges do not become darker individually;
- deterministic paint order at self-intersections;
- a maximum cost per gauge and per card.

`full` and `current` retain their existing semantics:

- `full` keeps a static full-scale color distribution and reveals the active
  portion;
- `current` redistributes colors over the current range and therefore requires
  range/color recomputation as the animated value changes.

## 4.5 Animation

The animator continues to produce semantic progress. The renderer chooses the
least expensive update for the selected mode.

- solid progress updates a dash or mask;
- hard segments keep static geometry and update their reveal state;
- a full gradient keeps static gradient geometry and updates its reveal;
- a current gradient recalculates its painted micro-ranges;
- static path measurements, ticks, and labels are never rebuilt for a state-only
  animation.

Targeted DOM updates should remain possible, as in the current horseshoe. The
proof must compare their correctness and cost with a Lit rerender before the
final update mechanism is selected.

# 5. Configuration policy

The final shape schema is intentionally deferred until the renderer proof is
complete. Early examples may show the intended direction:

```yaml
layout:
  horseshoes_v3:
    - entity_index: 0
      path:
        type: wave
        waves: 3
        amplitude: 8
```

This syntax is not yet a compatibility promise.

The first public schema must satisfy these requirements:

- existing arc horseshoe configuration remains valid;
- shape-specific parameters are confined to `path` configuration;
- value mapping, state modes, colors, widths, gaps, ticks, labels, markers, and
  animation remain shared features;
- raw SVG `d` is not a normal user-facing requirement;
- unsupported feature/shape combinations fail during configuration validation;
- downstream geometry and renderer code receives complete normalized values and
  does not create defaults or defensive fallbacks.

Raw custom paths may be considered later as an expert feature after path bounds,
scaling, orientation, validation, and error reporting have contracts of their
own.

## 5.1 Frozen shape schema

Issue #582 freezes the temporary `horseshoes_v3` shape configuration. Shared
placement remains on the layout item. Shape-specific dimensions live only in
`path` and use the card's established 0..100 coordinate space.

```yaml
layout:
  horseshoes_v3:
    - entity_index: 0
      xpos: 50
      ypos: 50
      rotate: 0
      flip: none
      path:
        type: arc
        radius: 40
        arc_degrees: 270
        start_angle: -135
      horseshoe_scale:
        min: 0
        max: 100
```

The supported shape fields are:

| `path.type` | Shape-specific fields |
| --- | --- |
| `arc` | `radius`, or `radius_x` and `radius_y`; `arc_degrees`; `start_angle` |
| `line` | `length`; `angle` |
| `rectangle` | `width`; `height`; `radius`; `start`; `direction` |
| `wave` | `length`; `angle`; `waves`; `amplitude` |
| `spiral` | `radius_inner`; `radius_outer`; `start_angle`; `degrees`; `points` |
| `infinity` | `radius_x`; `radius_y` |

For arc compatibility, omitting `path` retains the established top-level
`radius`, `arc_degrees`, and `start_angle` fields. New non-arc shapes do not add
top-level shape aliases.

`rotate` and `flip` transform visual path layers around the configured item
center. Ticks, labels, badges, and markers never inherit that SVG transform.
Their final positions, tangents, and normals are calculated from the transformed
geometry, so horizontal labels remain readable while path-oriented labels still
follow the transformed path. Group transforms follow the same rule.

The adapter normalizes percentages to SVG coordinates and supplies complete
generator, mapping, range, and paint contracts. Downstream path modules do not
read public card configuration or add defaults. During #582 only the existing
linear, normal, fixed state mode is connected. Issue #583 owns the remaining
horseshoe modes and annotations; requesting one before its migration fails at
the adapter boundary.

# 6. Proof-of-concept and migration phases

## Prerequisite - Restore a green repository baseline

The V3 implementation must not start while the existing suite is failing. On
2026-09-05 the baseline is:

```text
tests: 227
pass:  217
fail:  10
```

The failures currently cover bar fade, radial x-axis labels, cartesian bar
geometry, radial barcode sizing, radial barcode arc/rotation, and radial
day/night geometry.

The baseline-repair issue owns these exact failures:

1. `bar fade reverses at zero for positive and negative values`
2. `horizontal radial x-axis labels align away from the circumference`
3. `arc radial x-axis labels use unique readable text paths`
4. `bars share the zero baseline across negative and positive values`
5. `bar geometry keeps both outer half-bands inside axisArea`
6. `grouped bars divide every bucket without crossing the shared axis boundaries`
7. `radial barcode geometry reserves only its rounded outer edge`
8. `day and night radial barcode background uses the complete barcode ring`
9. `radial barcode uses the same configured arc and rotation`
10. `radial barcode reserves only outward rounded geometry`

Resolve these failures in a separate issue and branch before creating the V3
feature branch. Run the complete test and build commands after the fixes. Do not
combine V3 architecture changes with this baseline repair.

Exit criterion: `npm test` and `npm run build` both pass on `master`.

## Phase 0 - Capture the current contract

- Inventory every current horseshoe mode and configuration feature.
- Convert representative existing examples into a parity matrix.
- Record current gap, cap, gradient, string-state, label, tick, and animation
  behavior with tests and screenshots.
- Make no functional changes.

Exit criterion: existing behavior is explicit enough that parity can be judged
without relying on memory or visual interpretation alone.

## Phase 1 - Browser geometry harness

- Add a real-browser test harness for SVG geometry.
- Prove actual-length queries with and without `pathLength="100"`.
- Prove that the selected invisible measurement structure remains measurable.
- Prove the initial bind-and-rerender lifecycle without visible flicker.
- Prove signature-based reuse and invalidation.

Exit criterion: measurement behavior and lifecycle are deterministic in the
supported browser environment.

## Phase 2 - Path definition and measured geometry

- Implement arc, line, rectangle, and wave definitions together.
- Bind each definition to the browser geometry contract.
- Implement normalized point, tangent, and left/right normal queries.
- Define boundary, corner, cusp, direction, and closed-seam behavior.
- Add complete contract tests before adding rendering features.

Exit criterion: feature-layout code can use all four shapes without shape checks.

## Phase 3 - Semantic and painted ranges

- Reuse the existing scale and bar-mode semantics.
- Produce path-independent `0..100` semantic ranges.
- Produce painted ranges with one gap and cap policy.
- Cover continuous, absolute, bidirectional, color-stop, and string-state modes.

Exit criterion: range tests contain no shape knowledge and preserve current FHS
semantics.

## Phase 4 - Basic renderer proof

Prove on arc, line, rectangle, and wave:

- background track;
- continuous progress;
- multiple hard segments;
- internal gaps;
- all cap combinations;
- opaque fill and border;
- masked border with transparent fill;
- simple semantic progress animation.

Exit criterion: the same renderer paths work without shape-specific branches and
the browser screenshots meet the visual contract.

## Phase 5 - Stress geometries

- Add spiral as a long-path and performance test.
- Add infinity as a crossing, tangent, side, and overlap test.
- Re-run every geometry and basic renderer contract.

Exit criterion: either both shapes work generically or the document records a
clear capability boundary before public configuration is frozen.

## Phase 6 - Gradient proof

- Implement adaptive micro-range gradients.
- Prove full and current semantics.
- Prove seams, local direction, group opacity, crossing order, and animation.
- Measure CPU, DOM-node, and frame-time cost with multiple gauges.

Exit criterion: visual quality and performance budgets are documented and met.

## Phase 7 - Feature layout

- Add ticks, labels, badges, backgrounds, and markers through measured geometry.
- Test offsets, path direction, closed seams, rectangle corners, and crossings.
- Confirm that state-only updates do not move or rebuild static features.

Exit criterion: layout features require no path-type branches outside generators
or explicit shape metadata interpretation in the geometry layer.

## Phase 8 - Freeze configuration and add `horseshoes_v3`

- Finalize the public shape schema from the proven capabilities.
- Add the temporary adapter.
- Start with the simplest current horseshoe mode.
- Compare old and new implementations in the same showcase.

Exit criterion: at least one representative existing horseshoe has behavioral
and visual parity through the new engine.

## Phase 9 - Controlled parity migration

Add existing features in this order:

```text
fixed scale and solid state
bar modes
hard color-stop segments
gaps and caps
background/fill/border composition
string states
full gradients
current gradients
ticks and labels
badges and markers
animation refinements
```

Every regression must be fixed in the layer whose contract is broken. Do not add
an arc-only workaround to a renderer or feature-layout module.

## Phase 10 - Replacement and cleanup

- Complete the parity matrix and visual regression set.
- Point normal `horseshoes` configuration to the new implementation.
- Remove the old implementation only after all parity tests pass.
- Remove the temporary `horseshoes_v3` entry.
- Remove migration-only showcase content and naming.

merge, the feature branch must build and all accumulated tests must pass. A later
subissue branch starts from the updated feature branch.

The feature branch is not merged into `master` until all sixteen subissues are
closed and the final acceptance pass succeeds. The final pull request is the
only Horseshoe V3 pull request targeting `master`.

The split follows contracts and observable milestones, not individual functions,
classes, modules, or shape types. If a proof invalidates a later assumption,
update the parent plan and dependent subissues before continuing.

# 7. Test matrix

## 7.1 Geometry contracts

For every path definition:

```text
valid non-empty SVG d
non-zero measured length
progress 0, 25, 50, 75, and 100
correct start and end points
finite point/tangent/normal values
tangent boundary behavior
left/right normal perpendicular to tangent
path direction
measurement cache reuse
correct invalidation after geometry changes
```

Additional cases:

- arc: clockwise, counter-clockwise, 90, 180, 270, and closed/full-circle seam;
- rectangle: sharp and rounded corners, start position, and direction;
- wave: one and several waves with different amplitudes;
- spiral: inner/outer radius, turns, sample density, and cost;
- infinity: crossing order, tangent continuity, and side semantics.

## 7.2 Range contracts

```text
0 is the path start
100 is the path end
20..40 has semantic length 20
normal progress
absolute positive and negative branches
bidirectional ranges
hard color-stop ranges
stringstate_mode
stringstate_level
internal and endpoint gaps
zero-length ranges
clamping at the scale boundaries
```

These tests must not mention path types.

## 7.3 Browser renderer contracts

The same normalized dash configuration must reveal the same relative portion of
paths with very different actual lengths. Test all cap combinations, transparent
fill composition, group opacity, closed seams, corners, and crossings in a real
browser.

Visual baselines must include:

```text
270-degree horseshoe
full ring
line
sharp and rounded rectangle
wave
spiral
infinity
```

Each relevant shape is captured with solid progress, segments and gaps, mixed
caps, transparent fill and border, full gradient, current gradient, string state,
ticks, labels, marker, and animation.

## 7.4 Lifecycle and performance

Test:

- first render before and after geometry binding;
- repeated entity updates with unchanged geometry;
- theme and CSS-variable changes;
- size, rotation, flip, and shape changes;
- multiple gauges updating simultaneously;
- animation cancellation and replacement;
- gradient segment counts and DOM-node budgets;
- frame time and CPU use on a representative slower device/browser.

There must be no spinner, misplaced intermediate frame, repeated measurement, or
layout flicker caused by an unchanged path.

# 8. Architecture rules

1. Geometry knows nothing about entities, values, colors, or rendering modes.
2. Value mapping knows nothing about SVG coordinates or path types.
3. Renderers know nothing about Home Assistant states or bar-mode calculations.
4. Feature layout uses point, tangent, and normal operations, never radius/angle.
5. Path-type decisions remain in path generation and explicit geometry metadata.
6. The complete master centerline remains the single geometry source.
7. Segments are semantic or painted ranges, never independent geometry truth.
8. Normalized ranges and dash rendering use `0..100` consistently.
9. Actual browser length is used only inside measured geometry and physical
   layout calculations.
10. Geometry measurements are cached and never repeated for state-only updates.
11. Defaults and validation exist only in the configuration/constructor layer.
12. A new shape should require a generator and contract tests, not renderer forks.
13. A failed generic rendering proof changes the capability contract; it is not
    patched with distributed shape-specific conditions.

---

# 9. Definition of done

The path-engine foundation is complete only when:

- the browser geometry lifecycle is deterministic and produces no visible first
  or intermediate layout;
- arc, line, rectangle, and wave implement the same geometry contract;
- spiral and infinity have either passed the same contracts or have documented,
  justified capability limits before public release;
- ranges are path-independent and use only normalized progress;
- stroke/dash rendering, gaps, and mixed caps pass on all admitted shapes;
- transparent fill and border composition is visually proven;
- full and current gradients meet quality and performance budgets;
- ticks, labels, and markers use only measured geometry operations;
- unchanged geometry is measured once and reused across state updates;
- at least one existing horseshoe configuration reaches old/new parity through
  `horseshoes_v3`;
- the parity matrix covers every existing horseshoe feature;
- no renderer or feature-layout layer contains hidden arc-specific calculations;
- all new functions follow the repository's linear implementation style and have
  meaningful JSDoc and inline flow comments.

Only after full parity may the current horseshoe implementation be replaced.

---

# 10. Concise implementation brief

Build Horseshoe V3 as a reviewed, browser-measured path architecture rather than
a copied progress-path tool. Preserve the current FHS horseshoe as the functional
reference. Generate one stable centerline path, map entity values to semantic
`0..100` ranges, bind the path to an SVG geometry element for actual coordinate
queries, and render ranges through shared stroke, dash, mask, and gradient
capabilities. Prove the lifecycle and basic renderers on arc, line, rectangle,
and wave before adding spiral and infinity as stress cases. Freeze the public
shape configuration only after those proofs pass. Then connect the existing
horseshoe configuration through a temporary `horseshoes_v3` adapter and migrate
features one at a time until complete parity permits replacement of the old
implementation.
