# 12 - Theme-aware shared color cache

## 1. Goal

Share numeric color conversions between cards using the same effective color environment, while keeping different Home Assistant global themes, inherited view themes, modes and palette sources independent. A card must always resolve CSS against its own host.

No public YAML changes are required. The existing configured CSS colors, variables, fallbacks, interpolation, gradients and filters keep their meaning.

## 3. Current-code validation

Three defects were reproduced against the baseline using real Colors/CardTheme/CardEntities with a computed-style boundary:

- After theme A converts `var(--primary-color)` to red, theme B receives red from the expression-only cache instead of blue.
- Even with an empty cache, CardEntities for card A resolves blue from card B because the last caller changed the global `Colors.element`.
- A card with a blue palette variable caches `var(--fhs-test, red)`; a second card without that palette receives blue instead of its configured red fallback.

CardTheme additionally reads `hass.selectedTheme` as a name. HA defines that field as picker settings; recreating the settings object incorrectly reports a theme change. The global runtime name is `hass.themes.theme`.

The user explicitly included HA view themes. HA applies their variables on `hui-view-container` while forwarding the unchanged hass object to cards:

- https://github.com/home-assistant/frontend/blob/dev/src/panels/lovelace/views/hui-view-container.ts
- https://github.com/home-assistant/frontend/blob/dev/src/common/dom/apply_themes_on_element.ts
- https://github.com/home-assistant/frontend/blob/dev/src/data/ws-themes.ts

The same declared view theme can inherit missing variables from the global theme. An explicit `default` view theme can also differ from the globally customized default. Therefore cache identity must retain both global and view selections, not merely the effective name.

Inventory the complete chain: CardTheme publishes context; CardEntities, filters and tools consume it; Colors converts and caches; Sparkline and horseshoe owners retain paints; the existing post-commit follow-up refreshes paints after current CSS is present.

## 4. Scope

Explicit conversion context, shared context-aware cache, HA global/view theme changes, palette application/removal and the minimum paint-only refresh needed by existing retained paints. Add permanent reproductions and real-module/browser tests.

## 5. Out of scope

- New per-card theme settings, per-card conversion caches or computed-style fingerprints.
- Conflicting manual CSS overrides under the same declared environment.
- Changing color, interpolation, filter or CSS fallback formulas.
- History, aggregation, statistics, normal geometry, pointer or animation redesign.
- A generic invalidation framework, polling, unrelated guards or metadata changes.

## 6. Design and owner boundaries

### Prepared context

CardTheme owns `colorContext`: host element, global theme name, optional view theme name, active mode, current HA theme source, applied palette sources and cache readiness. Constructor/configuration boundaries supply initial values. Consumers receive this prepared context; they do not discover themes or manipulate cache entries.

Find the closest HA view container through composed ancestry, including slots and shadow hosts, on connection. Without an explicit view theme, retain the global selection. Recheck the stored view selection on HA updates. Share one view-style MutationObserver among subscribing cards, and remove it after the last disconnect. Its callbacks use existing post-commit scheduling; there is no polling or full DOM observer.

### Conversion and cache

Colors APIs receive explicit context. Remove the mutable global host and all `setElement()` calls after migrating their consumers. Filters, CardEntities, horseshoes, adaptive path gradients and Sparkline paints pass the current context. Graph gradient calculations receive an interpolation callback from the tool, so Graph remains independent of HA and DOM.

Colors alone owns buckets identified by the global/view theme combination and applied palette source sequence. Within a bucket, configured expressions map to RGBA values. Literal colors remain in the same bucket; no second literal cache is introduced.

Each bucket retains one active light/dark mode. A changed mode, HA theme definition source or applied palette revision invalidates that bucket once. Another card observing the same change must reuse freshly rebuilt results. Switching contexts preserves unrelated buckets. Buckets store no card/DOM references.

Context is not cacheable before the host has current theme CSS and the current palettes are applied. Unresolved colors remain uncached. Preserve nested fallback parsing and modern browser color resolution. Palette declarations preserve their existing order; unique names retain their stable meaning.

### Palette and retained paint

Apply the active palette mode before publishing it. Remove only obsolete variables previously owned by that card's palettes. Configuration replacement/removal, stale completions and disconnect/reconnect retain Plan 06 validity rules.

Use the existing Lit commit plus RAF follow-up to publish settled context and refresh retained paints. The follow-up must not fake a hass assignment. Update single/multi-series paints, horseshoe state/scale colors, gradients and marker colors using their existing owners. Reuse processed rows, statistics, coordinates, measured paths and animator progress. Separate color refresh from horseshoe value/range mapping where necessary; share its paint rules rather than adding a second interpretation.

Record one producer, stored result, consumer set and recalculation trigger for every affected calculation. Add functional English JSDoc/inline comments explaining identity, timing and reuse, rather than narrating assignments.

## 8. Permanent tests and acceptance

- Before each repair, confirm a small failing reproduction and its reason.
- Same-context conversion reuse; separate global themes and view themes, including partial inheritance and explicit default view.
- Light/dark/light changes, theme-definition reload under an unchanged name, repeated same change from multiple cards and picker-object recreation without a real change.
- Palette addition, replacement/removal, different availability and configured fallbacks; delayed application and stale completion/disconnect/reconnect.
- Modern CSS color functions, gradients/interpolation, filters and actual retained single/multi-series and horseshoe/marker paints.
- View change without entity update; observer sharing and complete cleanup/reconnect.
- Real neighbouring modules and complete-card DOM/computed paint, mocking only HA/network/time/DOM boundaries.
- Multiple-card cold/warm conversion counts; zero history, aggregation, statistics, normal geometry or path measurement for paint-only updates.
- Full Node suite, lint and affected Chromium/WebKit browser regressions after user visual approval.

Measure calculation separately from rendering. Reuse/owner counts are acceptance criteria; no arbitrary speed target or unnecessary screenshot matrix.

## 9. Definition of Done

Correct host and environment for every conversion; shared reuse remains; invalidation belongs only to Colors; CardTheme owns identity and lifecycle. All retained paints receive current colors without repeated data/geometry work. Public configuration and established algorithms remain compatible. Required checks pass and final whole-chain review has no unresolved findings.

## 10. Guarantees for following plans

Final cleanup may remove obsolete global-host/whole-cache-clear code, but must preserve explicit context, shared reuse, per-context invalidation and paint-only updates. Later plans consume prepared colors and geometry rather than discovering context or redoing calculations.
