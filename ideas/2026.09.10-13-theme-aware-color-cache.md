# 13 — Theme-aware global color cache

## 1. Goal

Preserve the original performance purpose of `Colors.colorCache`: once FHS has numerically converted a color, other cards using the **same theme** should be able to reuse that conversion.

At the same time, prevent a cached CSS-variable expression from one theme from being reused under another theme where the same variable name has a different value.

This is a lower-priority correctness/performance refinement. Do not let it distract from lifecycle/history/resource work.

## Architectural place in FHS

Plan 00 places this work after the lifecycle, history, resource, animation and
render-scheduling changes. Plan 13 must therefore remain a focused color-cache
change, not a second update or invalidation architecture.

The responsibilities stay separated:

- `Colors` owns color resolution, numeric conversion and the reusable cache.
- `CardTheme` owns the effective Home Assistant theme name, light/dark mode and
  invalidation of theme-dependent paint, palettes and paths for its card.
- `main.js` only publishes the Home Assistant update and orders the card
  lifecycle; it does not manage color-cache entries.
- tools, gradients, filters and horseshoes request colors through `Colors`; they
  do not clear or rebuild the global cache themselves.

Theme or palette changes are paint changes. They do not request history,
reaggregate graph data or rebuild normal geometry unless an existing paint
route genuinely requires it. No generic invalidation framework, new per-card
theme mechanism or new cache owner is introduced.

This plan follows the implementation order from Plan 00 and must not be used to
rewrite proven color, gradient or filter calculations.

## 3. Review reproduction

The reviewed cache lookup occurs before CSS-variable resolution.

Conceptually:

```text
card/theme A:
  colorToRGBA('var(--review-color)')
  computed style -> red
  global cache['var(--review-color)'] = red RGBA

card/theme B:
  same expression should resolve blue
  cache lookup finds existing red first
  computed style for B is skipped
  result incorrectly remains red
```

This affects colors FHS must numerically process, such as interpolation/filter calculations. A plain SVG/CSS declaration left for the browser to resolve does not necessarily use this conversion route.

## 4. Refined design decision

Do **not** replace the shared cache with one complete cache per card.

Desired structure is conceptually:

```text
colorCache
  theme A
    active mode: light
    colors
      var(--primary-color) -> RGBA
      #123456 -> RGBA (if kept in same bucket)
  theme B
    active mode: light
    colors
      var(--primary-color) -> different RGBA
```

The exact object/Map shape and property names should follow existing `Colors` style. The words above are not identifier instructions.

The cache identity is the effective theme name, the active light/dark mode and
the configured color expression. The active Home Assistant theme name comes
from `hass.themes.theme`; `selectedTheme` is theme-picker/local-storage data and
is not the runtime theme identity. There is currently no FHS `theme:` option
that lets a user select a separate Home Assistant theme for one card.

FHS palettes use namespaced variables such as `--fhs-ref-*` and `--fhs-sys-*`.
The supported palette rule is that one `--fhs-*` variable name has one stable
meaning and value within an effective theme/mode. If two palette definitions
need different values, they must use different variable names. The `fhs-`
prefix provides a namespace; it does not by itself make a duplicate variable
name safe.

## 5. Why theme-level sharing

If ten FHS cards use the same Home Assistant theme, the expensive CSS-variable resolution/parsing/conversion should be reusable between them where the effective theme color is the same.

Desired:

```text
first card using theme X -> calculate/cache
other cards using theme X -> reuse
card using theme Y -> separate value
```

This keeps the original global-cache optimization.

## 6. Dark/light behaviour

Do not preserve two permanent caches merely to make a later light -> dark -> light switch reuse an old value.

Instead, each theme cache only needs to represent its currently known dark/light mode.

Conceptually:

```text
theme X bucket currently light
HA/FHS sees theme X in dark mode
-> clear X's stored color conversions once
-> mark X bucket as dark
-> lazily repopulate dark values
```

When light returns, clear/repopulate again.

This avoids unnecessary long-lived duplicate color data.

## 7. Avoid repeated clearing by identical cards

Because the cache is global but `CardTheme` exists per card, two cards using the same theme can both observe the same mode change.

Do not let this happen:

```text
card A sees dark -> clears theme X -> calculates new dark colors
card B sees dark -> blindly clears theme X again -> discards A's freshly calculated dark colors
```

Therefore the shared theme bucket needs enough information to know which mode its values represent, or equivalent central logic in `Colors` must make invalidation idempotent for that theme/mode.

This is **not** a second dark cache. It is only a marker for the one active set of values.

## 8. Effective theme name

`CardTheme` is the FHS component that knows which theme name applies to the card's color processing.

Before implementation, Codex must verify the current Home Assistant/FHS source used for:

- global theme;
- view-level inherited theme;
- any currently supported card-level theme configuration.

The resulting functional rule is fixed:

```text
Colors must receive/use the theme name that actually applies to the card whose CSS variable is being resolved.
```

Do not invent a separate FHS theme-detection system when Home Assistant/current card config already provides the name.

If current FHS does not yet expose an explicit per-card `theme:` option, do not add one as part of this cache fix. The cache design must simply be ready to use the chosen theme name if/when FHS has one.

## 9. Current `Colors.element`

FHS currently uses a card element reference to resolve CSS variables through computed style.

Preserve that mechanism unless a separate demonstrated bug requires change.

The cache fix is about **cache identity**, not replacing `getComputedStyle()` resolution.

`Colors.element` remains the current card scope used while CSS variables are
resolved. Palette variables are still applied to the individual card host. The
shared cache is safe under the palette naming rule above; this plan does not
add a computed-style fingerprint or a complete cache per card.

## 10. Literal colors

Literal colors such as `#123456` do not depend on a CSS theme.

Two acceptable implementations:

1. keep all converted colors inside the per-theme bucket for simplicity;
2. retain a separate shared literal-color cache if the code remains obviously readable.

Do not add complexity for marginal memory savings. Theme-scoped caching of literals is acceptable if it keeps the implementation linear.

## 11. CSS fallbacks

`var(--x, fallback)` resolution must continue to follow current `Colors` semantics. The cache key remains the actual color expression within the correct theme/mode bucket.

Do not redesign CSS parsing in this plan.

## 12. Palette interaction

Palette application can update CSS variables used by FHS. Existing `CardTheme.loadPalettes()` clears the color cache after applying palettes.

With theme buckets:

- invalidate the relevant theme bucket when its effective palette variables change;
- do not unnecessarily destroy unrelated theme buckets;
- preserve async stale-result rules from Plan 11.

## 13. Theme name change on one card

If one card moves from theme A to theme B:

```text
card now reads/writes B bucket
A bucket remains reusable by other cards still on A
```

Do not globally clear all themes solely because one card changed theme, unless Home Assistant itself performed a global operation that makes all buckets invalid.

## 14. Global dark/light switch

When every card's effective dark/light mode changes, each used theme bucket will eventually be reset for the new mode. The idempotent per-theme mode check prevents multiple cards using the same theme from repeatedly clearing the fresh bucket.

## 15. Manual per-element CSS variable overrides

The primary supported target is Home Assistant theme identity. Do not turn this plan into a general computed-style fingerprint cache.

If users manually override the same global theme variable name differently on individual FHS cards while still declaring the same theme name, that can be treated separately unless current FHS explicitly supports that as a first-class theme mechanism.

A user should normally use a different/custom variable for card-specific semantics rather than redefining the same global theme variable under an identical theme identity.

The same rule applies to FHS palettes: a card-specific palette value must use a
unique `--fhs-*` variable name. Deliberately redefining one existing variable
with a different value on only one card is outside the supported shared-cache
contract.

## 16. Naming rules

Keep current names such as:

- `colorCache`
- `colorToRGBA`
- `getColorVariable`
- `setElement`
- `CardTheme`
- `theme`
- `darkMode`

Do not introduce:

- `ColorContract`
- `ThemeFeature`
- `ResolvedThemeContext`
- `CommittedColor`

If a small method is needed to obtain/reset one theme's cache, name it after that concrete operation using current `Colors` style.

## 17. Implementation sequence

Follow Plan 00's test-before-change rule:

1. Open the current source and confirm that the cache lookup precedes CSS-variable resolution and that `CardTheme` still performs whole-cache invalidation.
2. Add a baseline-failing reproduction using two effective theme identities with the same CSS-variable expression and different computed values.
3. Add the neighbouring `CardTheme` + `Colors` tests for shared same-theme reuse, theme separation, mode changes and palette application.
4. Change the minimum `Colors`/`CardTheme` interface needed to carry the effective theme name and active mode. Read the active name from `hass.themes.theme`; do not use `selectedTheme` as a runtime fallback.
5. Replace destructive whole-cache clearing with idempotent invalidation of the active theme/mode bucket. Preserve the global/shared cache and existing CSS-variable resolution.
6. Preserve palette invalidation after palette variables have been applied. Keep unique `--fhs-*` variable names as the supported palette contract.
7. Run the focused tests after each meaningful step, then run the complete Node suite and all affected browser tests.
8. Search for remaining whole-cache clears, direct cache ownership outside `Colors`, and internal card-update re-entry introduced by this work.

## 18. Required tests

Before changing production code, at least one test must fail on the baseline for
the reproduced cache contamination. Tests must assert functional color results
and lifecycle effects, not a newly invented cache class or architecture name.

### Layer A — color calculation and reproduction

- same effective theme, same variable and same resolved color reuse one result;
- different effective themes, same variable name return independent RGBA values;
- light -> dark -> light does not reuse a stale conversion from the previous mode;
- literal colors, CSS fallbacks and nested variables retain current conversion semantics;
- the active name is taken from `hass.themes.theme`, not `selectedTheme`.

### Layer B — neighbouring FHS modules

Use real `CardTheme` and `Colors` together, with only CSS/DOM boundaries mocked.

- two cards on one theme/mode do not repeatedly clear a freshly populated bucket;
- palette application followed by conversion uses the active palette value;
- a palette change invalidates the relevant active theme/mode values;
- a second palette using a unique `--fhs-*` name does not collide with the first;
- gradient interpolation and color-filter conversion receive the correct colors.

Do not add a test that relies on two cards deliberately redefining the same
`--fhs-*` variable differently; that is outside the supported configuration
contract.

### Layer C — complete card route

Use the real card/main route with a color-stop, gradient or color-filter user
configuration and assert that:

- the first render uses the correct theme color;
- a theme/mode change repaints the card without history requests,
  reaggregation or an unrelated geometry rebuild;
- palette completion repaints the configured color-dependent output;
- two simultaneous cards do not contaminate one another;
- existing YAML remains unchanged.

### Layer D — browser behaviour

Use real browser CSS resolution for at least one two-card reproduction with the
same variable name and different effective theme values, plus a light/dark
transition. Assert SVG attributes/styles directly; screenshots are unnecessary
for this cache contract. Run the affected Chromium tests and the WebKit route
before the plan is complete when the browser setup supports both.

Also run the full Node suite. Do not replace it with change-based partial test
selection; the suite is short enough for complete execution.

## 19. Required end state

- cache remains global/shared;
- cards using the same effective theme reuse calculations;
- different themes cannot cross-contaminate CSS-variable conversions;
- dark/light switch invalidates the one active cache for that theme instead of storing permanent light/dark duplicates;
- repeated same-theme card updates do not repeatedly clear a freshly rebuilt bucket;
- no per-card cache architecture or new theme mechanism is introduced unnecessarily.
