## 1. Goal and Functional Boundary

Complete the common configuration route established by Plan 15B and move
TextTool onto the same configuration, runtime, geometry and paint ownership.
Preserve existing public YAML, JavaScript behavior, formatting, style priority,
text calculations, measurement timing and connection lifecycle.

The prerequisite includes the 15B follow-up in PR #841, which preserves Icon
state-map styles when a parent supplies a complete paint-style map.

```text
sourceConfig
    -> optional evaluation with the existing item/entity context
    -> local newConfig
    -> existing post-evaluation translation/completion
    -> this.config
```

`sourceConfig` is the stable template-visible source, including the preparation
that JavaScript already observes. `this.config` is the sole current general
configuration. Runtime values, derived geometry and parent-driven styles have
their own owners.

This is an ownership refactor. Existing JavaScript evaluation/error behavior
stays unchanged. Do not add validation/recovery states, last-good configuration,
new runtime defaults or defensive checks. Preserve legitimate unavailable and
undefined runtime values and existing handling of user-authored templates.

## 2. Current Findings and Decisions

### BaseTool and the Common Entity Context

BaseTool already clones source configuration, accepts an explicit pure
translator and distinguishes configuration, group and theme changes. Retain
that mechanism; do not introduce another configuration framework.

Common entity data is still stored as `this.entity` and `this.entityConfig`.
Move those fields atomically to `runtime.entity` and `runtime.entityConfig`
across BaseTool and all its consumers. The inspected footprint includes
Name/Area/State/Icon, control consumers, Horseshoe and Sparkline, including
Sparkline's temporary StateTool formatting instances.

The migration is mechanical and does not migrate those families' other owners
ahead of their plans. Existing Name/Area/State/Icon runtime initialization must
extend the common runtime object rather than replace its entity fields.
Update prototype-created formatting instances and test fixtures explicitly.
Series-item `entity` and `entityConfig` fields are separate domain data and stay
unchanged. No compatibility getters or duplicate old/new fields are retained.

BaseTool initializes the common runtime object once. Subclasses extend that
object instead of assigning a replacement runtime object. Horseshoe's legacy
`runtimeConfig` and `activeItemConfig` are part of its unmigrated configuration
route, not aliases of runtime entity data. Keep those fields until Plan 19;
their removal is outside 16B Pass B.

### Text Configuration and Evaluation Order

TextTool currently removes `text` from the outer config and owns
`sourceTextParts`, `activeTextParts` and a separate parts signature. This leaves
two configuration paths inside one tool. The target stores the source parts in
`sourceConfig.text` and the completed current parts in `config.text`.

TextTool has one source configuration and one current configuration.
Outer Text fields and Text parts may require separate JavaScript evaluation
because they have different item/entity contexts, but those phases never
become separate persistent configuration owners.

Preserve these established preparation boundaries:

| Work | Boundary to preserve |
| --- | --- |
| Scalar text becomes a parts array; default part type, newline spacing and scalar localization are supplied | Before source capture, as currently visible to part templates |
| Outer tap-action and wrap-spacing defaults; existing overflow validation | Constructor/source preparation |
| Outer JavaScript evaluation | Existing outer item context and evaluation triggers |
| Inline source configuration updates | After outer evaluation, before per-part evaluation |
| Part id/entity context and JavaScript evaluation | Existing source-tool binding and per-part context |
| Configured color-stop and mode completion | Existing configuration boundary, subject to the staged color-stop exception below |
| Current entity values, state-map selection and localization output | Runtime processing |

Create a local `outerSource` projection containing the source fields other than
`text`. Use that projection both as the outer evaluator's value and as its
`item` context. Outer JavaScript detection and scheduling must scan that
projection only. BaseTool must neither detect nor recursively evaluate
`sourceConfig.text` as outer JavaScript. Hiding text only from `item` while
passing the complete source as the evaluated value would still be incorrect.

Part JavaScript is detected separately and evaluated only in its own Text-part
phase. Two scheduling signals are allowed because the contexts differ;
`textPartsHaveJavascript` may remain as immutable scheduling metadata if useful.
Keep `outerSource`, evaluated outer fields and evaluated parts local. Do not
persist `outerSourceConfig`, `activeTextConfig` or another source/current copy.

Preserve the containing item's id for ordinary parts, explicit part ids,
referenced source indexes and inline-source identity. Each part keeps its
current entity context. Reuse the existing Templates evaluator unchanged.

The normal runtime-configuration phase follows this exact sequence:

1. Project the outer source and evaluate its fields in the existing outer
   item/entity context when the existing outer schedule requires evaluation.
2. Update inline Name/Area/State source-tool configuration at the same boundary
   as today, before evaluating Text parts.
3. Evaluate each source part with its existing part context and the source
   binding available at this point. Source tools retain their own evaluation.
4. Bind the evaluated part's entity index to its inline source tool during
   configuration processing, after that part has been evaluated.
5. Assemble local `newConfig` from the current outer fields and evaluated parts;
   finish the existing part completion/normalization in `newConfig.text`.
6. Publish the complete current Text configuration once.
7. Run `setState()` to supply entity/runtime data and build displayed output.

Do not bind the new part index before part evaluation or silently reverse the
source-tool/part evaluation order. Characterize the sequence across initial
and successive updates before moving the binding out of `setState()`.

### BaseTool Pre-Publication Boundary

BaseTool currently publishes config inside `updateRuntimeConfig()`, before
TextTool performs its part work. Add one small explicit pre-publication
completion/evaluation boundary inside that normal BaseTool runtime route.
Ordinary tools keep their existing simple path; TextTool uses the boundary to
finish context-dependent parts and inline bindings before publication.

Reuse BaseTool's existing outer evaluation rather than copying its evaluator
into TextTool. Supply Text's local outer projection to that evaluation so part
templates are excluded from both outer detection and evaluation. BaseTool then
publishes `this.config` once, after Text completion; TextTool must not publish
an outer-only config and later replace it or append evaluated parts to it.

The boundary is runtime-only. It is not dispatched virtually from the BaseTool
constructor. Preserve the existing explicit pure translator for constructor
translation and the same source/default ordering on later updates.

Keep the existing evaluation schedules, including the cases where parts are
reevaluated after group/theme changes. A group/theme refresh does not imply
retranslating an unchanged structural configuration. Signatures may distinguish
those schedules where needed; they are change signals, not stored config copies.
Exclude geometry, runtime output and derived paint from structural equality.

`setState()` does not assign inline-source entity bindings, write
`sourceTool.config.entity_index` or publish another config. Inline sources remain
real child tools with their own normal config, rather than another Text config.

### Text Runtime, Geometry and Lifecycle

- Displayed parts belong to `runtime.textParts`. Selected state-map entries
  and resolved display values remain local unless later processing reuses them.
- Derived SVG coordinates, estimated/measured bounds, font metrics and fit
  scale belong to `geometry`, matching Name/Area/State.
- Persistent width/wrap measurement results belong to geometry; displayed
  overflow parts belong to runtime. Use existing meaningful field names within
  these owners, without introducing wrapper classes or a generic cache layer.
- DOM bindings, scheduled frames, font-wait jobs and connection state retain
  their explicit lifecycle ownership. Their identity/revision checks protect
  real asynchronous work and are not redundant configuration checks.
- Preserve stale-result rejection, disconnect/reconnect, the current retention
  of measured text while a replacement measurement is pending, and correction
  renders for rectangles that fit around text.

Preserve wrapping, ellipsis, fit and measurement algorithms. Ownership changes
must not become a rewrite of their calculations.

Record the concrete field map before implementation. The target for current
fields is fixed by their functional role:

| Current field | Target owner | Action |
| --- | --- | --- |
| `sourceTextParts` | `sourceConfig.text` | Remove separate source owner |
| `activeTextParts` | `config.text` | Remove separate current owner |
| `activeTextPartsSignature` | Configuration change signal, if necessary | Adapt or remove after proving its purpose |
| `textParts` | `runtime.textParts` | Move |
| `config.svg` | `geometry.svg` | Move |
| `textFitScale` | `geometry.textFitScale` | Move |
| `characterWidthFactor` | `geometry.characterWidthFactor` | Move |
| `textFontSize` | `geometry.textFontSize` | Move |
| `estimatedWidth`, `estimatedHeight` | Same fields under `geometry` | Move |
| `measuredWidth`, `measuredHeight`, `measuredXpos`, `measuredYpos` | Same fields under `geometry` | Move |
| `hasExactMeasurement` | `geometry.hasExactMeasurement` | Move |
| `textMeasurementSignature` | `geometry.textMeasurementSignature` | Move |
| `widthMeasurementParts` | `runtime.widthMeasurementParts` | Move measurement content |
| `widthOverflowParts` | `runtime.widthOverflowParts` | Move displayed overflow result |
| `widthOverflowSourceSignature`, `widthOverflowMeasurementSignature` | Same fields under `geometry` | Adapt measurement-input/result comparison |
| `textElement`, `setTextElement`, `textElementId` | Existing explicit DOM bindings | Keep |
| `widthMeasurementElements`, `widthEllipsisElements` | Existing explicit DOM arrays | Keep |
| `widthOverflowRevision` | Existing async request identity | Keep |
| `widthMeasurementScheduled`, `widthMeasurement` | Existing async scheduling/job ownership | Keep |
| `widthOverflowPending` | Existing async measurement lifecycle | Keep |
| `textClosed` | Existing connection lifecycle | Keep |

Do not group those lifecycle fields into a generic `cache`, `measurementState`
or `lifecycleState` object. Display content used for measurement remains runtime;
DOM arrays and async identity remain explicit. Geometry owns measured results,
not the pending job's lifetime.

### Parent Paint and Measurement

Retain the 15B presentation API:

```text
config.styles                    configured styles
paint.styles                     complete parent-resolved replacement, if present
paint.styles ?? config.styles    input to the existing style cascade
```

`setPaintStyles(styles)` publishes that complete map; passing undefined clears
it. Do not merge configured styles back into a replacement map. Preserve the
subsequent source/part/state-map, color-stop, animation and filter priorities
at their existing boundaries. The order is characterized before moving code.

TextTool must support this route as Name/Area/State already do. Measurement
signatures use the effective styles, including relevant part/source styles.
A font-metric change with unchanged displayed text must invalidate the affected
measurement. Repeating the same effective styles must not continually restart
measurement. Publishing paint must leave configured styles unchanged.

Characterize outer paint font changes and effective part/source font changes
separately, both with unchanged displayed text. Measurement equality must cover
the complete effective measurement input, not only outer `paint.styles`.

Production control callers retain their current style route until Plan 17B.
This plan proves the child API, including its measurement effect, without
performing the control-family migration early.

### Geometry Accessor and Color-Stop Staging

Keep `text-tool-geometry.js` as the shared accessor selecting estimated or exact
text bounds for CardTools. After TextTool migrates, remove its dual-storage
compatibility branch: all these text tools expose `geometry`.

The shared group-origin adapter still supports other unmigrated families;
do not remove that unrelated staging route in this plan.

Keep current shared active color-stop storage as an explicit legacy exception
until the atomic cutover at the end of Plan 19. Do not create duplicate
`config.colorstops` and `paint.colorStops` owners. Preserve ColorStops and
ColorFilter algorithms and the existing distinction between configured parts
and runtime-selected state-map overrides.

configuration once. Text projects only outer source fields into the existing
evaluator; prepared source parts live in `sourceConfig.text`, completed parts
in `config.text`. Inline source updates precede part evaluation; final child
bindings are complete before publication. `setState()` only consumes those
