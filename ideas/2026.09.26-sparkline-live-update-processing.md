# Sparkline live-update processing

## Purpose

Keep dashboards with many sparklines responsive when Home Assistant publishes a
new value. Each series processes that update once and retains all measurements
needed for its graph and statistics.

Issue: #753. Implementation branch:
`753-reduce-repeated-sparkline-processing-on-live-updates`.

Plan 09 was accepted and merged separately through PR #754 before this work.

## Measured cause

A controlled Chromium dashboard with 24 historical line cards and about 800
source rows per card reproduced substantial processing cost without debug
logging, additional history requests or pointer interaction. A changed sensor
value caused three complete history conversions and two statistics calculations
per single-series graph. Presentation detection also serialized complete graph
coordinates and bucket metadata on ordinary HA updates.

This establishes costly live-update work. The exact relationship to the user's
recurring dashboard CPU peaks still requires visual/live verification.

## Implementation

1. History retains the chronological order supplied by HA and copies the
   response for its own live insertion and pruning. Live measurements are
   inserted chronologically; a matching timestamp retains the existing
   correction rules. Calendar projection restores plot order only when moving
   the repeated winter-time hour onto another day reverses that order; this is
   part of History's timestamp conversion, before any graph consumes the rows.
2. History reuses converted measurements until their value, source-to-plot
   offset or categorical state map changes. Unchanged windows retain their row
   array. Changed sources report their inserted, corrected or expired rows
   locally. History updates only those prepared rows and publishes an immutable
   array snapshot; pruning retains the state immediately before the visible
   window. A new response or changed conversion settings rebuilds the collection.
3. Cartesian Series coordination performs pruning and statistics once for each
   item. GraphTool builds line, area, minmax and point paths once after shared
   geometry is final. Single-item paint layers and multi-series rendering consume
   these paths. Rendering no longer repeats Graph's path calculations.
4. Presentation detection compares Graph's existing processed-data revision and
   geometry signature. Statistics, paint, loading state and legend changes still
   participate in normal rendering.
5. History delivers source changes together with the prepared rows: a replacement,
   the previous delivered rows and the earliest altered plot timestamp. Pending
   live insertions, corrections and pruning belong to the same next delivery.
   History reports those facts; Graph chooses how to process them.
6. Graph retains raw bin groups and their computed results locally. Live updates
   rebuild the affected tail, normally just the active bin. Completed bins reuse
   their aggregates and min/max summaries. A moving window updates its first
   state and expires old groups; a changed bin plan or replacement source rebuilds
   the bins. Real-time remains a single current-value bucket, and state bands
   retain their separate transition-time behavior.
7. Plot values, tooltip metadata and min/max envelopes consume the same bin
   result. Whole-period statistics reuse the bin summaries too, preserving the
   time-weighted average, first/last interval clipping and extrema timestamps.
   The first plotted bin still keeps its latest value while period statistics
   include its earlier peaks. No raw-history statistics scan follows each live
   measurement in the normal prepared-data route.
8. Single-bar presentation uses Series' final rectangles, including the centered
   real-time bar. Point rendering uses already prepared coordinates. Preliminary
   bar measurements for outer margins remain distinct from the final rectangles.

History owns retained measurements and their conversion. Series continues to
coordinate Graph processing and shared scales. Graph owns aggregation, geometry
and statistics; GraphTool consumes those results for presentation.

## Verification

Preserve numeric results, min/max bands, retained samples, offset projection,
categorical state mapping, shrink/expand request reuse, empty results and pointer
behavior. Add bounded tests for reuse and owner call counts alongside the
existing lifecycle/history regressions.

The first identical 24-card comparison measured changed-value updates at about
360-380 ms on master and 75-90 ms with this fix. An unchanged-value HA update
changed from about 125 ms to 2 ms. Statistics calls fell from 48 to 24. Both builds
reported no page errors or new history/pointer work during those updates.
Wall-clock numbers are environment-dependent; retained measurements and operation
counts are the permanent acceptance criteria.

A second comparison measured the first populated render at about 498 ms on
master and 269 ms with the fix. HA history responses were immediate in this
fixture, so this measures local initialization/rendering rather than network
latency. The user also observed a faster dashboard after F5.

All 414 Node tests, lint, and all 11 affected lifecycle/history/pointer browser
cases pass in both Chromium and WebKit on the CPU test build. Two new permanent
regressions check converted-row reuse with appended/delayed/corrected samples and
exactly one pruning, aggregation and statistics pass for a changed single series.

User dashboard validation reported brief peaks around 0.1% and occasionally
1.8%, replacing the longer 4-5% peaks observed before this fix.

### Follow-up measurement, 2026-09-27

Further profiling found that statistics still sorted already ordered rows and
converted their timestamps repeatedly. Cartesian line paths were also built
twice: shared preparation generated them, then single-item preparation or the
multi-series renderer generated them again. Both duplications are removed in
this same issue and implementation branch.

A direct comparison with commit `5f77e71` used the same 24-card fixture, five
changed-value warm-up updates and fifteen measured changed-value updates:

| Operation | Before | After |
| --- | --- | --- |
| Statistics, average total | 38.6 ms | 12.5 ms |
| Main line path calculations per update | 48 | 24 |
| Complete update, average | 89.5 ms | 74.8 ms |
| Complete update, median | 86.1 ms | 79.1 ms |

The complete update averaged about 16% less time in this run. These measurements
include actual Lit rendering and report no page errors, extra history requests
or pointer work. Timing remains machine-dependent. Tests assert chronological
response ownership, unchanged time weighting, extrema timestamps and one path
calculation per geometry update, including minmax and point layers.

### Incremental processing, 2026-09-27

The two-week regression supplies 20,160 measurements at one-minute intervals.
Adding a live value assigns only the active bin's 16 measurements again; completed
bin summaries retain their identity. Tests compare incremental and full processing
for all nine aggregate functions, appended/delayed/corrected/removed measurements,
window movement, empty-bin carry, calendar midnight and source replacement.
The actual History -> Series -> Graph -> Tool route also checks that old bins are
reused and that single-bar/point rendering adds no final geometry calculation.

Two controlled Chromium comparisons used commit `5f77e71` and the new build.
Both had 24 line cards, real Lit rendering and no extra requests or pointer work:

| Workload / operation | Before | After |
| --- | --- | --- |
| 24 hours, 800 rows/card: complete update, average | 110.8 ms | 51.5 ms |
| 24 hours: statistics, average total | 45.8 ms | 1.1 ms |
| Two weeks, 20,160 rows/card: complete update, average | 1591.1 ms | 156.6 ms |
| Two weeks: bin processing, average total | 376.4 ms | 31.6 ms |
| Two weeks: statistics, average total | 1093.0 ms | 5.6 ms |

The 24-hour run measured fifteen updates after five changed-value warm-ups; the
two-week run measured five after the same warm-up. Neither run reported browser
errors. These are fixture timings, not guarantees for every dashboard.

This run identified a further 39.4 ms spent publishing History arrays and 29.8 ms
building line paths. History still walked retained source rows when publishing a
changed array, although conversion was cached. That publication cost is addressed
in this same issue below. This change does not claim that every remaining cost
is SVG rendering or that processing occupies a fixed percentage of the update.

All 432 Node tests and lint pass. The nine affected History, pointer and card
change-detection browser tests pass in Chromium and WebKit. The build is available
for user dashboard validation; master has not been changed.

Build for user verification before another master merge. Full Node tests, lint
and affected Chromium/WebKit regressions remain required before that merge.

### Incremental History publication, 2026-09-27

History now records inserted, corrected and expired source rows itself. Ordinary
live preparation converts only the changed measurements and inserts/removes
their prepared rows in chronological plot order. Unchanged row objects are
reused. A new history response, changed offset or changed categorical mapping
still prepares the complete dataset at that boundary.

The new published array retains the previous snapshot for Graph. A normal append
uses one native `concat` allocation rather than copying and then enlarging the
backing array again. Corrections and expiry preserve the existing seed state and
invalid-state rules. Binary plot-time lookup also preserves ordering when winter
time projects several source measurements onto the same local clock time.

The final controlled comparison used 24 cards, the same `5f77e71` baseline and a
fixed clock advanced one second per changed measurement. Both versions remained
inside the same bin, with no incidental boundary-timer work, extra requests,
pointer work or browser errors. Five changed-value warm-ups preceded fifteen
measured updates for 24 hours and five for two weeks.

| Workload / operation | Before | After |
| --- | --- | --- |
| 24 hours: History publication, total average per update | 1.3 ms | 0.5 ms |
| Two weeks: History publication, total average per update | 33.8 ms | 6.8 ms |
| 24 hours: complete update, average elapsed time | 102.9 ms | 49.4 ms |
| Two weeks: complete update, average elapsed time | 1621.6 ms | 121.4 ms |
| 24 hours: renderer main-thread CPU per update | 110.2 ms | 56.4 ms |
| Two weeks: renderer main-thread CPU per update | 1621.4 ms | 120.8 ms |

CPU values use Chromium CDP `ThreadTime` with the `threadTicks` time domain,
measured across the live-update phase and divided by its update count. They
include main-thread rendering/layout work during the short waits between updates.
They do not measure all browser processes, GPU or compositor threads. Earlier
tables report elapsed update time, not separately measured CPU time. Per-method
elapsed timings can be nested and must not be added together as CPU totals.

The full retained-source walk and full prepared-row equality scan are removed
from ordinary live publication. Copying the published array remains necessary
for the current immutable snapshot interface. The main line path is built once
for final geometry; its construction remains visible processing work.

Eight additional regressions cover bounded preparation lookups with two weeks of
rows, immutable snapshots, delayed/corrected/invalid measurements, equivalent
source refreshes, expired rows and the retained seed, categorical map changes,
offset changes, and repeated/equal winter-time projections. Luna Max completed
the test follow-up: all 40 History tests and all 440 Node tests pass; lint checks
115 files without fixes. No production source fix was needed during that check.

The final History build and benchmark are complete. All nine affected browser
cases also pass against this final build in both Chromium and WebKit. They cover
card change detection, History timer cleanup and actual Cartesian/radial/real-time
pointer behavior. User visual validation has reported no errors so far.
All changes remain on branch #753; no master merge has been performed.

## Scope

No update throttling, sample reduction, tooltip changes, empty-bin behavior
changes, timestamp-policy changes, new configuration defaults or version bump.
