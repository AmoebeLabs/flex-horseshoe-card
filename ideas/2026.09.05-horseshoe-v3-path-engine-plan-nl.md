# Horseshoe V3 — generieke Path Engine en renderarchitectuur

## Doel van dit document

Dit document beschrijft de voorgestelde architectuur voor een tijdelijke `horseshoes_v3`-implementatie in Flexible Horseshoe Card (FHS).

Het doel is **niet** om Swiss Army Knife (SAK) `ProgressPathTool` één-op-één over te nemen. Het doel is om de bewezen ideeën uit `ProgressPathTool` te combineren met de veel rijkere functionaliteit van de huidige FHS horseshoe.

De centrale gedachte is simpel:

> **Geometrie bepaalt één universeel SVG-pad. Configuratie bepaalt welke ranges van dat pad zichtbaar zijn en hoe ze worden geschilderd. Renderers mogen zo weinig mogelijk kennis hebben van het type geometrie.**

`horseshoes_v3` is alleen een tijdelijke parallelle ingang om de nieuwe implementatie naast de huidige horseshoe te kunnen ontwikkelen en vergelijken. De onderliggende nieuwe modules krijgen **geen** `V3`-namen.

---

# 1. Belangrijkste conclusie

De huidige FHS horseshoe en SAK `ProgressPathTool` zijn technisch geen totaal verschillende concepten. Beide draaien uiteindelijk om een SVG-pad.

Het grote verschil zit in de rendering:

- SAK `ProgressPathTool` gebruikt hoofdzakelijk een **centerline SVG path + stroke**.
- Delen van dat pad worden zichtbaar gemaakt met `stroke-dasharray`, `stroke-dashoffset` en masks.
- De huidige FHS horseshoe bouwt vaak een **echte gesloten bandgeometrie**: buitenboog + eindkap + binnenboog + beginkap.
- FHS gradients bestaan uit meerdere kleine gesloten bandsegmenten die tijdens animatie opnieuw kunnen worden opgebouwd.

Voor V3 moet de geometrie universeel worden, terwijl meerdere renderstrategieën mogelijk blijven.

De gewenste eindarchitectuur is dus niet:

```text
ProgressPathTool -> HorseshoeTool
```

maar:

```text
                    PathGeometry
                         |
               universeel master path
                         |
           +-------------+-------------+
           |             |             |
      Stroke/Dash     Masked       Gradient/
       Renderer       Renderer      Segment Renderer
           |             |             |
           +-------------+-------------+
                         |
                  Horseshoe features
```

# 2. Wat SAK ProgressPath al bewijst

Bron:

- `swiss-army-knife-card/src/progress-path-tool.js`
- GitHub: <https://github.com/AmoebeLabs/swiss-army-knife-card/blob/master/src/progress-path-tool.js>

De huidige `ProgressPathTool` is ongeveer 1.500 regels en ondersteunt als primaire padtypen:

```text
circle
line
rectangle
spiral
```

Daarnaast staat er al een `user`-pad ingang in de code, maar `_computeUserPath()` is leeg. Een willekeurig user-defined SVG-pad was dus blijkbaar ooit voorzien, maar niet geïmplementeerd.

Belangrijke bestaande eigenschappen:

## 2.1 Eerst wordt één pad gemaakt

De verschillende geometrieën leveren uiteindelijk allemaal één SVG `d` op.

Voorbeelden uit de huidige implementatie:

```text
_computeCirclePath()
_computeLinePath()
_computeRectanglePath()
_computeSpiralHelixPath()
```

Daarna gebruikt vrijwel alle verdere functionaliteit diezelfde `d`.

## 2.2 De browser meet het pad

Na rendering gebruikt ProgressPath onder andere:

```js
path.getTotalLength()
path.getPointAtLength(length)
```

Daarmee hoeft de applicatie bijvoorbeeld de exacte lengte van een Bézier-spiraal niet zelf analytisch uit te rekenen.

De browser is dus feitelijk al een deel van de geometry-engine.

Belangrijk: `getTotalLength()` en `getPointAtLength()` werken met de **werkelijke door de browser berekende geometrische lengte**. Het SVG-attribuut `pathLength="100"` verandert die DOM-metingen niet. Dat is juist nuttig: V3 kan twee bewust gescheiden ruimtes gebruiken:

```text
progress/render space = 0..100
geometry/coordinate space = werkelijke SVG-lengte
```

## 2.3 `pathLength="100"` maakt de renderlaag procentueel

ProgressPath gebruikt op het gerenderde master path bewust:

```svg
<path d="..." pathLength="100" />
```

Dit is native SVG-functionaliteit. Voor afstandsafhankelijke stroke-operaties kalibreert de browser het volledige pad dan naar een auteurslengte van `100`.

Daardoor kunnen onder andere:

```text
stroke-dasharray
stroke-dashoffset
```

rechtstreeks in een vaste `0..100` progressruimte worden uitgedrukt:

```text
0   = begin
25  = 25% van het pad
50  = helft
73  = 73%
100 = einde
```

De renderer hoeft daarvoor **niet** te weten of het echte pad 180, 640 of 1.400 SVG-units lang is. De browser schaalt de stroke-afstanden naar de werkelijke geometrie.

Dit moet in V3 geen toevallige implementatiedetail zijn, maar een expliciet contract:

```text
value / ranges / progress / dash rendering -> 0..100
point/tangent/normal queries               -> echte SVG-lengte
```

Alleen wanneer echte coördinaten nodig zijn wordt omgerekend:

```js
const actualLength = path.getTotalLength();
const distance = (progress / 100) * actualLength;
const point = path.getPointAtLength(distance);
```

Dit maakt de render- en rangeberekeningen aanzienlijk eenvoudiger.

## 2.4 Markers zijn al pad-onafhankelijk

ProgressPath bepaalt een punt op het pad met `getPointAtLength()` en gebruikt een tweede nabijgelegen punt om met `atan2()` de lokale richting te bepalen.

Conceptueel is dat al:

```text
pointAt(length)
tangentAt(length)
```

De marker hoeft daardoor niet te weten of hij op een circle, line, rectangle of spiral staat.

## 2.5 Colorstop-segmenten gebruiken steeds hetzelfde volledige pad

De gekleurde segmenten worden niet als aparte geometrieën opgebouwd.

Per segment wordt opnieuw hetzelfde volledige `d`-pad gebruikt en alleen een range zichtbaar gemaakt met:

```text
stroke-dasharray
stroke-dashoffset
```

Daarmee zijn segmenten en gaps in beginsel volledig path-onafhankelijk.

## 2.6 Masks lossen beperkingen van linecaps op

Een gewone `stroke-linecap: round` maakt automatisch **beide** uiteinden rond. Dat is niet altijd gewenst.

ProgressPath gebruikt daarom masks/markers met halve cirkels om bijvoorbeeld alleen het echte begin of einde van de complete progressvorm rond te maken.

De broncode bevat hier expliciet commentaar over: halve cirkels zijn nodig omdat een gewone round linecap beide zijden beïnvloedt.

## 2.7 Het pad wordt door meerdere lagen hergebruikt

ProgressPath gebruikt dezelfde geometrie voor onder andere:

```text
background
track
active track
colorstop parts
masks
motion/measurement path
marker calculations
```

Dat gebeurt niet overal met SVG `<use>`; meestal wordt dezelfde `d` opnieuw op meerdere `<path>`-elementen gezet. Conceptueel is het wel één mastergeometrie met meerdere renderlagen.

# 3. Wat we NIET blind uit ProgressPath moeten overnemen

ProgressPath is een waardevolle bewezen basis, maar de huidige code moet niet als nieuw architectuurcontract worden gekopieerd.

Er zitten nog historische beperkingen, TODO's en hacks in.

Voorbeelden:

- `user` path bestaat als configuratie-ingang, maar `_computeUserPath()` is leeg.
- Scale is in de huidige code alleen geconfigureerd voor circle en line; rectangle scale is expliciet uitgeschakeld.
- `getPerpendicularAngleAtLength()` bevat opmerkingen over problemen met CW/CCW en flip bij circles.
- Er wordt zowel met `pathLength="100"` als met de werkelijke `getTotalLength()` gewerkt. Dat is op zichzelf juist en moet in V3 **bewust worden behouden**, maar met een expliciet contract: `0..100` voor progress/stroke-rendering en de werkelijke lengte voor DOM-geometriequeries zoals `getPointAtLength()`.
- Er zijn historische comments en workarounds rond masks en linecaps.

Conclusie:

> **Gebruik ProgressPath als bewezen referentie voor path generation, dash ranges, masks en SVG-geometrie. Maak voor FHS een schoon expliciet contract.**

# 4. Wat de huidige FHS horseshoe anders en beter kan

Bronnen:

- `src/horseshoe-geometry.js`
- `src/horseshoe-shapes.js`
- `src/horseshoe-renderer.js`
- `src/horseshoe-animator.js`

GitHub:

- <https://github.com/AmoebeLabs/flex-horseshoe-card/blob/master/src/horseshoe-geometry.js>
- <https://github.com/AmoebeLabs/flex-horseshoe-card/blob/master/src/horseshoe-shapes.js>
- <https://github.com/AmoebeLabs/flex-horseshoe-card/blob/master/src/horseshoe-renderer.js>
- <https://github.com/AmoebeLabs/flex-horseshoe-card/blob/master/src/horseshoe-animator.js>

## 4.1 De huidige geometrie is arc-specifiek

`GaugeGeometry` rekent nu grofweg:

```text
value -> ratio -> angle -> x/y op circle/arc
```

Daarvoor bestaan methoden zoals:

```text
ratioToAngle()
scaleValueToRatio()
valueToRatio()
valueToAngle()
pointAt(angle, radius)
```

Dit is logisch voor een horseshoe, maar niet universeel voor line, wave, rectangle, spiral enzovoort.

## 4.2 De huidige renderer bouwt echte bands

`ArcPathBuilder.buildBandPath()` maakt een gesloten vorm met een binnen- en buitenrand en afzonderlijke caps.

Dat geeft veel controle over:

```text
breedte
start cap
end cap
gaps
segmentvormen
fill
stroke
```

Dit is rijker dan een naïeve stroked line.

## 4.3 De huidige gradientrenderer bouwt micro-arcs

FHS kan een conisch-ogende gradient langs de horseshoe nabootsen door de boog in kleine stukken te verdelen.

Ieder stuk krijgt zijn eigen lokale lineaire gradient.

Dit principe blijft bruikbaar voor een generiek pad, maar de segmentatie moet dan op **afstand langs het pad** gebeuren in plaats van op hoek.

## 4.4 De huidige animatie animeert de waarde en bouwt geometrie opnieuw

`horseshoe-animator.js` interpoleert met `requestAnimationFrame()` een `displayValue`.

Tijdens de animatie worden de mutable path-data opnieuw berekend en zet de renderer opnieuw het `d`-attribuut op het SVG-element.

Bij V3 kan voor veel modes waarschijnlijk een eenvoudigere dash/mask-animatie worden gebruikt, maar niet iedere mode wordt automatisch statisch. Bijvoorbeeld een gradient van `0 -> current` moet bij iedere gewijzigde current-value nog steeds opnieuw worden verdeeld.

## 4.5 FHS ondersteunt semantiek die ProgressPath niet zomaar vervangt

Onder andere:

```text
bar modes
linear/spline scale mapping
stringstate_mode
stringstate_level
hard colorstop segments
smooth gradients
full/current gradient behavior
gaps
mixed caps
inactive state opacity
```

Daarom moet de bestaande Horseshoe-functionaliteit de functionele referentie blijven.

# 5. Kernarchitectuur voor V3

De nieuwe architectuur moet uit duidelijke lagen bestaan.

```text
HorseshoeV3 adapter/orchestrator
        |
        +--> Value / Scale mapping
        |
        +--> Path Definition
                |
                v
          Path Geometry Engine
                |
                v
             Ranges
                |
                v
          Feature Layout
                |
                v
            Renderers
```

De belangrijkste regel:

> **Iedere laag krijgt een vast contract. Geen renderer mag zelf opnieuw geometrie gaan uitvinden.**

---

# 6. Laag 1 — Horseshoe V3 config adapter

Alleen de tijdelijke gebruikersingang heet V3, bijvoorbeeld:

```yaml
horseshoes_v3:
```

De nieuwe generieke modules krijgen geen `V3` in hun naam.

Tijdens ontwikkeling:

```text
horseshoes     -> huidige horseshoe implementatie
horseshoes_v3  -> nieuwe implementatie
```

Doel:

- dezelfde bestaande horseshoeconfig zo veel mogelijk kunnen voeren aan oud en nieuw;
- output naast elkaar kunnen vergelijken;
- functionaliteit stap voor stap aansluiten;
- eindgebruiker hoeft uiteindelijk niets van V3 te weten.

Na volledige parity:

```text
oude horseshoe implementatie verwijderen
normale horseshoes dispatch naar nieuwe implementatie laten wijzen
horseshoes_v3 tijdelijke ingang verwijderen
```

Dit is dezelfde migratiestrategie die eerder met `_v2` is gebruikt.

---

# 7. Laag 2 — Value / Scale mapping

Value mapping en geometrie moeten los van elkaar blijven.

De huidige `GaugeScale` bevat al veel bruikbare logica voor:

```text
min/max
linear/spline mapping
normal
absolute
bidirectional
bidirectional symmetrical
```

Deze laag moet als uitkomst **progress/ranges in de vaste `0..100`-ruimte** geven, niet angles en niet echte padlengtes.

Bijvoorbeeld:

```js
{
  start: 0,
  end: 63,
}
```

of bij een bidirectional mode:

```js
{
  start: 50,
  end: 72,
}
```

Deze `0..100`-ruimte sluit direct aan op SVG `pathLength="100"`. Voor de meeste rendering hoeft daarna geen omzetting naar pixels/SVG-units meer plaats te vinden.

Een renderer hoeft vervolgens niet te weten wat `37 °C`, `heating` of `absolute` betekent.

# 8. Laag 3 — Path Definition / Path Generators

Iedere vorm heeft een kleine generator die alleen verantwoordelijk is voor:

```text
config -> SVG d path
```

Start direct met meerdere geometrieën. Niet eerst alleen arc bouwen en de rest later toevoegen, omdat dan het risico bestaat dat hogere lagen opnieuw arc-specifieke aannames krijgen.

Minimale set voor de eerste architectuur/testfase:

```text
arc
line
rectangle
spiral
wave
infinity
```

### Arc

De huidige horseshoe is geometrisch eigenlijk een arc.

```text
90°  -> quarter arc
180° -> half arc
270° -> klassieke horseshoe
360° -> volledige circle/ring
```

`circle` kan dus eventueel gebruikersvriendelijke terminologie blijven, maar intern is `ArcPath` logischer.

### Line

Horizontale/verticale eenvoudige progressbar.

### Rectangle

Progress rondom een rechthoek of rounded rectangle.

### Spiral

Bestaande SAK-generator kan als bron/inspiratie dienen.

### Wave

Nuttig voor progress/process-achtige dashboardvormen.

Configuratie kan bijvoorbeeld parametrisch zijn:

```yaml
path:
  type: wave
  waves: 3
  amplitude: 8
```

### Infinity

Nuttig voor cyclische/continue concepten en als goede test voor self-intersection.

### Later optioneel

Alleen toevoegen als een nieuwe vorm vrijwel uitsluitend een nieuwe PathGenerator vereist:

```text
stadium/racetrack
steps
```

`steps` kan interessant zijn voor discrete levels/states zoals low/medium/high.

Niet doen als een nieuwe geometrie overal speciale rendercode vereist.

# 9. Laag 4 — Path Geometry Engine

Dit is het belangrijkste geometriecontract.

Een mogelijke interface:

```js
class PathGeometry {
  getPath();
  getTotalLength();
  pointAtProgress(progress);
  pointAtLength(length);
  tangentAtProgress(progress);
  normalAtProgress(progress);
}
```

Exacte methodenamen kunnen aansluiten op de bestaande FHS-stijl; het contract is belangrijker dan de naam.

## 9.1 Twee expliciete ruimtes, ieder met één doel

V3 moet bewust twee afstandsruimtes gebruiken:

```text
Progress/render space : 0..100
Geometry space        : werkelijke SVG-lengte
```

Dit is **geen ongewenste mix van eenheden**. Het is juist een vereenvoudiging waarbij SVG zelf de vertaalslag voor stroke-rendering doet.

### Progress/render space — `0..100`

Alles wat semantisch een positie of range op de gauge beschrijft werkt bij voorkeur rechtstreeks in:

```text
0   = begin
25  = kwart
50  = helft
100 = einde
```

Daaronder vallen onder andere:

```text
value mapping
progress
segment ranges
string states
colorstops
gaps
stroke-dasharray
stroke-dashoffset
animatieprogress
full/current range semantics
```

Het gerenderde master path krijgt daarom:

```svg
pathLength="100"
```

Voor stroke-operaties behandelt SVG het pad vervolgens alsof de totale lengte `100` is. De browser schaalt dit zelf naar de werkelijke geometrische lengte.

### Geometry space — werkelijke SVG-lengte

Alleen wanneer echte coördinaten/richtingen nodig zijn gebruiken we de door de browser berekende lengte:

```js
const totalLength = pathElement.getTotalLength();
```

Voor een punt op bijvoorbeeld 37%:

```js
const distance = (37 / 100) * totalLength;
const point = pathElement.getPointAtLength(distance);
```

Dit is nodig voor:

```text
point
tangent
normal
ticks
labels
markers
lokale gradientrichting
andere echte geometrische sampling
```

Belangrijk: `getTotalLength()` en `getPointAtLength()` gebruiken de werkelijke browsergeometrie; zij worden niet genormaliseerd door `pathLength="100"`.

## 9.2 Laat SVG beide kanten van het werk doen

Voor arbitraire paths hoeft FHS dus noch de werkelijke padlengte analytisch te berekenen, noch zelf alle dash-afstanden naar pixels om te zetten.

SVG/browser doet beide:

```text
master d
   |
   +--> getTotalLength()/getPointAtLength()
   |      -> echte geometrie/coördinaten
   |
   +--> pathLength="100"
          -> genormaliseerde stroke/render space
```

Daarmee blijft FHS-logica eenvoudig:

```text
"toon tot 63"        -> dash/progress 0..63
"label op 75"        -> 75/100 * actualLength -> pointAtLength()
"state range 40..60" -> dash range 40..60
```

## 9.3 Geen onnodige pixelberekeningen in ranges/rendering

Een renderer moet voor gewone dash-based output **niet** steeds doen:

```text
progress -> actualLength -> dash length in SVG units
```

Als het path `pathLength="100"` heeft, is dit voldoende:

```text
range start = 20
range end   = 47
```

De browser voert de fysieke schaalconversie uit.

Alleen geometry/layout-code die werkelijk een coordinate nodig heeft vertaalt `0..100` naar `0..getTotalLength()`.

Dit onderscheid moet centraal worden vastgelegd en getest, zodat hogere lagen nooit gaan gokken welke lengteeenheid ze ontvangen.

# 10. Laag 5 — Path Ranges

Het tweede belangrijke contract is een generieke range.

Bijvoorbeeld:

```js
{
  start: 20,
  end: 40,
  color: '#ff9800
  active: true,
  startCap: 'butt',
  endCap: 'round',
}
```

De configuratie bepaalt welke ranges bestaan.

Voorbeelden:

## Continuous progress

```text
0 -> current
```

## Hard colorstop segments

```text
0 -> 20 green
20 -> 40 yellow
40 -> 70 orange
70 -> 100 red
```

## String states

```text
off      -> 0 .. 20
idle     -> 20 .. 40
heating  -> 40 .. 60
cooling  -> 60 .. 80
error    -> 80 .. 100
```

`stringstate_mode` kan alleen de gekozen range actief maken.

`stringstate_level` kan cumulatief meerdere ranges actief maken.

## Steps path

Een toekomstige `steps`-geometrie kan horizontale treden en connectoren als ranges beschrijven. Connector-ranges kunnen bijvoorbeeld permanent neutraal of niet-actief blijven.

# 11. Laag 6 — Feature Layout

Ticks, labels en markers moeten niet weten welk padtype wordt gebruikt.

Zij vragen alleen geometrische informatie op.

## Tick

```text
point = pointAtProgress(progress)
normal = normalAtProgress(progress)
```

Daaruit:

```text
inside  = point - normal * offset
outside = point + normal * offset
```

## Label

De labelcode hoeft alleen te weten:

```text
inside
center
outside
offset
```

Niet:

```text
circle
wave
rectangle
spiral
```

## Marker

```text
position = pointAtProgress(current)
rotation = tangent angle
```

Dit is conceptueel al bewezen door ProgressPath.

## Hoeken

Rectangle/steps hebben scherpe hoeken waar de tangent niet uniek is.

De Geometry Engine moet daar één vaste regel voor definiëren, bijvoorbeeld:

```text
incoming tangent
outgoing tangent
of een gemiddelde
```

Die keuze hoort in de engine, niet in iedere renderer/layoutklasse.

# 12. Laag 7 — Renderers

Eén universele geometrie betekent **niet** dat er maar één renderingtechniek hoeft te bestaan.

De renderstrategie wordt gekozen op basis van de gewenste visuele functie, niet noodzakelijk op basis van path type.

Mogelijke renderers:

```text
StrokeRenderer
DashRangeRenderer
MaskedStrokeRenderer
GradientSegmentRenderer
BandRenderer (alleen behouden indien echt nodig)
```

# 13. Stroke/Dash renderer — vermoedelijke nieuwe basis

Dit is de belangrijkste techniek uit ProgressPath.

Voor ieder zichtbaar segment wordt hetzelfde volledige master path gebruikt.

Bijvoorbeeld:

```text
master path
0----------------------------------------100%

segment A
████████

segment B
          █████████

segment C
                     ███████████
```

Technisch:

```text
same d path
+ stroke-dasharray
+ stroke-dashoffset
```

Omdat het master path `pathLength="100"` krijgt, kan een generieke range `[start,end]` rechtstreeks in progress-units worden gerenderd:

```text
start       = 20
end         = 47
rangeLength = 27
```

Die waarden kunnen direct de basis vormen voor `stroke-dasharray` en `stroke-dashoffset`. De renderer hoeft de werkelijke `getTotalLength()` hiervoor niet te kennen.

Alleen wanneer dezelfde range echte punten/coördinaten nodig heeft, wordt `start`/`end` via `/ 100 * getTotalLength()` naar geometry space vertaald.

Daarna worden gap/caps toegepast, eveneens bij voorkeur in de afgesproken `0..100` render space tenzij een feature expliciet een fysieke SVG-unit nodig heeft.

Belangrijk:

> De zichtbare segmenten zijn alleen rendering. De volledige geometrie blijft altijd het master path.

---

# 14. Gaps

Gaps horen bij ranges/rendering, niet bij geometrie.

Voor iedere range kan de zichtbare lengte worden verkort en de start/eindoffset worden aangepast.

De exacte gap-semantiek moet één keer worden vastgelegd en getest:

```text
gap volledig tussen segmenten
half gap aan beide zijden
speciale behandeling van eerste/laatste segment
```

Niet in iedere renderer apart opnieuw interpreteren.

---

# 15. Caps en masks

Gewone SVG linecaps zijn onvoldoende wanneer begin en einde verschillend moeten zijn.

Voorbeeld:

```text
start = round
end   = butt
```

Een `stroke-linecap: round` maakt beide zijden rond.

ProgressPath bewijst dat masks met halve cirkels dit kunnen oplossen.

Voor V3 moet dit als zelfstandige, geteste functionaliteit worden ontworpen:

```text
butt / butt
round / round
round / butt
butt / round
```

Daarmee kunnen zowel volledige progressbars als afzonderlijke segmenten correct worden opgebouwd.

---

# 16. Fill + stroke/border op een willekeurig pad

Een belangrijk doel is behoud van het visuele onderscheid tussen:

```text
fill
stroke/border
```

op ieder willekeurig pad.

## 16.1 Opaque fill — eenvoudig

Hetzelfde master path tweemaal tekenen:

```text
onderste path -> bredere stroke = border
bovenste path -> smallere stroke = fill
```

Dit simuleert een brede band met rand.

## 16.2 Transparante fill — simpele dubbele stroke is fout

Als de binnenste fill bijvoorbeeld `opacity: 0.3` krijgt, schijnt de bredere border eronder door.

Dat is niet hetzelfde als een echte transparante fill over de kaartachtergrond.

## 16.3 Transparante fill — masked border

De oplossing is:

1. teken een brede border-stroke;
2. gebruik een mask dat het middelste deel uit de border verwijdert;
3. teken de fill als aparte smallere stroke;
4. de transparante fill ziet daardoor de echte achtergrond, niet de border eronder.

Conceptueel:

```text
brede stroke
██████████████

midden wegmaskeren
██          ██

aparte fill
   ████████
```

Dit moet als proof-of-concept bewezen worden op meerdere vormen.

# 17. Gradients langs een willekeurig pad

SVG ondersteunt geen echte conische/path-following gradient voor een willekeurig path.

De bestaande FHS-techniek blijft daarom waardevol:

```text
pad opdelen in veel kleine ranges
per range lokale lineaire gradient
```

Het verschil met de huidige horseshoe:

```text
V2: segmenteren op arc angle
V3: segmenteren op distance/ratio langs het master path
```

Bijvoorbeeld:

```text
0.0 -> 0.5
0.5 -> 1.0
1.0 -> 1.5
...
```

Per microsegment:

```text
start point
end point
start color
end color
```

De lokale gradientrichting kan uit de segmentpunten/tangent worden bepaald.

# 18. Gradient `full` versus `current`

De nieuwe rendertechniek verandert deze semantiek niet.

## Full

Kleuren worden over de volledige schaal verdeeld.

De geometrie/kleuren kunnen grotendeels statisch blijven; progress bepaalt welk deel zichtbaar is.

## Current

Kleuren worden opnieuw verdeeld van het begin tot de huidige waarde.

Bij iedere statewijziging moet nog steeds:

```text
current ratio opnieuw bepalen
color distribution opnieuw berekenen
microsegmenten/ranges opnieuw bepalen
lokale gradients opnieuw instellen
```

Dash rendering maakt dit niet magisch statisch. Alleen de manier waarop de ranges worden getekend verandert.

# 19. Opacity en overlap van gradientsegmenten

Microsegmenten kunnen een kleine overlap nodig hebben om anti-aliasing-naadjes te voorkomen.

Zet dan niet op ieder segment afzonderlijk bijvoorbeeld `opacity: 0.5`.

Anders worden overlappende delen donkerder.

Beter:

```svg
<g opacity="0.5">
  <!-- alle interne segmenten zelf opacity 1 -->
</g>
```

De groep wordt eerst intern samengesteld en daarna als geheel transparant gemaakt.

Dit moet expliciet getest worden.

Bij een self-intersecting pad zoals `infinity` moet ook worden bekeken wat er gebeurt op het kruispunt, omdat daar meerdere path-ranges fysiek over elkaar kunnen lopen.

# 20. Animatie

De huidige horseshoe animeert de `displayValue` en bouwt vervolgens mutable geometrie opnieuw.

V3 kan voor veel modes eenvoudiger werken:

```text
0 -> current visible range
```

De range kan via dash/mask groeien terwijl het master path gelijk blijft.

Dat kan waarschijnlijk veel geometry churn tijdens animatie voorkomen.

Maar niet iedere mode kan alleen met één dashoffset worden afgehandeld.

Voorbeelden:

- `solid progress`: eenvoudig range/dash animeren;
- hard colorstop segments: vaste segmenten, progress/mask onthult ze;
- `gradient full`: vaste gradientsegments, progress/mask onthult ze;
- `gradient current`: kleurenverdeling zelf verandert tijdens animatie en moet dus blijven worden herberekend.

De animator moet daarom de **semantische progresswaarde** blijven animeren. De renderer kiest daarna de goedkoopste manier om die mode te visualiseren.

# 21. String states

Voorbeeld:

```text

state idle     -> range 1
state heating  -> range 2
state cooling  -> range 3
```

# 37. Conceptueel eindmodel

Uiteindelijk moet de horseshoe intern ongeveer zo werken:

```text
Home Assistant state / config
            |

      Value / Scale
            |
       normalized ranges
            |
            v
       Path Definition
            |
            v
       Path Geometry
            |
   master SVG d + length

            |
            v
       Feature Layout
            |
            v
         Renderers
     /       |       \
 stroke    masks    gradient segments
     \       |       /
            v
           SVG
```

De huidige horseshoe wordt daarmee conceptueel:

```text
Horseshoe = ArcPath + bestaande Horseshoe feature/config semantics
```

Een wave wordt:

```text
Horseshoe = WavePath + exact dezelfde feature/config semantics
```

Een rectangle wordt:

```text
Horseshoe = RectanglePath + exact dezelfde feature/config semantics
```

De naam `horseshoe` blijft voor backwards compatibility en productidentiteit bestaan; intern wordt het veel meer een algemene path-based gauge engine.

# 38. Waarom dit de moeite waard is

De refactor is groot, maar beheersbaar omdat veel onderdelen al bewezen bestaan:

- SAK bewijst multi-shape SVG path generation;
- SAK bewijst `getTotalLength()` / `getPointAtLength()`;

- FHS bewijst string-state rendering;
- FHS bewijst adaptive gradient microsegments;
- FHS bewijst de huidige animatiesemantiek;
- de sparkline-ervaring bewijst dat een goed geteste engine de renderlagen veel voorspelbaarder maakt.

De echte nieuwe opgave is dus vooral:

> **de bestaande bewezen technieken achter één strak contract zetten en daarna de bestaande Horseshoe-config gecontroleerd aansluiten.**

Als dit lukt, wordt een nieuwe vorm geen nieuwe tool meer maar hoofdzakelijk een nieuwe geometriegenerator.

Dat is het belangrijkste succescriterium van Horseshoe V3.

# 40. Korte opdrachtformulering voor Codex

> Bouw Horseshoe V3 niet als een nieuwe losse progress tool. Gebruik SAK `ProgressPathTool` als referentie voor generieke SVG-path generation, path measurement, dash ranges en masks, en gebruik de huidige FHS horseshoe als functionele referentie voor alle gauge-features.
