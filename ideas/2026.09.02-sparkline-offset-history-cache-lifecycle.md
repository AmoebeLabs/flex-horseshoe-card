# Sparkline Offset History Cache Lifecycle

## Status

Ideas plan. No implementation changes are part of this document.

## User Problem

A sparkline with a negative period offset represents a completed historical
period. Examples are yesterday or the same rolling window one day earlier.
After that history has been loaded, ordinary card updates should not fetch the
same data again.

Repeated requests are unnecessary and can briefly show the loading spinner.
They are especially visible when returning to a browser tab or while Home
Assistant continues to update the card.

The historical graph must still move to the next source day after local
midnight. Configuration or entity changes must also load the newly requested
history.

## Expected Behavior

For a period with `offset < 0`:

- Fetch the requested history when the sparkline is initialized.
- Reuse that history during the rest of the same local day.
- Do not refetch it because an optional periodic refresh interval expires.
- Do not refetch it after an ordinary realtime entity update.
- Fetch again when the local day changes and the offset therefore refers to a
  different concrete source day.
- Fetch again when the entity or period configuration changes.

An active period with `offset: 0` keeps its existing lifecycle. This plan does
not change realtime updates, reconnect recovery, active history pruning, or bin
updates.

## Cache Identity

Cached offset history represents this combination:

```text
entity + period configuration + concrete source day
```

The numerical start and end timestamps of an offset rolling window move as the
current time advances. That movement alone must not invalidate the cache. The
source day is the relevant boundary: the cache remains valid during that day
and expires after the next local midnight.

## Current Behavior

The sparkline tool already separates active and closed source ranges:

- `offset: 0` is active.
- `offset < 0` is closed.

It also already avoids adding current entity states to closed history and does
not request offset history merely because Home Assistant reconnects.

Two remaining details make the cache contract incomplete:

1. A closed rolling-window range is currently accepted indefinitely. It does
   not become stale when its concrete source day changes.
2. A configured periodic refresh can still bypass a valid closed-range cache
   and request the same offset history again.

The history conversion, series coordination, graph engine, statistics, and
rendering layers do not cause this behavior.

## Architecture Boundary

The change belongs entirely to the Home Assistant history lifecycle in
`SparklineGraphTool`.

```text
SparklineGraphTool
  - decides whether cached history represents the requested source period
  - decides whether Home Assistant history must be fetched

SparklineSeries
  - unchanged

SparklineGraph
  - unchanged

rendering and tooltip layers
  - unchanged
```

No new cache service, coordinator, fallback, or renderer-specific exception is
needed.

## Implementation Plan

### 1. Expire offset rolling history at the source-day boundary

Update `acceptedHistoryContainsRange()` so a closed rolling-window cache is
accepted only while its stored range end and the requested range end belong to
the same local calendar day.

This preserves the intended behavior within a day even though the requested
rolling timestamps continue to move. After local midnight, the newly computed
range belongs to another source day and is no longer represented by the cached
history.

Calendar offsets keep their existing exact range coverage check.

### 2. Ignore periodic refresh for represented closed history

Update `fetchHistoryIfNeeded()` so a represented closed range returns before a
periodic refresh deadline can trigger another request.

An explicit resynchronization caused by an entity or period configuration
change must remain able to fetch new history. Active ranges retain the existing
periodic refresh and resynchronization behavior.

These are the only production routines that need to change.

## Tests

Add focused lifecycle coverage without changing graph rendering tests.

### Offset rolling cache within one day

- Store a fetched range for `rolling_window.offset: -1`.
- Advance the current time within the same local day.
- Verify that the stored history still represents the request.
- Verify that no additional Home Assistant history request is made.

### Offset rolling cache after local midnight

- Store a fetched range before local midnight.
- Advance the current time into the next local day.
- Verify that the stored history no longer represents the request.
- Verify that one new history request is made.

### Periodic refresh on a closed range

- Store history that represents a closed offset range.
- Make `history.refresh_interval` due.
- Verify that no new request is made.

### Configuration change

- Store history for a closed offset range.
- Change the entity or period configuration.
- Verify that the deliberate resynchronization still requests the newly
  configured history.

### Existing behavior

- Keep the active `offset: 0` history tests unchanged.
- Keep completed calendar offset tests unchanged.
- Run the complete test suite and production build.

## Acceptance Criteria

- A loaded negative-offset sparkline does not show a spinner during ordinary
  updates on the same local day.
- A configured refresh interval does not repeatedly fetch represented closed
  history.
- The graph refreshes after local midnight when the offset points to a new
  source day.
- Entity and period changes still fetch the requested data.
- Active sparkline periods behave exactly as before.
- No changes are made to `SparklineSeries`, `SparklineGraph`, statistics,
  geometry, or rendering.

## Impact

The production impact is narrow: two decisions in the sparkline tool's history
lifecycle plus focused tests. The data and render pipelines keep the same input
and output contracts.
