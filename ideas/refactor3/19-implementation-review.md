## 2. Confirmed Plan-19 Results

### 2.1 Horseshoe configuration ownership is materially cleaner

The old competing Horseshoe owners are gone.

The current `src/horseshoe-gauge.js` no longer contains:

```text
activeItemConfig
runtimeConfig
pathConfig
renderContract
stateData.config
this.config.colorstops
this.pathDefinition
this.pathGeometry
this.valueMapper
this.scale
this.value
stateMarkerStyles
```

The current owner model is now recognizable:

```text
this.config
geometry.*
runtime.*
paint.*
```

The former pattern where entity-state processing replaced or mutated the active Horseshoe configuration has been removed.

`getGaugeStateData()` now returns semantic state output rather than a state-specific replacement config.

### 2.2 Dynamic first configuration does not introduce another lifecycle framework

The implementation uses the existing:

```text
hasJavascript
activeConfigInitialized
```

boundary.

A dynamic Horseshoe remains inert before first complete evaluation:

- path generation does not run at construction;
- `render()` returns empty when no path definition exists;
- `updated()` exits before evaluated config exists;
- palette refresh exits before current runtime mapping exists;
- no additional ready/pending/candidate/publication state machine was added.

This matches the approved Plan-19 constraint.

### 2.3 Path and geometry ownership is explicit

Path input, generated path definition, transformed geometry and path-element geometry now live under `geometry`.

`CardLayout` no longer precomputes Horseshoe SVG/path dimensions through a separate Horseshoe-specific route.

Labels and markers no longer consume the former `runtimeConfig` / `pathConfig` conventions.

### 2.4 State mapping no longer owns active palette colors

`getGaugeStateData()` now separates semantic mapping from active render colors.

Examples:

- string color stops build state/value/rank mapping without storing active palette color in the semantic state map;
- `rank_state` maps source thresholds into ranked semantic values;
- palette-derived colors are rebuilt separately by `buildGaugeColorStops()`.

This is a real improvement over the previous state-specific config replacement.

### 2.5 Icon post-review correction is correct

The Luna Max review found one Plan-19 regression before merge:

> Icon state-map rendering constructed a distinct render item, causing BaseTool to skip the icon's own palette and use entity paint.

The merged correction explicitly passes the Icon palette:

```js
this.applyColorStops(
  configStyle,
  renderItem,
  ["fill", "color"],
  this.paint?.colorStops,
);
```

This preserves the intended priority:

```text
icon/item palette
→ entity palette fallback
```

while retaining state-map styling.

The Plan-19 record reports the focused Icon/BaseTool/CardEntities regressions passing after this correction.

## 3. REWORK 1 — Whole-Value JavaScript Series Can Retain the Wrong Entity Palette

### 3.1 Summary

Plan 19 moved normalized entity color-stop output out of resolved entity configuration and into:

```js
CardEntities.paint.colorStops[]
```

That migration missed one existing late-binding route.

For a Sparkline whose complete `series` array is generated by JavaScript, the actual source `entity_index` of a named series is only known after GraphTool evaluates and publishes the canonical series.

`CardEntities.updateSparklineEntities()` correctly updates the derived entity configuration to the real source entity.

It does not update the parallel `CardEntities.paint.colorStops[]` entry.

As a result, a derived `fhs_sparkline.*` entity can have:

```text
correct source_entity_index
correct copied source config
wrong active entity color-stop palette
```

### 3.2 Why this is a Plan-19 regression

Before Plan 19, entity color-stop paint travelled inside the resolved entity configuration itself.

The old route normalized:

```js
resolvedEntityConfig.colorstops = ColorStops.normalize(...);
```

When a whole-value JavaScript series was later rebound to another source entity, the source config was copied as part of the rebinding.

Therefore the palette travelled with that source config.

Plan 19 intentionally removed active color-stop output from config and created the parallel owner:

```js
this.paint = { colorStops: [] };
```

`buildRuntimeEntityConfigs()` currently fills it before GraphTool has evaluated a whole-value JavaScript series:

```js
this.paint.colorStops = resolvedEntityConfigs.map((entityConfig, entityIndex) => {
  if (evaluatedEntityConfigs[entityIndex].color_stops !== undefined) {
    return sourceColorStops[entityIndex];
  }
  if (entityConfig.source_entity_index !== undefined) {
    return sourceColorStops[entityConfig.source_entity_index];
  }
  return undefined;
});
```

For whole-value JavaScript series, the preliminary binding may use:

```js
sparklineConfig.entity_index ?? 0
```

because the real named-series source is not yet known.

Later, `updateSparklineEntities()` correctly discovers the published series entry and updates the derived entity config:

```js
const { attribute: _attribute, name: _name, ...sourceEntityConfig } =
  resolvedEntityConfigs[seriesConfig.entity_index];

entityConfig = {
  ...sourceEntityConfig,
  ...entityConfig,
  source_entity_index: seriesConfig.entity_index,
};

resolvedEntityConfigs[entityIndex] = entityConfig;
```

But there is no matching update of:

```js
this.paint.colorStops[entityIndex]
```

The active paint owner can therefore remain bound to the provisional source.

### 3.3 Concrete failure case

Assume:

```text
entity 0
  color_stops → blue palette

entity 1
  color_stops → orange palette
```

and whole-value JavaScript produces:

```js
[
  {
    id: 'comparison',
    entity_index: 1,
  },
]
```

with a derived entity such as:

```text
fhs_sparkline.graph_comparison_avg
```

Before canonical series evaluation, CardEntities may provisionally associate that derived entity with the parent Sparkline entity index.

After GraphTool publication:

```text
source_entity_index → 1
resolved entity config → entity 1
```

but:

```text
CardEntities.paint.colorStops[derivedIndex]
```

can still contain entity 0's palette.

`BaseTool.applyColorStops()` now reads the new paint owner:

```js
const colorStops =
  configuredColorStops
  ?? this.card.cardEntities.paint.colorStops[item.entity_index];
```

so the stale palette can become visible in an ordinary tool using that derived entity.

### 3.4 Required correction

When whole-value JavaScript series binding changes or establishes the final source entity for a derived Sparkline entity, the entity palette owner must follow the same source binding.

The correction should preserve the intended priority:

```text
explicit color_stops on the derived entity itself
→ otherwise source entity palette
```

Do not reevaluate the whole-value JavaScript expression in CardEntities.

Do not restore active `colorstops` into resolved entity config merely to fix this.

Do not introduce another palette cache or source-config owner.

The existing late source binding simply needs to update its parallel Plan-19 paint owner consistently.

### 3.5 Permanent regression test

The existing test:

```text
CardEntities publishes primary and named statistics from whole-value JavaScript series without evaluating the source again
```

already covers the relevant route and should be extended.

Give the source entities visibly different palettes, for example:

```text
entity 0 → blue color_stops
entity 1 → orange color_stops
```

After:

```js
cardTools.updateSparklineRuntimeConfig();
cardTools.setSparklineEntityStates(...);
cardEntities.updateSparklineEntities(...);
```

verify both config and paint binding.

Required assertions should cover at least:

```text
derived comparison source_entity_index == 1
derived parent source_entity_index     == 0

derived comparison palette == entity 1 palette
derived parent palette     == entity 0 palette
```

Also include the priority case where the derived entity itself declares `color_stops`; that explicit palette must remain its own palette rather than being overwritten by the source entity palette.

## 4. Sparkline Palette Ownership Review

Plan 19 adds most of its new source lines around Sparkline palette handling.

The main additions are:

```text
1. retain explicit legacy per-series colorstops authorship
2. compose active per-series palettes
3. identify palette changes that affect numeric graph calculation
4. avoid graph geometry invalidation for color-only theme changes
```

### 4.1 Legacy series override provenance

`SparklineSeries` now retains only the explicitly authored old-form:

```js
series[].sparkline.colorstops
```

override:

```js
item.paint.colorStopsOverride
```

This replaces the temporary Plan-18 bridge that parsed:

```js
activeConfigSignature
```

as a data source.

That is architecturally better than the Plan-18 bridge:

- no raw series-config cache;
- no second complete config owner;
- no signature parsing to recover authored data;
- no additional JavaScript evaluation;
- stable series item identity remains intact.

### 4.2 Active per-series palette

`updatePalettePaint()` composes the active palette from:

```text
series public color_stops, if present
otherwise parent active palette
+
legacy explicit colorstops override, if present
```

Render consumers now read:

```js
item.paint.colorStops
```

rather than the former active palette stored under config-shaped fields.

This satisfies the approved Plan-19 ownership rule.

### 4.3 Numeric palette invalidation

`SparklineSeries.getPaletteCalculationSignature()` creates a signature from:

```text
scales
stop value
rank
state
```

and deliberately excludes active color-only changes.

GraphTool stores:

```text
runtime.paletteCalculationSignature
runtime.paletteCalculationChanged
```

and uses that signal to mark graph geometry dirty only when palette changes affect numeric/rank calculation.

Within the approved Plan-19 requirements this has a concrete purpose.

However, this should be explicitly revisited by the later simplification/de-abstraction plan.

The implementation currently spends additional code and serialization work to avoid recalculating graph state when only colors change.

The later review should ask:

```text
What calculation is actually avoided?
How expensive is it?
Is the bookkeeping cheaper and clearer than simply recalculating it?
```

This is not a Plan-19 correctness defect.

It is a candidate for later simplification.

## 5. Horseshoe Mapping Invalidation Review

Horseshoe state processing now calculates:

```js
const mappingKey = JSON.stringify([
  entity.state,
  entity.attributes[entityConfig.attribute],
  entityConfig.attribute,
  this.config.state_map,
  this.config.horseshoe_scale,
  this.config.bar_mode,
  this.config.zero_ratio,
  this.config.horseshoe_state.mode,
  this.card._hass.locale,
  this.paint.sourceColorStops.colors.map(({ color, styles, ...mapping }) => mapping),
]);
```

The intended behavior is:

```text
state / thresholds / rank / scale change
→ rebuild semantic mapping, GaugeScale and PathValueMapper

only active colors change
→ retain semantic mapping objects
→ rebuild paint
```

The implementation and tests are internally consistent with this requirement.

The tests explicitly verify:

```text
light → dark → light
```

retains:

```text
runtime.stateMap
runtime.scale
runtime.valueMapper
```

while rank-threshold changes rebuild them.

Again, this is not a Plan-19 implementation error.

But it is a strong later simplification candidate.

The future review should verify whether preserving those identities is measurably valuable enough to justify:

```text
mappingKey serialization
mapping identity bookkeeping
separate palette-only route
```

rather than simply rebuilding the small semantic objects when the relevant state/theme route already runs.

## 6. Active Color-Stop Cutover

The Plan-19 cutover is broadly complete.

### Ordinary tools

Item-level active palettes now use:

```text
tool.paint.colorStops
```

Entity fallback uses:

```text
CardEntities.paint.colorStops[entity_index]
```

### Text

Text parts can retain explicit part-level active palettes under the runtime part's paint data.

State-map and referenced-part behavior is covered by the new tests.

### Icon

The post-review correction preserves Icon's own palette when a state map produces a separate render item.

### Sparkline

Parent active palette is stored separately from canonical config.

Stable series items own their active series palette.

### Horseshoe

Active render stops, min/max render stops and related painted ranges no longer live as active config fields.

No temporary Plan-18 palette bridge remains.

## 10. Final Conclusion

Plan 19 successfully removes the former competing Horseshoe configuration owners and completes the intended active color-stop ownership cutover without introducing another general config/lifecycle framework.

The Horseshoe state/config route is materially cleaner than the baseline.

The main implementation concern is one missed dependency created by moving entity active palettes out of resolved config into a parallel paint owner.

Because whole-value JavaScript Sparkline series are rebound to their real source entity only after canonical series publication, the new parallel palette owner must be rebound at the same time.

Until that is corrected:

```text
BLOCKING: 0
REWORK:   1
ADAPT:    0
```

After that focused correction and regression test, the expected final disposition is:

```text
BLOCKING: 0
REWORK:   0
ADAPT:    0

PLAN 19 CLOSED
```

The broader concerns around presentation signatures, paint/style indirection, generic invalidation bookkeeping and over-abstraction are intentionally not treated as Plan-19 defects here. They belong in the later whole-chain simplification/de-abstraction work after Plan 20 establishes the final consistent baseline.
