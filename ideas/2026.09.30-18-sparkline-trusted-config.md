# 2026.09.30 - 18 - Sparkline configuration simplification

## 1. Goal and boundaries

Make Sparkline configuration processing easier to follow and remove only
proven repeated public-configuration checks and conversions. Preserve the
existing YAML, JavaScript-template, chart, history, pointer, rendering, startup,
and failure behavior. This is a configuration refactor, not a new acceptance or
recovery feature.

The [master simplification plan](refactor2/00-master-simplification-plan.md),
[testing policy](refactor2/TESTING.md), and
[Plan 16 guardrails](refactor2/16-plan-simplification-guardrails.md) apply.
Plan 17 did not establish a new universal JavaScript-validation contract.

The earlier draft of Plan 18 proposed atomic parent/series acceptance and
retaining the previous valid configuration after an invalid result. **Do not
implement that proposal.** `BaseTool` currently publishes evaluated
`this.config` before Sparkline-specific runtime work, and this plan must not
change that lifecycle or introduce a last-valid-config state.

## 2. Current route and ownership

- `SparklineGraphTool` completes defaults and legacy/style forms in its
  constructor. Static day/night and radial checks run there when their inputs
  are concrete. JavaScript-backed values are evaluated through the existing
  `BaseTool.updateRuntimeConfig()` route and checked at runtime.
- The tool's runtime method currently mixes configuration checks with duration
  availability, graph preservation during history loading, locale-dependent
  measurement, Series/History coordination, and geometry updates. These are
  different responsibilities; only proven configuration duplication is a
  removal target.
- `SparklineSeries.updateConfig()` merges the parent and each series override,
  applies series-wide paint precedence, checks raw override restrictions and
  the resulting relationships, and retains rows, Graph instances, and
  request/data state by series ID. These are related responsibilities owned
  by Series; the merge and precedence rules are public behavior.
- `SparklineHistory` converts configured durations/offsets while calculating
  ranges and separately validates external HA history rows. `SparklineGraph`
  converts some configured axis/radial values while also converting processed
  state values and CSS-like presentation values.

Recheck these facts against the then-current master before editing. Existing
line numbers in the draft plan are not implementation instructions.

## 3. Configuration contract

`sourceConfig` remains the stable input for re-evaluation. `this.config`
remains the active tool configuration. Do not add a persistent candidate,
runtime-config copy, pending state, or validator framework. There are no new
public YAML keys or defaults.

Use one implementation of each Sparkline-specific completion rule where
possible, invoked at the **existing** constructor or runtime point. This does
not mean forcing all static checks into runtime or forcing JavaScript values
to become concrete in the constructor. Preserve existing error timing and
messages where practical; an invalid user-authored JavaScript result is not
made recoverable by this plan. `undefined` is not globally invalid: ordinary
optional defaults and unavailable HA state retain their current meanings.

`SparklineSeries.updateConfig()` remains the owner of series configuration
**and** runtime series state. Check restrictions on the raw series override
before merging: explicit ID and entity index, offset-only period overrides,
forbidden series-owned radial geometry, and the wrong `y_axis` form. Those
restrictions cannot be recovered from a completed effective config. Then
merge parent and override, apply the existing paint precedence, and check
the effective item and cross-series chart/axis relationships. The implicit
single series follows the same effective-config path while retaining its
existing `default` ID and parent entity binding. Do not split this closely
related work across GraphTool and Series merely to relocate validation.

Do not normalize numeric text merely to remove a downstream `Number(...)`.
History period signatures and other config-change detection can distinguish
`"24"` from `24`, even when a particular calculation treats them equally.
Move a conversion only when both representations already have identical
behavior across config comparison, History signatures, Series updates, and
Graph calculation. Otherwise keep it at its current consumer. Do not
broaden accepted values. A temporarily unavailable dynamic history duration
still uses the existing `periodDurationAvailable` route; it is not a new
configuration error. The calendar-day minimum and its warning retain their
current observable behavior.

## 4. Implementation steps after review

**Do not begin implementation until this document has been reviewed.** Then
create one parent issue and feature branch from the current master. The
following are implementation stages, not a required number of subissues or
PRs. Split them only where the audit finds an independently useful ownership
boundary; any intermediate PR targets the feature branch, not master:

1. **GraphTool configuration boundary.** Characterize constructor versus
   runtime behavior first. Consolidate only duplicated defaults, style
   conversion, legacy boolean visibility conversion, and field checks.
   Separate actual configuration changes from group/theme presentation work
   where this does not alter existing behavior. Keep duration availability,
   history-loading preservation, locale measurement, and geometry coordination
   in their current runtime route. Result: valid static and JavaScript configs
   still produce the same active fields, chart, warning, and startup behavior.
2. **Effective-series configuration.** Keep `SparklineSeries.updateConfig()`
   as the one owner of series construction and validation. Make its existing
   order clear: check raw override restrictions, merge with the parent, apply
   paint precedence, check effective item and collection relationships, then
   reuse runtime items by ID. Avoid adding GraphTool-side series preparation
   or a parallel effective-config collection. Result: implicit, explicit,
   offset-comparison, radial-family, axis, and item-style outcomes are
   unchanged, including current error behavior.
3. **Consumer cleanup and integration.** Remove a History/Graph/Series
   `Number(...)`, fallback, or guard only after proving that removing it
   preserves both numerical results and config/signature change detection.
   A consumer-owned conversion stays where it is. Use a neighboring-owner
   test for any conversion or check that actually moves or disappears.
   Audit the remaining GraphTool conversions in the same way. Result: no
   proven duplicate policing in History/Graph and unchanged graph, range,
   tooltip, and lifecycle results.

Keep the implementation in existing owners. A small Sparkline-specific helper
is justified only if it removes real duplication without adding a second
configuration state or merely relocating a long block. Sol xhigh owns the
cross-class/config integration; Luna Max may handle bounded characterization,
tests, and the conversion inventory. Review Luna's changes in the full chain.

## 5. Checks that stay with their owners

- HA entity/history value conversion and invalid-row handling stay with the
  state/history processing that receives external data.
- Stale request identity, loading/empty/error state, timers, and reconnect
  checks stay with History and the existing lifecycle owners.
- One-point/zero-width/degenerate graph guards stay with the graph algorithm
  when valid input can produce them.
- CSS font-size and SVG dimension conversion stay with presentation geometry;
  DOM pointer `dataset` parsing stays with pointer handling.
- Theme-selected color-stop scales may change active paint or geometry without
  being a new public configuration. Preserve the existing real-time bar and
  equalizer range behavior across theme changes.
- Do not copy the Plan-17 control pattern to Sparkline: `themeModeChanged`
  can legitimately require graph configuration or geometry work when the
  active palette changes a color-stop scale or another geometry input.

Classify each candidate removal as public configuration, external runtime
data, lifecycle validity, algorithmic edge case, or consumer-owned semantic
conversion. If moving it would change existing behavior, leave it in place
and record why rather than adding fallback or recovery code.

## 6. Regression and acceptance

Use existing tests as regression coverage for untouched behavior. Add focused
permanent tests only for configuration work or consumer checks that actually
move, change triggering conditions, or disappear:

- valid static and currently supported JavaScript values, quoted numeric
  configuration values, defaults, legacy visibility booleans, radial/day-night
  settings, axis bounds, and real-time scale requirements;
- implicit versus equivalent explicit single series, unique IDs, entity
  indexes, raw period-offset restrictions, forbidden series-owned radial
  geometry, mixed chart-family rejection, axis IDs, and parent/series paint
  precedence after the final merge;
- unchanged calendar/rolling/DST ranges, offset comparisons, shared axes and
  bins, line/area/minmax/bar/dots/radial/state-bands/real-time output,
  derived entities, loading/empty/error behavior, pointers, and theme reuse;
- retained validation of external HA history rows and consumer conversions
  that are not public-configuration checks; retained change detection when a
  supported JavaScript field changes between numeric text and number.

Avoid a new matrix of hypothetical invalid JavaScript outcomes. Use focused
tests during implementation, build once for the user's visual check, then
run `npm test`, lint, Rollup, and the affected browser projects before asking
for a master merge. The user's visual review is an explicit hold point.

Record before/after product code and physical lines for GraphTool, Series,
History, Graph, and any new helper, plus the runtime method's responsibilities.
The draft's estimate of 150-300 deleted lines is not a target: report the real
result. Do not add substantial infrastructure to achieve a cosmetic decrease.

## 7. Done when

- Public Sparkline configuration and JavaScript behavior are unchanged.
- Effective series inherit and use paint settings exactly as before.
- Series remains the single owner of raw overrides, effective-series config,
  and runtime series identity; GraphTool does not duplicate that work.
- History/Graph no longer repeat **proven** completed public-config checks;
  remaining conversions and guards have an identified owner.
- History/time formulas, Graph math, runtime state, and rendering are unchanged.
- Focused/full checks pass, source-size findings are recorded, and the user
  has visually reviewed the feature branch before any merge to master.

Plan 19 may then use the same trusted-config principle for Horseshoe/Path,
without assuming that Plan 18 introduced a new JavaScript failure contract.

## 8. Implemented result (2026-09-30)

Parent issue: [#829](https://github.com/AmoebeLabs/flex-horseshoe-card/issues/829).
Feature branch: `829-simplify-sparkline-configuration-ownership`. The audit found
one cohesive GraphTool boundary, so no independent subissues were needed.

- GraphTool now uses one implementation each for static/runtime radial checks,
  day/night checks, and legacy boolean x/y visibility conversion. These still
  run at their original constructor/runtime points, with the same errors and
  JavaScript evaluation behavior.
- Series already checks raw overrides before inheritance, then merges the
  parent and series, applies paint precedence, checks effective item styles,
  and retains runtime items by ID. Moving those checks to GraphTool would split
  that ownership, so Series was left unchanged.
- History's period signature distinguishes numeric text from numbers; Graph
  and Series also perform consumer-owned numerical conversions. No conversion
  was removed without proof that both calculation and change detection would
  remain identical. Theme-selected scales can affect geometry, so theme
  invalidation was not narrowed.
- GraphTool's runtime method still owns duration availability, history-loading
  preservation, locale measurement, Series/History coordination, and graph
  updates. No parallel config state, recovery path, or new YAML option was added.

Source-size results use the same Acorn comment classification as Plans 16 and

That contrast observation is separate from this configuration refactor.
