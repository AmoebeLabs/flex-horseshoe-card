## 1. Goal and Functional Boundary

Give Controls the same recognizable configuration, geometry, runtime and paint
ownership as the reference tools while making Control configuration obey the
same JavaScript ordering as Horseshoe, Sparkline and the corrected BaseTool
route.

Controls keep:

```text
config
    authored/evaluated structural configuration
    configured presentation branches

geometry
    derived placement, bounds and native control geometry

runtime
    current HA values, selection and interaction state

paint
    current resolved child presentation where persistence is useful

lifecycle
    DOM references, listeners, timers, RAF handles and measurement scheduling
```

Structural inheritance is completed once per generated child lifetime. Runtime
state may select presentation, but it does not repeat structural inheritance or
mutate a child's canonical config.

The configuration route is:

```text
template-visible source preparation
-> sourceConfig
-> JavaScript evaluation
-> local newConfig
-> subtype translation / validation / preset completion
-> completeRuntimeConfig()
-> this.config
-> geometry / runtime / paint
```

No Control may validate, select a preset, select a visualization, choose an
orientation-dependent branch, or otherwise interpret a field while its value is
still unresolved `[[[ ... ]]]` syntax.

This plan does not invent a new JavaScript language or context. It restores
Controls to the existing FHS rule that dynamic configuration is evaluated before
its final value is interpreted.

Configured visibility remains configuration. Actual entity availability and
current interaction state remain runtime.

The shared active color-stop owner remains staged until Plan 19.

## 2. Prerequisite: Plan 16C

Plan 16C establishes the generic invariant:

> `translateConfig` receives only concrete/evaluated values.

This applies to fields interpreted by that tool. Nested generated-child source
keeps its own templates until evaluation by the owning child, as specified in
section 5. Parent translation treats those child expressions as source data.

Plan 16C is complete at the reviewed baseline. 17B uses its existing evaluator,
configuration-publication boundary and initial dynamic-geometry behavior.

The local `newConfig` passes through subtype translation and the existing
`completeRuntimeConfig()` boundary before BaseTool publishes `this.config`.
Geometry, runtime updates and child presentation then consume that complete
current configuration. Controls do not copy the evaluator or introduce another
configuration-publication route.

Controls may use pure subtype translators after evaluation, but they do not
create:

```text
candidateConfig
activeConfig
effectiveConfig
renderConfig
controlRuntimeConfig
```

as alternative general config owners.

## 3. Current Control Ordering Problem

Current Controls do not all interpret selectors at the same lifecycle boundary.

Examples include constructor-time branching/validation on:

```text
orientation
show.item_variant
show.item_viz
show.item_style
content mode / subtype-specific shorthand
```

Button, Number, Select and Slider currently merge subtype defaults/presets before
BaseTool captures source. Toggle also has a separate post-super `buildConfig()`
path.

That order is incompatible with a dynamic selector such as:

```yaml
show:
  item_style: '[[[ return entities[entity_slots.style[0]].state; ]]]'
```

when constructor logic attempts to use the literal template string as a preset
key.

Horseshoe and Sparkline already demonstrate the expected user model:

```text
FHS input changes
-> JavaScript produces a new selector
-> current config changes
-> geometry/presentation follows
```

Controls must follow the same model.

## 4. Source Preparation Versus Subtype Translation

Before movement, characterize what each subtype currently exposes through
`item`.

Classify current constructor work as:

```text
PRE-SOURCE / TEMPLATE-VISIBLE
POST-EVALUATION TRANSLATION
DERIVED GEOMETRY / PRESENTATION
```

### PRE-SOURCE

Keep only preparation that is valid without interpreting an unresolved dynamic
selector.

Examples:

- context-independent common defaults;
- stable source-visible default branches;
- recursive haptic/default objects that do not depend on a dynamic selector;
- source normalization that does not require a final enum/value.

PRE-SOURCE completion may inspect only concrete source shapes. If an action,
style or other value is itself unresolved JavaScript, preserve that source value
unchanged. Apply its corresponding defaults/normalization after evaluation and
before publication of the owning tool's current config.

Nested JavaScript may remain inside an otherwise concrete source object when
surrounding completion leaves that nested value intact and does not interpret
it. For example, adding a haptic default to a concrete action object preserves
its nested `action` template; a template returning the entire action object
must first be evaluated before that object can receive the default.

### POST-EVALUATION TRANSLATION

Move selector-dependent work here.

Examples:

- `orientation` validation;
- `show.item_variant` validation;
- `show.item_viz` validation;
- `show.item_style` validation;
- style/preset selection;
- orientation-dependent structural completion;
- visualization-dependent structural completion;
- safe content shorthand completion whose meaning depends on evaluated config.

### DERIVED GEOMETRY / PRESENTATION

Never put these in the translator:

- `config.svg`;
- native track/thumb coordinates;
- generated child placement;
- generated SVG/filter IDs;
- current selected/active branch;
- current HA options;
- current slider values/scale;
- current child paint.

## 5. Preserve Existing `item` Context Without Reintroducing Early Branching

Some current subtype constructors merge defaults/presets before BaseTool captures
source, so existing JavaScript may be able to read those completed values through
`item`.

Characterize this before moving preset completion.

If a currently supported JavaScript context demonstrably depends on a
selector-dependent preset being visible through `item`, preserve that behavior
with a bounded local evaluation sequence.

Allowed shape:

```text
stable prepared source
-> evaluate required parent-owned selectors once
-> local preset/item-context completion using those resolved values
-> evaluate only remaining parent-owned fields in their existing item context
-> local newConfig
-> pure translator
-> completeRuntimeConfig()
-> this.config
```

These are evaluation phases, not additional persistent config owners.

Do not create a second `sourceConfig` or `activeConfig`.

If characterization proves the selected preset was never part of a supported
template-visible contract, keep the simpler one-pass route.

Record the result per subtype before moving its configuration work. A bounded
selector phase is justified only by an existing, characterized `item` context;
otherwise use the single evaluation pass. Any necessary phases stay in the
existing configuration route and produce one local `newConfig` for publication.

### One evaluation per owning configuration pass

A template expression is evaluated at most once per configuration pass. Reuse
each already evaluated selector value when completing the local preset/item
context and evaluating the remaining fields. Do not revisit its original
template during recursive evaluation. Preserve `sourceConfig` for later passes.

The unit is an expression at its source field, not its string content: identical
template strings in different fields or different children remain independent
expressions with their own contexts. Two context phases can be necessary; two
executions of the same source-field expression in that pass are not.

`activeConfigSignature` represents the one complete evaluated parent config,
including preserved child source. Keep the existing evaluation scheduling:
unchanged evaluated output may retain `this.config`, and a pass for which
evaluation is not requested does not execute templates. No separate persistent
selector configuration or selector signature owner is introduced.

### Parent and generated-child evaluation contexts

Characterize the boundary per subtype before changing evaluation:

```text
parent-owned fields
-> evaluate with the existing parent Control item/entity context

generated-child-owned fields
-> retain source syntax through parent evaluation and translation
-> construct the complete generated child source once for its lifetime
-> evaluate with that child's existing item/entity context
```

Exclude child-owned template fields from recursive parent evaluation. Their
presence alone must not make the parent evaluator consume them. Identify the
actual parent layout fields and child source fields in Step 1 rather than
excluding an entire content branch that also contains parent-owned expressions.

Keep one source/current config route per tool. Apply the existing context-boundary
approach used by multipart Text without copying its evaluator or creating a
second configuration owner. A child-owned expression is never first evaluated
against the parent and then passed to the child as an evaluated source value.

## 6. Dynamic Control Selectors Are Required Behavior

`type` is compile-time structural identity and must always be static. It selects
the tool/config structure through compile/dispatch, before runtime evaluation.

All other ordinary Control configuration values follow the normal FHS
JavaScript contract: they may be authored statically or as JavaScript that
resolves to the same accepted value or shape.

A field is not considered static merely because the current implementation or
schema happens to consume or describe it as static before evaluation. Control
schemas describe this general contract; static constraints define the accepted
value after JavaScript evaluation.

The order for ordinary configuration values is:

```text
static source or JavaScript source
-> evaluate JavaScript in the owning context
-> validate / normalize / select the preset from the concrete value or shape
-> complete and publish current config
```

Characterize and support representative selectors, including:

```text
orientation
show.item_variant
show.item_viz
show.item_style
visibility
```

The list is representative, not a whitelist. The same rule covers ordinary
subtype values, action objects, styles, label positioning and other normal
configuration fields. Parent/child ownership and single evaluation follow
section 5.

Static and equivalent JavaScript forms must converge on the same canonical
configuration after evaluation/translation.

Example:

```yaml
show:
  item_style: ios
```

and:

```yaml
show:
  item_style: '[[[ return "ios"; ]]]'
```

must select the same Toggle preset.

A browser/FHS-input regression must prove at least one live selector switch,
for example:

```text
fhs_input_select
-> Toggle item_style
-> ha -> ios -> industrial
```

without recreating card configuration externally.

Likewise characterize dynamic orientation where the subtype supports both
orientations.

### Schema alignment

Update Control schema definitions so ordinary configuration values accept
`common.javascript` consistently while compile/dispatch `type` stays static.
Missing JavaScript support for an ordinary field is a schema inconsistency to
correct in 17B, not a restriction on that field's runtime contract.

Do not leave runtime support and authoring schema in disagreement.

Regenerate derived schema output through the normal schema generation workflow.

## 7. ControlBase

Preserve common source-visible preparation where it does not depend on a dynamic
subtype selector:

- visibility/unavailable defaults;
- recursive haptic defaults;
- label defaults;
- label positioning/style defaults.

Apply the PRE-SOURCE shape rule from section 4 to these defaults. In particular,
`addControlHaptics()` must preserve a whole-action template instead of reading
its `.action` or merging the template string as an action dictionary. After the
owning evaluation produces the action object, apply the normal control haptic
completion before current config publication.

Likewise preserve a whole `label.styles` template instead of passing its source
string through `toStyleDict()` or alignment-style merging during construction.
Normalize and merge evaluated styles with label alignment afterward, before the
owning tool publishes current config. Apply the same ordering to a dynamic label
position when selecting alignment. Preserve the parent/child contexts from
section 5 and each expression's single owning evaluation.

Do not remove existing visibility validation until equivalent failure
timing/behavior is proven.

Generated label TextTool creation remains separate because absolute coordinates
depend on current parent geometry.

A parent geometry change may recreate the label tool. Once created, the label
child source is stable for that child lifetime.

## 8. Family-Wide Geometry Rule

All five concrete controls use:

```text
geometry.svg
```

No migrated control retains:

```text
config.svg
```

as a compatibility copy.

Subtype geometry extends the same owner.

### Initial dynamic configuration

Use Plan 16C's existing first-publication boundary. A constructor may initialize
geometry and child lifecycle storage, but selector-dependent geometry and
generated children are built from the first fully evaluated `this.config`.
Later configuration changes use the same ordering.

Retain the existing initial dynamic-render behavior and initialization signal.
Use `hasJavascript` / `activeConfigInitialized` for that boundary. Before the
first complete dynamic publication, render and lifecycle forwarding must
tolerate selector-dependent children being absent. In particular, constructors
do not build unresolved Button content, Select option content, Toggle icons,
Slider StateTools, Number children or label TextTools. The first publication
builds the applicable geometry and children once. Static Controls can initialize
immediately from their concrete translated config.

Group changes update placement from current config; theme changes refresh
presentation through the existing change signals. No additional waiting state
or readiness lifecycle is introduced.

### Button

Move button SVG/bounds and indicator placement inputs into geometry.

### Select

Move control bounds, segment division and indicator placement into geometry.

### Toggle

Move:

```text
svgVbW
svgVbH
renderTrackX
renderTrackY
renderTrackWidth
renderTrackHeight
on/off knob positions
live derived icon transform
```

to geometry/render-derived owners.

Generated shadow/filter IDs are instance render resources, not config.

### Slider

Calculate fixed physical bounds when config/group geometry changes and let
pointer/render paths consume those values.

State-dependent thumb positions remain derived from current runtime values.

### Number

Fold current `numberGeometry` into:

```text
geometry.*
```

and remove the parallel `numberGeometry` owner.

Keep `valueMeasurementSignature` and `valueMeasurementPass` as explicit
measurement lifecycle fields.

### Dormant Toggle fields

In particular, checked/unchecked preset `iconStyles` and any other dormant

```text

-> preserve

-> may be removed in Pass B

-> separate functional change, not 17B
```

## 11. Generated Content and Structural Inheritance

Preserve the current inheritance order:

```text
parent entity
-> shared content item
-> per-option/item override by ID
-> complete generated child source
-> generated placement / pointer-transparent actions
-> child construction
```

Structural inheritance is resolved once per generated child lifetime.

The complete generated child source does not need to be written back into the
parent's canonical config.

Button keeps shared configured content.

Select keeps shared configured content plus each option's authored override
dictionary.

Different Select options may therefore create different complete child sources
from the same shared item.

Child-owned JavaScript remains source syntax during this structural inheritance;
section 5 defines its owning evaluation context.

### Dynamic inherited entity binding

When a parent's evaluated `entity_index` changes from A to B, BaseTool binds the
parent from the newly published current config. Generated children follow the
existing inheritance priority: an explicit shared-item or option override still
takes precedence over the parent entity.

For a child that inherits the parent binding, use an existing explicit live-binding
route only where that is already the child's contract. Where the entity is part
of stable structural source, end the old child lifetime and construct one
replacement source using B. Close old resources once and forward the current
lifecycle to the replacement once.

Do not simulate new structural inheritance by mutating a retained child's
`config.entity_index` or `sourceConfig.entity_index`. Ordinary selection/state
updates retain child/source identity and do not repeat inheritance.

### ControlContent canonical reference

`ControlContent.config` may reference canonical parent configuration.

Therefore ControlContent must **not mutate that shared parent object in place**
while normalizing padding, margins, items, or generated child inputs.

Normalized construction inputs and completed generated-child values remain local
construction/geometry data unless they are already canonical parent config.

Config/geometry/option changes may legitimately end one child lifetime and create
a replacement. End old child resources first and activate replacements exactly
once.

## 12. Parent Paint

Remove runtime writes such as:

```js
child.tool.config.styles = ...
```

Use the existing contract:

```js
child.tool.setPaintStyles(completeResolvedMap);
```

Preserve the exact merge priority:

```text
visual-state icon/text styles
-> configured child styles
-> control transition
-> child state-map/color-stop/animation/filter cascade
```

Configured child styles therefore keep their current priority over parent
selected/active visual styles where that is current behavior.

Semantic parent paint applies only to the current semantic scope:

```text
Icon
Text
State/Name/Area adapted to Text
```

Do not inject that semantic paint into:

```text
Line
Circle
Horseshoe
Sparkline
```

which retain their independent presentation behavior.

Text font-metric paint changes must trigger the 16B measurement invalidation
route. Control code does not reset Text measurement fields directly.

Keep configured active/inactive and selected/unselected branches in config.

Use current runtime selection to derive the current map locally.

Do not create:

```text
paint.active
paint.inactive
paint.selected
paint.unselected
paint.optionStates
```

as duplicate configured branches.
