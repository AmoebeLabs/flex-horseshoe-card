# Side-positioned rectangle and polygon paths

## Status

Implementation plan for GitHub issue #610. Development takes place on its
feature branch. The feature reaches `master` only after all subissues, tests,
documentation, and visual validation are complete.

## Goal

Give every closed shape with sides the same predictable path coordinates. A
user identifies a corner with an integer and a position along a side with a
decimal. The same geometry drives a horseshoe and a normal polygon shape, so
both can be placed exactly on top of each other.

This extends the existing generic path engine. It does not add polygon-specific
state, scale, gradient, tick, label, or animation renderers.

## User model

Corner numbers increase clockwise. A decimal is the distance along the side
from that corner to the next corner:

```text
Rectangle             Triangle              Hexagon

0 ------- 1               0                   0 --- 1
|         |              / \                 /       \
|         |             /   \               5         2
3 ------- 2            2 --- 1               \       /
                                               4 --- 3
```

- `0.5` is halfway from corner `0` to corner `1`.
- `1.5` is halfway from corner `1` to corner `2`.
- For four sides, `4` is the exact closing end of side `3`.
- `start: 0` and `end: 0` has zero length and draws no state path.
- A complete rectangle uses `start: 0` and `end: 4`.
- A complete hexagon uses `start: 0` and `end: 6`.

`direction: clockwise` follows increasing positions. `direction:
counterclockwise` follows decreasing positions and wraps over the closing
position when needed.

## Choosing what faces upward

`top` places one side position at twelve o'clock by changing the generated
coordinates. It is not an SVG transform, so ticks and labels use the final
geometry and remain readable.

- `top: 0` puts corner `0` at the top.
- `top: 0.5` puts the middle of side `0 -> 1` at the top.
- `top: 0.1` puts the point ten percent along side `0 -> 1` at the top.

The natural default is `top: 0` for polygons with an odd number of sides and
`top: 0.5` for polygons with an even number of sides. Odd polygons therefore
start with a point at the top; even polygons start with a horizontal top side.

## Selecting part of a path

`start` and `end` select the centerline used by the complete horseshoe scale.
State, scale, gradients, gaps, caps, ticks, labels, markers, and animation all
map from zero to one hundred percent over that selected centerline.

For a rectangle, this creates a roof that remains proportional at every size:

```yaml
path:
  type: rectangle
  width: 80
  height: 50
  radius: 3
  start: 3.5
  end: 1.5
  direction: clockwise
```

Nested rectangles can use the same positions with different dimensions. Their
roof paths then keep the same composition without pixel coordinates or negative
offsets.

## Rounded corners

Rectangle and polygon corner numbers remain stable when a corner radius is used. An integer
position lies halfway around the rounded corner. Half of that corner belongs to
the preceding side and half belongs to the following side. `radius: 0` places
the integer at the sharp corner.

This makes `0.5` the middle of the complete top side range for every rectangle,
including both adjoining half-corners.

## Polygon dimensions and corner radius

A convex polygon has `sides >= 3`. Its configuration uses the same dimensions
and corner-radius meaning as a rectangle:

```yaml
path:
  type: polygon
  sides: 6
  width: 80
  height: 55
  radius: 4
```

`width` and `height` define the exact outer bounds. `radius` rounds the corners
and defaults to `0`. Polygon and rectangle configuration is therefore identical
for dimensions and rounding.

## One geometry contract

Every generator returns one continuous SVG centerline definition. Polygon and
rectangle paths enter the same browser geometry, value mapping, range painting,
gradient, mask, element, and animation modules as every other path type.

The standalone `layout.polygons` tool uses the exact polygon generator used by
`path.type: polygon`. A shape and a horseshoe with equal center, dimensions,
side count, and `top` therefore have identical coordinates.

The first version supports ordinary convex polygons. Star polygons,
arbitrary point lists, and multiple disconnected paths are outside this scope.

## SAK reference

The [SAK Regular Polygon tool](https://swiss-army-knife-card-manual.amoebelabs.com/tools/regular-poly-tool/)
demonstrates useful Schlaefli-based regular-polygon point calculations. Proven
calculations may be retained where they satisfy this contract. The monolithic
tool lifecycle, star-polygon options, defaults, and rendering ownership are not
copied into FHS.

## Delivery layers

1. **#611 Geometry** - shared numeric rectangle and polygon centerlines, plus
   focused unit and browser geometry tests.
2. **#612 Horseshoe** - configuration-boundary validation and path contracts;
   all rendering continues through the generic engine.
3. **#613 Polygon shape** - `layout.polygons` using the shared generator and the
   established shape lifecycle.
4. **#614 Documentation and validation** - practical examples, configuration
   reference, complete builds, and browser visual comparison.
5. **#620 Consistent dimensions and rounding** - require polygon `width` and
   `height`, use `radius` for corner rounding, and keep the shape and horseshoe
   on the same rounded centerline.

Each subissue is implemented on its own branch and merged into the feature
branch. Closing the parent issue and merging the feature branch into `master`
requires all five layers to be complete.
