## 2. Current Code and Migration Boundaries

`HorseshoeGauge.setConfig()` routes the original root fields and both supported
layout sections. It applies legacy tickmark conversion and `normalizeBaseConfig()`
before BaseTool captures source configuration.

Current `updateRuntimeConfig()` swaps `this.config` through `activeItemConfig`
and `runtimeConfig`. `normalizeRuntimeConfig()` combines public defaults,
validation, group placement, SVG coordinates and active color-stop output.

Current `setState()` calls `getGaugeStateData()`, publishes `stateData.config`,
then writes localized `state_map` and `mapped_state` into that configuration.
String stops and rank-state mapping can also substitute render stops and a
different value scale. These calculations are functional; the config swapping
is the architectural problem.

The shared color-stop chain extends beyond Horseshoe. Current consumers include
BaseTool, CardEntities, TextTool, SparklineGraphTool and Horseshoe helpers.
Controls and ordinary shapes consume that chain through their retained children
or BaseTool paint operations. The audit must follow those indirect consumers too.

18B deliberately retained normalized active `colorstops` as a temporary legacy
exception. Its `completeRuntimeConfig()` contains the narrow per-series override
bridge that reads the last evaluated source signature on theme changes. Plan 19
removes that bridge as part of the complete shared cutover.

Out of scope: new path forms, marker features, color semantics, JS error handling,
new validation policy, and unrelated defects. CardEntities issue #876 remains a
separate bugfix. The known HA-validator issue #864 also remains separate.

## 3. Configuration Publication and JavaScript

The normal route is:

```text
existing card compilation and legacy routing
-> preserve established template-visible source preparation
-> sourceConfig
-> existing JavaScript evaluation
-> local newConfig
-> translateConfig
-> existing context-dependent completion boundary where needed
-> this.config
-> geometry / runtime / paint
-> render
```

Use BaseTool's existing explicit translator and pre-publication completion route.
Do not copy its evaluator into Horseshoe or call a subclass-dependent translator
from the BaseTool constructor.

Before moving preparation, classify every current default/completion as
PRE-SOURCE/TEMPLATE-VISIBLE or POST-EVALUATION. Characterize what real templates
see through `item`, including currently prepared show/default/entity fields and
any normalized values actually exposed by the existing route. Preserve that
context and order without creating a second persistent configuration owner.
If an existing compatibility context needs a local view, it belongs to the same
evaluation pass, not another evaluator or retained current config.

PRE-SOURCE completion inspects concrete source shapes only. Whole-value JS stays
source until its owning evaluation. Normalization and validation then operate on
the evaluated values. Existing template behavior and error handling stay as they
are; no last-valid-config recovery or general undefined prohibition is added.

Static and dynamic configuration use the same translation semantics. Complete
configuration is published before state processing. Initial dynamic construction
must not feed unresolved values to path generation, scale calculations, marker
setup or rendering. Reuse the existing first-publication/readiness pattern and
retain the card's real connection state.

### 3.1 Before the first dynamic publication

Use only `hasJavascript` and `activeConfigInitialized` to identify the existing
pre-publication boundary. Use the existing CardTools connection state for
connection ownership. No queue, worker, extra readiness flag or state machine
is introduced.

For a dynamic Horseshoe whose complete config has not been published:

| Entry point | Required behavior |
| --- | --- |
| `render()` | Return empty output; do not generate path, scale or marker inputs. |
| `updated()` | Do not bind/generate paths or inspect evaluated marker/show fields. |
| `updatePalettePaint()` | Remain inert until current configuration and its dependent owners exist. |
| `hasPresentationChanged()` | Do not calculate presentation from unresolved fields; the normal first-publication change signal activates presentation afterward. |
| `setState()` | The normal card route calls it only after complete current config has been published. |
| `connected()` / `disconnected()` | Preserve the lifecycle of already-created concrete async resources; do not initialize config-dependent resources from unresolved values. |

First publication completes `this.config`, then initializes/updates geometry and
the required animator/marker resources. Initialization observes the card's actual
connection state, including connection before publication and publication after
a disconnect. Subsequent render/updated/state processing follows the existing
normal route. Static initialization keeps its existing behavior.

Preserve `show.horseshoe` filtering deliberately: a concrete static false remains
factory-filtered; an unresolved expression is retained without evaluating or
interpreting it during section construction. Characterize the existing dynamic
visibility behavior and preserve it after publication. Do not invent another
visibility policy or destroy/recreate an instance merely because the field is JS.

`this.config` remains the sole current tool configuration. Group and theme
changes update their actual derived owners; current HA state cannot publish or
repair configuration. Retain the existing distinct configuration, group and
theme change signals instead of treating each as a general config replacement.

Public YAML, legacy routing, default priority and existing constraints remain
unchanged. Existing field validation stays at configuration boundaries. Do not
add defensive config checks or replacement defaults to normal consumers.

## 4. Horseshoe Owners and State Mapping

| Owner | Contents |
| --- | --- |
| `sourceConfig` | Stable template-visible source, including required existing source defaults and unresolved expressions. |
| `this.config` | Complete current public/translated Horseshoe settings, configured state map, configured styles and structural color-stop definitions. |
| `geometry` | SVG placement, current group-derived placement/transform, path input/definition, measured path, transformed geometry, positioned elements and their measurement inputs. |
| `runtime` | Entity and entity config, raw/numeric/mapped state, current display state map, effective value scale, value mapper, unpainted value ranges and displayed progress. |
| `paint` | Active stops/minmax stops, gradients, painted ranges, effective marker styles, background presentation and renderer layer appearance. |
| Existing domain owners | PathGeometry measurement/cache, PathStateAnimator frames/mount and marker icon asynchronous lifecycle. |

Move standalone `pathConfig` to `geometry.pathInput`. Keep the path generator
inputs and calculations equivalent. Group offsets and legacy position precedence
must produce the same coordinates; removing config-derived SVG is not permission
to change placement formulas. Audit CardLayout initialization and all remaining
consumers of the old SVG fields as part of this move.

State mapping stays cohesive in the existing state module. Change its result
from a general state-specific config to explicitly named derived data:
raw state, mapped value/state, current state map, render stops/minmax stops and
the effective scale input. The caller publishes each result to its owner.

`config.state_map` remains the configured map. Ranked/string-state maps and
localized display labels belong to runtime. A ranked render scale supplies
`runtime.scale` and the existing value mapper without changing configured scale
min/max. Numeric, ordinary mapped, string and rank-state cases retain their
current threshold order, source colors, labels and value conversion.

### 4.1 Semantic mapping versus palette-derived colors

Keep semantic runtime mapping separate from the active colors used to render it.
Runtime retains state/value/rank, display labels, relations, source value and the
effective numeric mapping/scale. Paint retains the current mapped-state color,
rank/string render colors, active palette fallback colors and painted output.

An explicitly configured state-map color remains valid configuration input and
keeps its existing priority. A color derived from the active palette belongs to
paint, not `runtime.stateMap` or `runtime.mappedState`. The same applies to a
retained full source color-stop object: retain only the selected index/rank/value
needed by semantic mapping, not an active-color object inside runtime mapping.

Keep the existing mapping algorithm cohesive. Its derived output distinguishes
semantic mapping from render color inputs; the caller publishes each to the
correct owner. Do not split the mapping algorithm across unrelated modules.

For string stops and rank-state, a color-only palette switch refreshes paint
while preserving the mapped numeric value, selected rank, semantic state-map
result and effective calculation scale. Reuse unchanged semantic mapping rather
than rebuilding it to insert new colors. Numeric threshold/rank/mapping changes
still invalidate the calculations that actually depend on them.

Separate unpainted value ranges from painted SVG ranges. Moving both under an
object called paint would conceal the mapping responsibility rather than clarify
it. Conversely, the existing mixed `renderContract` must not survive as another
unclassified general state owner: place its retained fields with runtime or paint
according to what they represent, adapting renderer inputs where necessary.

Labels, ticks and markers receive explicit configuration and runtime/geometry/
paint inputs. Remove the `runtimeConfig` convention from those interfaces.
Support modules remain ordinary domain modules, not new BaseTool descendants.

Preserve all generators, offset paths, spline/value mapping, scale modes, marker
attachment/orientation, flips, readable labels, round-cap browser fixes, gradient
overlap policy and animation behavior. Keep opacity on the established complete
paint group where required. Preserve asynchronous palette and icon completion,
DOM measurement and connection cleanup order.

## 5. Atomic Active Color-Stop Cutover

Implement this as one isolated, working integration change across every family.
The active theme/state-selected output moves out of config-shaped fields.
Structural/authored definitions, including supported legacy authoring forms,
remain configuration. Do not rename public YAML keys.

Owner destinations:

- Ordinary tools: their `paint.colorStops` when they have item-level stops.
- Entity-level stops: CardEntities paint indexed by the existing entity index.
- Text: part-level paint at the existing part owner, including mapped/referenced
  parts; do not move a selected state-map override into canonical part config.
- Sparkline: parent paint and active paint on its existing stable series items.
- Horseshoe: active numeric/string/rank render stops and minmax stops under paint.

Consumers receive the appropriate active paint explicitly where a part or series
is involved. Do not create another general configuration container merely to
carry a palette. Preserve item-over-entity priority, parent/series inheritance,
legacy explicit override merging, stop styles and fill/stroke selector behavior.

### 5.1 Explicit Sparkline series overrides

During the normal publication pass, inspect each evaluated raw series entry
before inheritance obscures whether it authored a legacy color-stop override.
Transfer only that narrow override information to paint/provenance on its
already-stable series item. Absence of an override means parent paint is inherited;
an authored override is composed with current parent paint using the existing
merge order. This provenance is source information for paint composition, not a
second effective series configuration or a duplicate active palette.

For whole-array JS, use the entries produced by that single owning evaluation.
On actual config changes, update or remove the narrow override along with normal
series binding; retain identity by the existing series ID. On theme-only changes,
compose paint from the retained explicit override and current parent paint.

Do not retain a complete raw series entry/collection, create a raw-series cache,
parse `activeConfigSignature` as runtime configuration data, or evaluate JS again
to recover provenance. The temporary 18B bridge disappears completely. Preserve
stable Series item and Graph identities when their own inputs are unchanged.

All inherited consumers use the same current owner or an explicit reference to
it. No persistent active config+paint copies, obsolete aliases or partial-family
cutover remain. Remove BaseTool/Text/CardEntities assignments of active output
into config and remove the temporary 18B Sparkline bridge in this same step.

Keep `ColorStops.normalize()`, minimum-stop completion and color interpolation
semantically unchanged. Reuse existing field/default completion at the config
boundary; palette-dependent validation may consume the locally normalized
result without publishing it as another canonical config.

Active stops are not exclusively colors. Their scales, values and ranks can
feed gauge defaults, thresholds, grade geometry and state mapping. Preserve
those dependencies explicitly. Calculation owners receive only the needed
numeric/mapping input, rather than reading a relocated general config.

For invalidation:

- Color-only changes refresh paint and presentation, retaining unaffected path
  definitions, measurements, processed history and running animation position.
- Numeric threshold/rank changes refresh the dependent calculations and their
  presentation even when the current formatted state is unchanged.
- Actual shape/group changes update geometry through its existing owner.
- Palette completion before or after initial path measurement follows the
  existing lifecycle; neither ordering loses colors or triggers another evaluator.

Run focused ordinary-tool/Text/Control/Sparkline/Horseshoe tests together directly
after this cutover. If an atomic working result cannot be obtained, stop and
revise this substep. Do not commit a half-migrated owner or undo user changes.
