# 2026.09.28 - 16 - Configuration ownership simplification

## 1. Goal

Centralize existing tool configuration processing so `sourceConfig` remains a stable re-evaluation source and `this.config` is the active configuration used by ordinary layout tools. Remove repeated defaults, conversions and checks only where the same work already has a configuration owner. **This is a refactor, not a change to public or runtime behavior.**

The [Plan 16 simplification guardrails](refactor2/16-plan-simplification-guardrails.md) take precedence over earlier proposals that expanded this refactor beyond existing behavior.

## 2. Prerequisites

- Plan 15 and its Icon follow-up are complete on master (`e70f536f2dbc87d7b242d1d8f3784bad37f5563f`).
- Review `refactor2/00-master-simplification-plan.md`, `refactor2/TESTING.md` and the guardrails above before implementation.
- Recheck the current commit, affected functions, callers, tests and source size before editing code; the locators below are only a starting point.

## 3. Functional contract

Keep the current card-level compilation and ordinary tool lifecycle. For configurations that work today, the tool-level route remains:

```text
card-compiled sourceConfig
  -> existing JavaScript evaluation, when present
  -> existing defaults / conversion / normalization / validation
  -> active this.config
  -> existing geometry, state updates and rendering
```

JavaScript is part of that route, not a separate lifecycle. The user authors the template and may return a suitable default when HA data is absent. The user is responsible for its output; the card does not add a new fallback or recovery mechanism. Preserve the current template evaluator and rendering behavior. Do not add pending-tool, accepted-tool or retry states.

`sourceConfig` must not acquire runtime mutations through `this.config`, including nested `show`, `color_stops` or `state_map` objects. Existing derived fields such as `svg` may stay on the active config, but must not feed back into the source.

For the same valid configuration, geometry, rendering, theme, layout, entity selection and error behavior remain unchanged. Keep HA state separate from configuration: numbers, text, `unknown`, `unavailable` and `undefined` remain runtime inputs, not configuration errors.

Plan 16 does not change how the card handles user-authored JavaScript. Its purpose is to simplify ownership of the configuration that already works.

## 4. Current-code validation

Before implementation, follow the current source through BaseTool, each ordinary tool, CardTools and `main.js`; identify every consumer of `configChanged`, `sourceConfig`, `this.config`, `entity_index`, `zpos` and active `colorstops`. Classify each check as configuration, HA/network/DOM runtime data, lifecycle, algorithmic or consumer-owned conversion. Remove a check only when the existing owner already provides the same guarantee.

Verify existing startup and JavaScript behavior when moving code. These checks establish regression coverage, not new behavior.

## 5. Current-code anchors

- `src/main.js:setConfig()` owns the existing card-level templates, `ref()`, `calc()`, `same_as`, compounds, slots and final layout preparation. Leave that pipeline in place.
- `src/base-tool.js` currently aliases `sourceConfig` and `this.config`, evaluates JavaScript in `updateRuntimeConfig()`, materializes color stops and combines config, group and theme changes into `configChanged`.
- `src/card-tools.js:getSortedRenderableTools()` repeats z-position coercion.
- Name, Area, State, Text, Icon, Rectangle, Polygon, Line, Circle and Arc have ordinary runtime-config hooks. Text has its own parts/measurement lifecycle; Icon has an external source lifecycle.
- Controls, Sparkline and Horseshoe also consume BaseTool change signals. Their own schema migrations belong to Plans 17-19.

## 6. Scope

- Make `sourceConfig` independent of runtime mutations while preserving existing JavaScript evaluation.
- Put existing ordinary-tool defaults, normalization and checks at one clear owner where they can be moved without changing when or how failures occur.
- Remove only duplicate downstream config work made redundant by that owner. Keep ordinary calculation and rendering linear.
- Distinguish accepted config changes from group/layout and theme-derived changes where the current broad `configChanged` signal causes unnecessary work; preserve every existing refresh.
- Keep config-derived shortcuts such as `entity_index` and `zpos` synchronized with the active config using the current lifecycle.
- Preserve active light/dark color-stop materialization and theme-dependent label/geometry changes.

Use direct code in existing owners. No validator framework, extra persistent config layer, state machine or chains of wrappers.

## 7. Out of scope

- New JavaScript validation, fallback or recovery behavior.
- New startup, retry, rendering or Home Assistant state behavior.
- Family-specific migrations in Controls, Sparkline and Horseshoe/Path (Plans 17-19).
- Changes to CardTemplates, graph formulas, history, FHS-input persistence or public YAML.

## 8. Implementation sequence and GitHub work

When authorized, create one Plan 16 parent issue and feature branch from current master. Use small child issues/PRs into that branch; keep master unchanged until the feature passes visual and automated review. Suggested order:

1. **Stable source:** establish current static/JavaScript behavior and remove source/active aliasing without changing evaluation or startup. Result: nested active mutations cannot alter later source evaluation.
2. **Ordinary tools:** consolidate only existing defaults, conversions and checks for shapes, text and icons. Result: the same valid inputs produce identical geometry and presentation with less repeated config work.
3. **Change signals and consumers:** separate config, group and theme work where needed, clean redundant z-position/config coercion, and preserve transitional family behavior. Result: unchanged input avoids unnecessary work without missing a layout/theme refresh.
4. **Integration:** run targeted and full regression checks, inspect the diff for new behavior or infrastructure, and record source-size/readability results. Result: a reviewable feature branch ready for the user's visual validation.

Use Sol xhigh for the shared BaseTool/change-signal design and final integration review. Luna Max may handle bounded ordinary-tool changes and focused tests. Stop if a child requires new failure semantics; move that work to a separate issue.

## 9. Checks that must remain

Retain checks for actual HA state, external Icon results, DOM/text measurement readiness, async lifecycle and algorithmic edge cases possible with valid configuration. Do not delete checks merely because they use `if`, `Number.isFinite` or a fallback. Avoid adding defensive checks outside existing config ownership.

## 10. Permanent tests

Verify source/active nested independence, repeated evaluation, geometry, entity selection, Text/Icon behavior, theme mode changes, group moves and HA state presentation. Cover Controls, Sparkline and Horseshoe compatibility with the BaseTool change.

Do not create tests that define new failure behavior. Build for the user's visual check; then run Node tests, lint, Rollup and affected Chromium/WebKit/Firefox suites according to `refactor2/TESTING.md` before final merge.

## 12. Definition of Done

- Existing valid YAML/JavaScript, startup, HA state, geometry, rendering, theme and group behavior are preserved.
- `sourceConfig` remains independent of mutable active config and derived fields.
- Existing configuration rules have clear owners; redundant downstream work is removed without new validation semantics.
- Config, group and theme updates do not cause unnecessary cross-work or missed refreshes.
- No new pending/recovery/fallback state or generic validation layer exists.
- Focused and full checks pass; size and readability results are recorded.

## 13. Guarantee for Plan 17

Controls can build on the clearer source/active ownership and change signals. Plan 16 does not silently change their behavior.

## 14. Implementation result (2026-09-29)

Feature issue #817 contains the merged source, ordinary-tool and change-signal subissues #818, #819 and #820. Integration is tracked by #821. Master remains unchanged pending visual validation.

- `BaseTool` now keeps a deep source snapshot; active `this.config` can receive derived fields without changing that source. A JavaScript update uses local `newConfig` during the existing processing route.
- Ordinary geometry work distinguishes configuration and group changes from theme-only paint changes. The existing broad `configChanged` signal remains for Controls, Sparkline and Horseshoe until Plans 17-19. Text parts retain their existing theme refresh.
- Existing Polygon field checks no longer repeat for a pure group move. CardTools sorts already-numeric z positions and render indexes directly. Constructor-only Text, Icon and Rectangle behavior was left unchanged rather than extending their rules to dynamic JavaScript output.
- No new JavaScript fallback, validation, render delay or error recovery was added.
