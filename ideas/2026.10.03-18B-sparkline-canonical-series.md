## 1. Goal and Functional Boundary

Give Sparkline the same recognizable configuration route and ownership as the
reference tools:

```text
template-visible source preparation
-> sourceConfig
-> existing JavaScript evaluation
-> local newConfig
-> translateConfig(newConfig)
-> existing completeRuntimeConfig() boundary where context is required
-> this.config
-> geometry / runtime / paint and domain consumers
```

The defining invariant is:

> At the operational boundary, this.config.series[] is the sole canonical series
> configuration. Every entry is complete before Series, History or Graph uses it.

Public YAML and observable behavior remain unchanged. Preserve history requests,
time windows, bucketing, aggregation, statistics, graph formulas, rendering,
animation, pointer interaction, tooltips, legends, axes and derived entities.
Do not add a validation framework, last-valid-config recovery or JS error policy.
The existing evaluator behavior remains the user's configuration contract.

Both migration and removal of proven redundant owners are mandatory. Moving
fields without removing the second configuration route is not completion.

## 2. Current Code Findings

- GraphTool currently completes defaults, styles, selectors and periods before
  BaseTool captures its source, then repeats some completion during runtime.
- Series.updateConfig() validates raw overrides, merges each one over its parent
  and stores a separately constructed item.config.
- An implicit single series is currently generated inside Series rather than
  appearing in the tool's canonical configuration.
- GraphTool stores derived dimensions in both this.svg and this.config.svg.
- History already owns requests, records and time calculations. Its updateConfig
  name describes ownership it does not have.
- Graph already has separate data and geometry invalidation. Its config object
  is calculation input, rather than public tool configuration.
- The parent GraphTool graphConfig is assigned without production reads. Each
  series graph already receives its own calculation input.
- Ordinary nested series templates currently use the outer Sparkline item
  context through BaseTool's recursive evaluator.

These are ownership and lifecycle changes. They do not justify altering the
underlying calculations or adding unrelated bug fixes.

## 3. Source Preparation and JavaScript

Classify constructor operations before moving them:

| Category | Placement and behavior |
| --- | --- |
| PRE-SOURCE / TEMPLATE-VISIBLE | Preserve existing concrete defaults and context visible through item. |
| POST-EVALUATION TRANSLATION | Interpret evaluated selectors, normalize shapes and complete final config. |
| DERIVED OUTPUT | Calculate only from current config under its geometry/runtime/paint owner. |

PRE-SOURCE preparation may inspect only concrete source shapes. If an entire
style, period, selector branch or other ordinary value is unresolved JavaScript,
preserve it unchanged until evaluation. Templates nested inside a concrete
object may remain when surrounding preparation does not interpret them.

The layout tool's structural type remains static. Existing dynamic Sparkline
selectors, including chart_type and period.type, retain their JS behavior.
Ordinary configuration values may be static or JavaScript producing the same
accepted value/shape. A schema omission alone does not make such a value static.
Correct directly affected schema mismatches locally; do not redesign schemas.

Use the existing evaluator and its context. In particular:

- Do not reinterpret series expressions as per-series-entity expressions.
- Do not evaluate inherited parent expressions once again for every series.
- Preserve template-visible defaults, source array order and existing key/value
  evaluation semantics.
- Do not expand implicit series in sourceConfig: item sees the prepared public
  source form, while current config receives the canonical internal form.
- Keep newConfig local; never introduce this.newConfig or another persistent
  general configuration object.

Static input uses the pure translator at construction. JS-backed construction
retains source-safe working state and reaches the same completed config through
the existing 16C runtime route. Do not instantiate configuration-consuming
Series/Graph processing from unresolved values. Use the existing initialization
signal and lifecycle rather than a new pending/accepted-config state machine.

### Before First Dynamic Publication

Choose deferred domain-owner construction (review option B). Static Sparklines
retain construction from their translated config. Dynamic Sparklines create
Series and History only after their first complete config publication; Graph
creation then follows the existing period/data rules.

Use `hasJavascript && !activeConfigInitialized` at the lifecycle boundaries:

- `render()` and `renderSvg()` produce empty SVG before first publication and
  do not apply renderer/layer logic to unresolved configuration.
- `hasPresentationChanged()` reports no visible presentation before publication;
  it does not run the Series comparison or BaseTool's configured paint pipeline.
- `connected()`, `disconnected()` and `hassConnected()` do not call absent domain
  owners. Preserve the card's existing connection state in CardTools; do not add
  another tool readiness or connection flag.
- `hassAvailable()` may record the existing HA-availability information, but
  does not create legend/config consumers from unresolved values.
- `requiresHassUpdate()` returns true while initial dynamic publication is
  needed, then delegates to History as before.
- Palette refresh, legend publication/measurement and pointer attachment remain
  inactive before publication. No timer, request or listener is started then.

The first runtime-config pass evaluates and completes config through BaseTool's
normal route, creates the domain owners from that published config, and applies
the existing CardTools connection state before any history scheduling. If the
card is disconnected, History remains disconnected; later connection uses the
existing lifecycle. Do not replay earlier lifecycle events through a new queue.
After initialization, retain normal owner reuse and connection behavior.

Preserve the card's current producer/consumer ordering:

```text
source entities available
-> updateSparklineRuntimeConfig()
-> complete current config and initialize/update domain owners
-> bind Sparkline source entities
-> publish fhs_sparkline.* derived entities
-> update presentation consumers
```

An unchanged evaluated source retains the current config and does not repeat
translation. Group or theme changes retain their distinct invalidation meaning.
setState() does not complete or publish configuration.

## 4. Canonical Series Translation

Complete the parent and series in one recognizable configuration route. Keep
the implementation linear; use a helper only for a substantial existing concept,
not for each individual check or assignment.

```text
evaluated public input
-> parent legacy/default/style/period/axis completion
-> inspect evaluated raw series overrides
-> validate restrictions that depend on explicitly supplied fields
-> inherit parent once per series
-> apply existing selector/style priority
-> validate complete series and shared chart restrictions
-> finish context-dependent fields at the existing publication boundary
-> publish this.config with complete series[]
```

Raw overrides are transient translation inputs, not a second persistent owner.
Preserve current merge semantics unless a specific existing replacement rule
already applies; do not change Merge.mergeDeep() globally.

### Internal Entry Shape

- Missing public series creates one entry with ID `default`, the existing
  entity binding and the existing primary-axis behavior.
- Explicit entries retain their stable IDs, order, entity_index, y_axis_id,
  names/colors and complete inherited Sparkline, period and axis settings.
- Each entry contains its own ID, not the parent tool ID, and no nested series.
- A runtime item references its canonical entry directly. It does not clone,
  re-merge or complete that entry.
- Remove implicit/explicit configuration-building branches and the production
  hasExplicitSeries flag when they have no remaining runtime function.

Preserve the distinction between implicit and explicit input while validating
raw overrides. For example, the explicit-series chart restrictions must not be
applied to an implicit barcode or state-band graph merely because all final
configurations now contain series[].

### Existing Restrictions and Priority

Preserve non-empty unique IDs, integer entity bindings, axis IDs, offset-only
series period overrides, shared radial geometry and the prohibition on mixing
radial and Cartesian series. Evaluate JS before checking its resulting shape.

Keep the current precedence of parent selectors, series-wide item_style and
deeper line/area/minmax selectors. Preserve style and color-stop inheritance and
the existing color override behavior. Characterization tests establish those
results before the inheritance code moves.

### Whole-Value Series JavaScript and Schema

The ordinary FHS JavaScript rule applies explicitly to the public series value:

```yaml
series: |
  [[[ return [
    { id: "temperature", entity_index: 1,
      sparkline: { show: { chart_type: "line" } } }
  ]; ]]]
```

Keep this expression in sourceConfig. Evaluate it once in the existing outer
Sparkline item/entity context. The returned array is the raw explicit-series
input: validate its override restrictions before parent inheritance, then
publish complete canonical entries. Do not evaluate that outer expression for
each generated runtime item. Templates returned within the array retain the
existing recursive evaluator semantics and outer context.

Align the series field in the authoritative
`ai-card-builder/config-schema/definitions/layout/sparklines.yaml` locally:
an array of the existing layout.sparklineSeries entries or common.javascript.
Regenerate affected schema artifacts through the existing generation route.
Static item restrictions remain constraints on the evaluated array. Do not
broaden unrelated schema definitions or introduce a different JS syntax.

Add a real-evaluator regression comparing a static series array with whole-value
JavaScript returning that array. Assert equivalent canonical config, IDs/order,
entity bindings, inheritance and paint priority; source-template retention; one
owning evaluation; and Series entry reference identity without inheritance repair.
Also prove an invalid raw override returned by JavaScript is rejected at the
existing configuration boundary before inheritance hides the supplied field.

## 5. Domain Owners and Calculation Inputs

### Series

Series consumes complete config entries and owns stable runtime items, current
entity/entityConfig, rows, request/data statuses, graph instances, graph layout
coordination and the shared bin plan. Reuse surviving items and graphs by ID.
Removal or entity replacement retains existing request invalidation behavior.

Automatic per_hour remains `auto` in configuration. Series calculates its
numeric bin result from current dimensions, chart settings and density. The
graph input receives that result. Resizing may change the bin plan without
altering the authored configuration or discarding reusable processed data.

### History

Rename updateConfig() to updateInputs(). Keep the existing argument meanings
and domain-owned records, ranges, row conversions, timers, retries and stale
completion protection. History receives config references and runtime items;
it does not complete or own a general Sparkline config.

Preserve retained source history across repeated duration changes, missing-range
loading behavior and incremental live-row publication.

### Graph

Perform this bounded mechanical naming step separately from ownership movement:

```text
buildGraphConfig() -> buildGraphInput()
updateGraphConfig() -> updateGraphInput()
SparklineGraph.config -> SparklineGraph.input
graphConfig local/parameter names -> graphInput
rebuildGraphConfig completion flag -> rebuildGraphInput
```

Remove the unused parent GraphTool graphConfig instead of introducing an unused
replacement. Graph retains its real calculation input, processing state and
geometry. Do not wrap this domain engine in Tool-style containers for symmetry.

Keep plot-time versus source-time projection, comparison-day handling, numeric
bins, real-time scale bounds and locale-derived label inputs unchanged.
No graph formula changes belong in this naming step.

## 6. GraphTool Field Ownership

Map the existing fields before editing, using these fixed category boundaries:

| Owner | Existing information assigned to it |
| --- | --- |
| config | Completed public settings, configured styles/selectors/maps and canonical series entries. |
| geometry | GraphTool SVG placement/dimensions, tool-owned plot area/margins and axis references, legend layout/measurements, existing GraphTool renderer/path caches, animation baseline and tool-owned invalidation. |
| runtime | Current HA bindings, localized state-map results, period availability, data-change signals, tooltip/selection/hover/drag state and current derived values. |
| paint | Retained gradients, grade colors/visual presentation, legend marker presentation and effective derived styles where persistent. |
| domain owners | Series runtime items/bin plan/shared layout; History records/timers; Graph input, processed bins/statistics and engine-owned calculation geometry. |
| lifecycle | Child-tool instances, DOM references, listener identity, frame handles and connection/measurement scheduling. |

### Tool Geometry Versus Calculation Geometry

GraphTool.geometry contains the tool-owned placement, measured layout and
renderer caches that GraphTool already owns. It may retain an existing reference
to engine/Series output, but does not move or clone that calculation result into
a new tool owner.

SparklineGraph keeps coords, graphArea, axisArea, dataArea, drawArea, its geometry
input/result signatures and all graph-family coordinate calculations, including
graded, bar and point geometry. SparklineSeries keeps shared axis-range, bar
position/total and multi-series layout coordination. These are not GraphTool
calculations and do not move merely to give the tool a geometry container.
Do not introduce a Tool-style wrapper around Graph.

### Grade Calculation and Paint

Configured state maps remain in config. Localized/current mapping output belongs
to runtime. Numeric grade boundaries, rank values/ranges (including rangeMin and
rangeMax) and mappings needed by getGrades() remain calculation input consumed
by Graph. Grade colors and retained visual presentation belong to paint.
Preserve their existing association and calculation behavior; neither side
becomes another general public configuration.

The field inventory records every moved persistent field and its consumers.
Fields move with their existing calculations and call order. Do not duplicate
Graph-owned results inside a new general runtime or geometry structure.

Remove both this.svg and config.svg in favor of geometry.svg. Temporary migration
aliases must be removed before completion. Update real consumers, including
ControlContent-generated sparklines, legend/tooltip children and derived-entity
routing; do not modify raw card entity resolution merely because internal series
are canonical.

### Temporary Color-Stop Exception

Shared active color stops remain in their current location until the atomic
Plan-19 cutover. Complete/synchronize inherited series paint at the existing
pre-publication boundary where necessary, preserving current override priority.
Do not repeat the general parent/series merge during a theme update and do not
introduce a duplicate paint.colorStops owner.

Test palette loading and theme changes with both implicit and explicit series.
Pure color changes update presentation without requesting history or
reprocessing bins. Changed numeric grade/rank inputs retain their existing
data/geometry invalidation: they are calculation changes, not paint-only changes.
