# 2026.09.28 - 17 - Control configuration simplification

## 1. Goal

Reduce repeated control-configuration work after Plan 16 without changing public YAML, JavaScript-template behavior, Home Assistant state handling, interaction, rendering, or child lifecycles. This is a configuration refactor, not a control redesign or a bugfix project.

The [master simplification plan](refactor2/00-master-simplification-plan.md), [testing policy](refactor2/TESTING.md), and [Plan 16 guardrails](refactor2/16-plan-simplification-guardrails.md) apply. If a proposed deletion requires new validation, fallback, unavailable behavior, or recovery, leave that check in place and record why.

The older master-plan summary still mentions shared child-lifecycle work for Plan 17. This reviewed plan narrows that scope to configuration work; child-lifecycle changes are out of scope until separately agreed.

## 2. Prerequisites

- Plans 15 and 16 are on master. Review this plan against the current commit before touching code; the initial review used `55cf29d`.
- Preserve Plan 16's stable `sourceConfig`, active `this.config`, and distinct `configurationChanged`, `groupChanged`, and `themeModeChanged` signals.
- Plan 16 does not validate control-specific fields. A check may be removed only when the same control already provides the same result and failure behavior elsewhere.
- Characterize the current control routes before removing work. Constructor completion, JavaScript evaluation, HA data, and derived presentation are different responsibilities.

## 3. Functional contract

The existing card compilation and control construction remain in place. Preserve each control's current config-completion order: Button, Number, Select, and Slider complete their constructor-owned defaults and presets before calling `super(...)`; Toggle completes its selected style after that call and still needs `buildConfig()` for real configuration changes. JavaScript-backed updates continue through the current `BaseTool.updateRuntimeConfig()` route. Do not add a second evaluator, persistent config copy, validator framework, or new failure handling.

`this.config` is the current active control config. A group move may require geometry and child placement; a theme change may require paint/presentation work. Neither alone means that public control configuration needs to be completed or checked again. Actual HA entity values, option lists, and slider scale attributes remain runtime inputs, not configuration errors invented by this refactor.

Slider `scale.min`, `scale.max`, and `scale.step` are required scale inputs; the constructor supplies attribute references when they are omitted. Whether they are configured as literals or read from HA attributes, the resolved scale must be numeric and valid. Only the current slider value may be `unknown`, `unavailable`, or non-numeric and use the existing non-interactive background-track presentation. Do not apply that presentation to an invalid scale.

This plan does **not** promise that arbitrary invalid JavaScript output becomes valid, is rejected earlier, or retains a previous config. Existing JavaScript behavior remains the boundary. Static-versus-JavaScript equivalence tests cover only currently supported valid configurations.

## 4. Current-code validation

Before implementation, follow each control from `ControlTool.setConfig()` through its constructor, `BaseTool.updateRuntimeConfig()`, `setState()`, child tools, and `render()`. Recheck every named method against the then-current source; do not use the old line numbers as instructions.

For each apparent check/default/conversion, record whether it is:

1. constructor/config completion that runs once;
2. repeated work on a configuration change;
3. work repeated only because group/theme also sets the broad `configChanged` signal;
4. validation or conversion of current HA/DOM/runtime data; or
5. a calculation that valid config can still require.

Only category 3, or a proven duplicate in category 2, is a deletion candidate. Keep a check whose removal changes existing error or presentation behavior. Do not replace `configChanged` with a different broad combined condition or replace a small check with a larger abstraction. Decide separately whether each operation needs configuration, group/layout, theme, or ordinary child updates.

## 5. Current-code anchors

- `ControlBase` completes visibility, unavailable styles, action haptics, and label defaults in its constructor. `updateRuntimeConfig()` checks visibility on each pass. Its existing `getContentTools()` forwarding is lifecycle work, not part of this plan.
- Button, Number, Select, and Slider complete most presets and public field checks before calling `super(...)`; `BaseTool` captures that completed source. Do not move those checks solely to make the architecture look uniform. Audit their runtime methods mainly for unnecessary geometry or child reconstruction.
- Toggle calls `super(...)` before `buildConfig()`. Its stored source can therefore still need `buildConfig()` when a real JavaScript configuration update occurs. `updateRuntimeConfig()` currently repeats style completion and `validateOrientation()` under the broad `configChanged` signal, which also includes group/theme changes. Retain completion for actual configuration changes and the geometry/child refreshes that group or theme changes genuinely need.
- Slider `setState()` resolves literal or HA-attribute scale values and checks the resulting numbers. It also handles unavailable entity values and range ordering. These checks are not already guaranteed by its constructor.
- Select can build `option_map` from current `entity.attributes.options` and stores the result in `this.config.option_map`. Keep that ownership and its option-rebuild behavior. Its render-time indicator-position error has no equivalent constructor check today; deleting it would not remove a duplicate. `ControlContent` checks item ids/types when constructing its own nested content.
- Number's measurement pass, Slider pointer/timer cleanup, Select option rebuild, and all child lifecycle forwarding are intentionally unchanged.

At the reviewed commit, the eight `control-*.js` modules contain 4,646 physical lines. The full Plan-16 product baseline is 72 JavaScript modules, 23,692 code lines, and 32,378 physical lines. Re-measure both baselines at the implementation commit.

## 6. Scope

- Remove only repeated control-configuration work for which the existing control constructor or another existing control-owned path already provides the same result and failure behavior.
- Use the Plan-16 change signals individually: configuration changes may require preset completion and child config updates; configuration or group changes may require geometry and placement; theme changes require only the theme-dependent work. Verify the exact conditions per control before changing them. In particular, inspect ControlBase visibility and Toggle's repeated style/orientation work; neither is automatically removable merely because it runs more than once.
- Distinguish child recreation (`create*Tools()`) from forwarding updates to existing children (`updateRuntimeConfig()`, `setState()`, `updated()`, connection, and disconnect). Reduce recreation only when it is proven unnecessary; preserve forwarding and child lifetimes.
- Keep derived `svg`, active styles, child placement, and entity-driven option output synchronized with the current config and layout.
- Keep the implementation linear and local to the existing control owners. One small shared method is justified only if it removes actual duplication without changing lifecycle behavior.

## 7. Out of scope

- Centralizing or rewriting child `updated()`, `hasPresentationChanged()`, connection, disconnect, or measurement lifecycles.
- Moving HA-derived Select options out of `this.config.option_map` or introducing a parallel option-state object.
- Treating a missing/non-numeric HA scale attribute as an unavailable slider value. The current slider throws for an invalid resolved scale; only an unavailable current value uses the non-interactive background-track presentation. Preserve that distinction.
- New validation of JavaScript-produced subtype fields; new pending, retry, last-valid, or fallback states.
- Moving the Select render error or `ControlContent` constructor checks merely to eliminate their location.
- Control appearance, service/action semantics, pointer math, FHS input persistence, and Sparkline/Horseshoe work.

## 9. Checks that must remain

Retain checks of current HA state, HA-sourced slider scale and option values, runtime range ordering, pointer/drag validity, DOM availability, resource cleanup, and action failures driven by external data. Retain constructor or render checks that are the only current owner of a field until an equivalent, behavior-preserving route is proven. `ControlContent` keeps its own child-construction rules. Select continues to keep HA-derived options in `this.config.option_map`.

## 12. Definition of Done

- Existing supported YAML, JavaScript, HA state, group/theme, control interaction, child lifecycle, and error behavior remain unchanged.
- Every removed control-config operation has an existing owner that provides the same result; remaining checks are classified and explained.
- No new generic config or lifecycle framework, fallback, recovery, or unavailable behavior has been added.
- The feature branch passes focused/full acceptance and the user has reviewed its visual behavior before master merge.
- The source-size and readability results are recorded honestly, including controls left unchanged.

## 13. Guarantee for Plan 18

Plan 17 proves only the control simplifications that are safe under the Plan-16 behavior guardrails. It does not establish a new universal JavaScript-validation or lifecycle contract for Sparkline. Review Plans 18-20 for the same scope expansion before implementing them.

## 14. Implemented result

Issue #827 uses one feature branch and one integration PR. The audited change is local to the five control families and `ControlBase`; separate child issues would add no useful ownership boundary.

- Toggle keeps its constructor completion order. Its runtime preset completion now runs only when a JavaScript-backed control configuration changes. Configuration and group changes still rebuild its geometry and child placement; a theme-only change updates the retained icon.
- Button, Number, Select, and Slider still rebuild geometry and children for configuration or group changes. A theme-only change retains those children and forwards their runtime updates. `ControlBase` similarly updates a retained label on a theme-only change.
- The visibility check remains on every runtime pass. It is not duplicated in the constructor, and a failed check occurs after `BaseTool` marks the active config initialized; narrowing this check would change repeated-error behavior.
- Slider scale resolution and unavailable value handling, Select's HA-derived options, action handling, and all ordinary child lifecycle forwarding remain unchanged.

On the implementation branch, product-owned source has 72 JavaScript modules, 23,699 code lines and 32,386 physical lines. The Plan-16/master baseline was 72 modules, 23,692 code lines and 32,378 physical lines. The eight `control-*.js` modules changed from 4,646 to 4,654 physical lines: `ControlBase` +3, Button -2, Toggle +7, and the other five unchanged. The small source increase supports separate change conditions and preserved child updates; this plan removes repeated runtime work, not a large block of source code.

Focused Node regressions cover valid static and JavaScript Toggle config, theme-only child/label retention and forwarding, real `CardLayout` group `xpos`/`ypos` changes in Button/Number/Select/Slider, and repeated visibility failure. The user visually checked light/dark theme changes without finding a difference. Group movement is covered by the automated tests rather than that visual check. Final acceptance passed with 506 Node tests, lint, Rollup, and 19 existing browser checks across Chromium, WebKit and Firefox. The direct control cases are Node tests; the browser checks cover card lifecycle, group SVG layout, and config-reference rendering.
