# 01 — Card lifecycle and dataflow

This plan applies the shared implementation rules from
[`00-master-refactor-plan.md`](00-master-refactor-plan.md) and the shared test
strategy from
[`14-regression-and-integration-testing.md`](14-regression-and-integration-testing.md).
It must be implemented together with
[`06-fhs-sparkline-entities.md`](06-fhs-sparkline-entities.md), because the
card update order and publication of `fhs_sparkline.*` entities form one
functional change.

## 1. Goal

Make the card update route predictable again:

```text
Home Assistant sends one update
        -> FHS processes that update once
        -> tools calculate only what their inputs require
        -> Sparkline-derived local entities are propagated internally
        -> FHS schedules at most the necessary render
```

The central result of this plan is that `setHass()` is no longer a generic reprocessing function. It is the external Home Assistant input route only.

This plan establishes the direct update routes and their ordering. Plan 02
subsequently completes fine-grained visible-output comparison. Plan 05
subsequently separates Sparkline data changes from geometry changes. Do not
pull those larger optimizations into this plan, but do leave the update routes
ready for them.

## 2. Why this has priority

The architecture metrics show that Sparkline is the strongest multi-signal hotspot, and the source scan found two runtime calls from `SparklineGraphTool` back into `card.setHass(card._hass)`. The current card also restarts `setHass()` after an FHS-input change and after external palettes finish loading. Static imports remain acyclic, so ordinary dependency analysis does not reveal these runtime feedback routes.

The current route is therefore harder to reason about than it looks:

```text
HA -> main.setHass()
     -> Sparkline
     -> update fhs_sparkline.*
     -> Sparkline calls parent setHass(same hass)
     -> card domains and tools are evaluated again
```

Flags and readiness checks keep this from becoming a simple infinite loop, but that does not make the direction correct.

## 3. Baseline source locations

### Main HA entry

- `src/main.js`
- `set hass(hass)`
- `setHass(hass, forceUpdate = false)`
- Baseline locator: https://github.com/AmoebeLabs/flex-horseshoe-card/blob/731421a420e92cab7749ed9283fe832b9dc56247/src/main.js#L120-L330

Important baseline behaviour to verify:

- `_hass`, templates, Home Assistant helper, theme and child cards are updated near the start.
- `localEntityStateChanged` is read from `CardEntities.stateChanged`.
- runtime entity configs can be rebuilt.
- `renderRequired` becomes true for broad Hass-context changes.
- Sparkline runtime config/entities run before derived Sparkline entities.
- ordinary runtime config/entities run after derived Sparkline entities.
- the route ends with `requestUpdate()` if it did not return early.

### Internal card re-entry

The reviewed source has four internal routes that restart the card through its
HA entry:

- `src/main.js`: the `CardInputEntities` callback calls `setHass(this._hass)`;
- `src/main.js`: the palette-loaded callback calls `setHass(this._hass, true)`;
- `src/sparkline-graph-tool.js`: a bin/local-statistics refresh calls the parent `setHass()`;
- `src/sparkline-graph-tool.js`: accepted history calls the parent `setHass()`.

Calls such as `Templates.setHass()`, `HomeAssistant.setHass()` and
`ChildCards.setHass()` only publish the current HA context to their own owner.
They are not parent-card re-entry and must not be removed for this reason.

### Tool forwarding

- `src/card-tools.js`
- `updateSparklineRuntimeConfig()`
- `setSparklineEntityStates()`
- `updateRuntimeConfig()`
- `setRuntimeEntityStates()`
- Baseline locator: https://github.com/AmoebeLabs/flex-horseshoe-card/blob/731421a420e92cab7749ed9283fe832b9dc56247/src/card-tools.js#L85-L155

## 4. Current design strengths to preserve

The current `main.setHass()` already has a useful visible order:

1. update card-wide HA context;
2. evaluate entity configs;
3. update groups/card styles;
4. update Sparkline before ordinary tools;
5. publish Sparkline-derived entities;
6. update ordinary tools;
7. update animations;
8. mark state handled;
9. render.

Do not throw this away. The refactor should make this order **more exact**, not replace it with an event bus or unrelated framework.

## 5. Required final HA update order

The normal synchronous HA update must follow this sequence:

```text
1. `hass` setter calls `setHass(newHass)`.
2. Store the new HA reference.
3. Update card-wide HA-dependent domains:
   - Templates
   - HomeAssistant helper
   - CardTheme
   - ChildCards' HA reference
4. Determine which configured external/local-input source entities changed.
5. Re-evaluate runtime entity configuration only when its actual inputs changed.
6. Publish the final source entity/config arrays for this update.
7. Re-evaluate groups/card styles when their actual inputs require it.
8. Update Sparkline runtime config when required.
9. Give Sparkline its current source entities.
10. Let Sparkline calculate any synchronous data/result changes it can calculate now.
11. Rebuild `fhs_sparkline.*` entity objects from Sparkline results.
12. Compare old and new `fhs_sparkline.*` values; only changed values become new local entity input for consumers.
13. Update ordinary tools that depend on changed source/local entities or changed runtime config.
14. Update animation selection/state when its inputs changed.
15. Collect whether any visible card output changed.
16. Mark the source/domain change markers handled.
17. Call `requestUpdate()` once if visible output changed or a render is otherwise explicitly required.
18. End the HA update.
```

No step is allowed to jump back to step 1.

The entities array shared with Templates must retain its identity. Update its
contents only after the final source and derived entity values for the current
route are known.

## 6. Required async history completion order

A history result is not a Home Assistant state event. It must use this route:

```text
1. History request returns.
2. Verify that the result still belongs to the live Sparkline tool and active series/config.
3. If stale: ignore it and stop.
4. If current: store/prepare the returned history in the history owner.
5. Recalculate affected Sparkline data.
6. Recalculate graph geometry only when the new data requires it.
7. Update Sparkline statistics/metadata.
8. Rebuild affected `fhs_sparkline.*` entities.
9. Compare those values with the previous local values.
10. Update ordinary tools that depend on changed local values.
11. Update animation state only when affected.
12. Call `requestUpdate()` once if visible output changed.
13. End.
```

There is no `setHass(card._hass)` in this route.

## 7. Required timer/bin-boundary order

A bin-boundary/calendar timer is also not an HA event.

Required behaviour:

```text
timer fires
  -> determine whether the active time/bin range changed
  -> refresh/reprocess affected Sparkline history/data
  -> update affected fhs_sparkline.* values
  -> update dependent tools
  -> render only if output changed
```

Do not use the stored `_hass` object to restart the entire card update merely because a Sparkline timer fired.

## 7.1 Required FHS-input update order

An FHS input is a local card input, not a newly received HA object:

```text
input changes
  -> CardInputEntities publishes the changed input state
  -> evaluate affected runtime entity configuration with the current HA context
  -> publish the final source entities
  -> update Sparkline and ordinary consumers in their normal order
  -> update animations
  -> request one render when visible output changed
```

Preserve the existing local/global input persistence and synchronization
between cards. A change received by multiple cards must be processed by each
card without turning it into a fake HA update.

## 7.2 Required palette completion order

Loaded palettes change paint, not sensor history or graph data:

```text
palette load completes
  -> verify that the result still belongs to the active card/configuration
  -> apply the palette and invalidate affected paint caches
  -> update affected visual tools
  -> request the required paint render
```

Do not reprocess entities, history, bins or statistics through `setHass()`.
Keep the existing follow-up render used when gradients can only be updated
after their SVG elements exist.

## 8. Source entity changes versus local derived changes

Keep these sources distinct.

### Home Assistant states

Examples:

- `sensor.temperature`
- `binary_sensor.*`
- normal HA helpers/integrations

These arrive through `hass.states` and can make runtime JS config, groups, colors, tools and Sparkline change.

### FHS input entities

Examples already present in FHS:

- `fhs_input_number`
- `fhs_input_boolean`
- `fhs_input_select`

These are managed by `CardInputEntities` and have their own synchronization behaviour. Preserve that mechanism.

### Sparkline-derived entities

Examples:

- `fhs_sparkline.*` min/avg/max
- duration
- bin duration
- aggregation name
- min/max timestamp

These are **outputs from Sparkline processing**. They must not be treated as if HA had sent them in a new `hass` object.

## 9. Main.js responsibility after this plan

`main.js` must:

- own the outer order of one card update;
- publish current HA context to the appropriate card domains;
- ask CardTools/CardEntities to perform their functional work;
- combine change results into the final Lit-render decision;
- provide a small internal route for Sparkline async/local result propagation if one is needed;
- provide direct functional routes for FHS-input and palette changes;
- stop the card-wide lifecycle on disconnect/replacement through existing managers.

`main.js` must not:

- calculate Sparkline bins;
- calculate history ranges;
- understand line/radial/state-band graph details;
- pull statistics out of graph internals itself;
- use `forceUpdate` as a broad escape hatch for ordinary internal flow.

## 10. CardTools responsibility after this plan

`CardTools` remains an instance/lifecycle coordinator.

It may:

- enumerate tools;
- forward runtime-config/entity updates;
- return whether child tools changed if that fits the current internal API;
- forward connected/disconnected/update lifecycle;
- route Sparkline and non-Sparkline update order.

It may not become a second `main.js` that knows graph/history semantics.

## 11. Tool responsibility after this plan

A tool receives relevant prepared input and determines its own effective state.

The card can know that the input object changed. It cannot know whether that means the output of every tool changed.

Examples:

```text
StateTool:
20.1 -> 20.4 with integer output => displayed value may remain "20"
```

```text
Sparkline:
20.1 -> 20.4 => new point/history/statistics may matter even when a text label stays "20"
```

Do not centralize these semantics in `main.js`.

For derived entities, compare the state and every exposed value that consumers
can observe, including unit, device class, name and attributes. Return the
changed derived indexes or an equivalent ordinary change result. Do not mark
all derived entities changed merely because Sparkline processing ran.

The graph can still require a render when its geometry or points changed while
its published average remained equal. Keep the graph's own change result
separate from the changed derived-entity result.

## 12. Handling JavaScript runtime config

The baseline evaluates JavaScript-backed runtime config when Hass context changes. Preserve that capability.

Refinement required:

- “Hass context changed” must not automatically mean “every visual output changed”.
- runtime config can be evaluated cheaply when its dependencies require it;
- compare the resulting active config with the previous active config;
- only the tool work affected by a real config difference continues.

Do not change YAML JavaScript-template semantics as part of this plan.

JavaScript templates can read the shared `entities` collection and broader HA
context. Do not introduce a parser or dependency-tracking framework. Until
Plan 02 can narrow this safely, evaluate JavaScript-backed consumers
conservatively when newly published derived values can affect them, then use
their existing active-config comparison to avoid unnecessary follow-up work.

## 13. Groups and card styles

Groups and card styles remain earlier than tool rendering because tools consume their effective results.

Do not move group/style evaluation after tools merely to simplify main.

The desired improvement is only to avoid treating a broad HA assignment as proof that all tool output changed.

## 14. Animation update position

Animation selection remains after entity/tool data is current for that update. It must see the final source entities plus current Sparkline-derived entities.

Do not let an animation callback call `setHass()`.

If animation itself changes an SVG state over time, that is an animation/render route, not another HA data route.

## 15. Render decision

At the end of one logical update, there must be one card-wide answer:

```text
visible output changed? yes/no
```

That answer can include:

- tool effective-state change;
- runtime config change that affects output;
- group/layout change;
- theme/paint change;
- child-card state requiring parent output update;
- Sparkline geometry/statistics change;
- animation selection change.

The decision must not simply be “`hass` object arrived”.

“Once” here means one card-wide scheduling decision for one logical data
update. It does not forbid a separate, justified Lit/SVG follow-up required for
DOM measurement, gradient painting, pointer interaction or animation. Those
presentation callbacks must not restart data or history processing.

## 16. What may still call `requestUpdate()` directly

This plan should inventory current direct `requestUpdate()` calls. Direct calls can remain where the callback is inherently a render lifecycle boundary, for example geometry becoming measurable after DOM creation.

However, a direct call must have a narrow reason. It must not be used as a substitute for `setHass()` and must not cause unrelated history/data recalculation.

## 17. Required source inventory before editing

Codex must search the working branch for:

```text
setHass(
requestUpdate(
requiresHassUpdate(
stateChanged
forceUpdate
updateSparklineEntities(
```

For each call/site, classify it by functional reason:

- HA input
- config input
- derived Sparkline update
- async result
- time boundary
- DOM measurement
- pointer interaction
- animation
- theme/paint

Do not edit until all internal `setHass()` call sites are accounted for.
Record which direct `requestUpdate()` calls are legitimate presentation
boundaries and which ones currently compensate for card re-entry.

## 18. Do not solve this by adding flags

Do not introduce names/logic equivalent to:

```text
skipNextHass
preventRecursiveUpdate
isInternalUpdate
isLocalEntityPass
alreadyProcessed
ignoreSecondPass
```

If removing re-entry breaks a route, add the proper direct functional call for that route rather than recreating recursion with a flag.

## 19. Do not create an event bus

FHS does not need a generic publish/subscribe architecture for this change.

The current direct call graph is a strength when the direction is correct. Keep the sequence visible and traceable.

## 20. Naming rules for changes in this plan

Do not name code after this document's architecture prose. In particular do not introduce identifiers such as:

- `LifecycleContract`
- `UpdatePipeline`
- `ProcessingStage`
- `commitEntities()`
- `resolvedToolState`

Use current functional names. If a new main helper is needed, name it after the concrete action it performs, consistent with nearby `update...`, `set...`, `get...` methods.

## 21. Implementation and issue structure

Create one main GitHub issue and one feature branch for the complete lifecycle
change. The main pull request targets `master` only after every subissue below
has been merged into the feature branch and the complete acceptance suite
passes.

Use **Refactor card lifecycle and internal data flow** as the main issue title.
Create its feature branch from the current `master`; let the GitHub issue
number prefix the usual lowercase issue-title branch name.

Use **seven subissues**, implemented in this order. Create every subissue branch
from the current feature branch, merge it back into that feature branch, and
close the subissue after its result has been verified. Update the next branch
from the feature branch before starting its implementation. Do not merge an
individual subissue directly into `master`.

### Subissue 1 — Inventory and lifecycle test baseline

Account for every `setHass()`, `requestUpdate()`, refresh flag and derived-entity
publication route. Add the counters and real-module test harness required by
Plan 14. Demonstrate the current feedback calls before changing them, but do
not merge deliberately failing tests.

**Result to demonstrate:** the current external and internal update routes are
named by function, existing visible behaviour remains covered, and a test can
distinguish an external HA update from an internal card re-entry.

### Subissue 2 — Publish Sparkline-derived entities once

Implement the Plan 06 publication and equality rules for all eight derived
entity types, implicit Sparkline series and explicit series. Preserve the
shared entities-array identity and expose an ordinary result that identifies
which derived entities actually changed.

**Result to demonstrate:** changed values or observable metadata update their
consumers, equal derived results do not report a change, and no graph/history
calculation is performed by `CardEntities`.

### Subissue 3 — Direct Sparkline result route

Add the direct card route for synchronous graph results, accepted history and
bin/calendar timer results. Remove both Sparkline-to-parent `setHass()` calls
and stop using refresh state solely to force the second pass.

**Result to demonstrate:** a history or timer result updates the graph,
`fhs_sparkline.*`, dependent tools and animations in one forward sequence;
`setHass()` is not called and the graph is not processed a second time.

### Subissue 4 — Direct FHS-input route

Replace the `CardInputEntities` callback into `setHass()` with a direct local
input update. Preserve card-scoped input behaviour, global synchronization,
persistence and JavaScript-backed consumers.

**Result to demonstrate:** changing one FHS input updates every applicable card
and its visible consumers without pretending that Home Assistant supplied a
new state object or causing unrelated history work.

### Subissue 5 — Direct palette completion route

Replace palette completion through forced `setHass()` with the existing paint
owners and a direct visual update. Keep palette application, color-cache/path
invalidation and the required post-render gradient measurement in their
current owners.

**Result to demonstrate:** an asynchronously loaded palette repaints the live
card, a stale palette completion changes nothing, and entity, history, bin and
statistics processing counters remain unchanged.

### Subissue 6 — Final render decision and lifecycle cleanup

Combine the results from the four routes into one understandable card-wide
render decision. Preserve legitimate direct presentation renders. Remove only
feedback-specific flags and code proven unused after the direct routes exist.

**Result to demonstrate:** one logical data event produces one card-wide render
decision, reconnect and configuration replacement still initialize the active
tool generation correctly, and loading, DOM measurement, pointer and animation
updates still render without restarting data processing.

### Subissue 7 — Regression and integration acceptance

Complete the Plan 14 matrix against the assembled feature branch. Run the full
Node suite, the affected Chromium suite and the required WebKit lifecycle/SVG
cases. Exercise normal HA updates, FHS inputs, palettes, history success,
valid-empty history, failure/recovery, stale results, timers, offsets,
reconnect and configuration replacement.

**Result to demonstrate:** all suites pass with existing YAML fixtures, no
internal route calls the parent `setHass()`, and measured processing counters
show no duplicate graph/history work. Only then is the main issue complete and
the feature branch eligible for its pull request to `master`.

## 22. Test layers and focused tests

Use all four layers required by Plan 14:

1. small reproductions for equality, ordering and stale-result decisions;
2. real adjacent modules for CardTools, CardEntities, SparklineGraphTool and consumers;
3. the real card created from existing YAML, with `hass` assigned through its public setter;
4. browser tests for actual Lit/SVG timing and visible results.

Minimum expectations:

1. A single external `hass` assignment invokes `setHass()` once.
2. Sparkline history completion does not invoke `setHass()`.
3. Sparkline bin-boundary refresh does not invoke `setHass()`.
4. A changed Sparkline average updates a StateTool that reads `fhs_sparkline.*`.
5. An unchanged Sparkline-derived value does not create an unnecessary dependent-tool/render pass.
6. A formatted StateTool value that remains equal does not require a render solely because raw input changed.
7. Existing JavaScript config updates still occur when their HA inputs change.
8. A local FHS input reaches all applicable cards without card-wide HA re-entry.
9. Palette completion changes paint without recalculating history or graph data.
10. A stale history or palette result from an old tool/configuration changes nothing.
11. Reconnect and configuration replacement initialize each current tool generation once.

Also cover valid empty history, failed history followed by recovery, rolling
and calendar windows, bin/day boundaries and the existing offset matrix.
Control time in tests; include UTC and `Europe/Amsterdam` where calendar/DST
behaviour matters.

## 23. Full-route test

Construct the real card with existing YAML containing:

- one HA sensor;
- one Sparkline using that sensor;
- one local `fhs_sparkline.avg` entity;
- one StateTool displaying the local average.

Then verify:

```text
initial hass
-> history result
-> avg local entity changes
-> StateTool output changes
-> one resulting card render route
-> no second setHass(same hass)
```

Use real neighboring modules in this route. Mock only the Home Assistant
platform boundary, history response, time and browser APIs that cannot run in
Node. Do not mock Graph/Series or the card-to-tool interfaces whose cooperation
the test is meant to prove.

Run focused tests during implementation. Before this plan is complete, run the
full Node suite and the affected browser suite. Chromium covers the complete
configured route; WebKit must cover the lifecycle/SVG timing cases relevant to
this change. Keep existing YAML fixtures unchanged unless a confirmed bug in a
fixture is documented.

## 24. Required end state

This plan is complete when:

- there are no internal Sparkline calls to `card.setHass(card._hass)`;
- `setHass()` has one clear external meaning;
- local Sparkline outputs can reach consumer tools directly;
- an async history/timer result can update the card without faking an HA event;
- one logical update produces one understandable linear call sequence;
- existing YAML behaviour remains unchanged except confirmed bug fixes;
- tests prove both ordinary HA updates and derived Sparkline updates;
- tests prove FHS-input and palette completion without HA re-entry;
- Plan 06's complete derived-entity publication is included;
- remaining fine-grained render and geometry optimization is explicitly left to Plans 02 and 05.
