## 1. Goal and Authoritative Inputs

Audit the migrated source as one complete chain, then remove the architectural
redundancy that the completed migrations have made unnecessary.

Use the current refactor3 architecture, migration sequence and verification
documents, together with the implementation results of Plans 15B, 16B, 16C,
17B, 18B and 19 and their separately merged corrections. The starting revision is
`82c96efccb0717d2febbe08f15aad3278401c9c7`, including the derived-series palette
correction from issue #885 / PR #886.

The older refactor2 Plan 20 is historical. Its gatekeeper, literal zero-guards
target, mandatory missing-entity fix and arbitrary line-removal targets do not
apply to this plan.

Scope covers all 72 product-owned root `src/*.js` modules. Copied
`src/frontend_mods/`, dependencies and generated bundles are not migration
targets. Tests, the bundle and relevant documentation accompany product changes.
The complete removal of the accidental `layout.horseshoes_v2` development alias
also includes its schema sources and generated active schema references.

## 2. Functional and Architectural Rules

For tools, identify this route directly:

```text
compiled/routed item
-> existing template-visible source preparation
-> stable sourceConfig
-> JavaScript evaluation in the existing context and order
-> local newConfig
-> existing translation/default completion
-> current this.config
-> geometry / runtime / paint
-> rendering
```

- Keep one source configuration and one current configuration. `newConfig` stays
  local. `setState()` consumes current config and updates runtime/paint rather
  than completing or replacing configuration.
- Preserve existing static and JavaScript authoring behavior, including defaults
  visible through `item`, expression evaluation counts and parent/child contexts.
- Text outer fields and parts retain their distinct evaluation phases under one
  source/current owner. Preserve inline-source binding before setting current config.
- Keep authored `state_map` in config, selected/current state in runtime, derived
  dimensions in geometry and the current active-color ownership separate from
  authored config.
- Preserve the final SVG/CSS styles of retained children, their precedence and
  text-measurement updates when font-related styles change. Use the existing
  child presentation route during Plan 20 without declaring `paint.styles` or
  `setPaintStyles()` permanent product requirements.
- Keep active color stops with the owners established by Plan 19. Preserve
  explicit series overrides, entity fallback precedence and the #885 correction.
- Support modules retain meaningful domain structures such as history, graph
  inputs, measured paths, animation, requests and caches. They do not need empty
  BaseTool-like containers merely for visual symmetry.
- Preserve public YAML, HA state interpretation, algorithms, units, geometry,
  transitions, interactions, request scheduling and reconnect behavior. The
  explicitly approved exception is removal of `layout.horseshoes_v2`, a temporary
  development name rather than an intended public compatibility contract.

No new features, JS error-handling policy, validation framework, fallback layer,
compatibility aliases or competing configuration lifecycle belong here.
Separately discovered functional defects are recorded separately unless the user
explicitly brings them into scope.

Current internal storage and exact object identity are not permanent functional
contracts. Preserve correct values, colors, styles, geometry and meaningful
processing reuse; the Plan-21 boundary in section 4 distinguishes that from the
current render-gating implementation.

## 3. Audit Method and Recorded Decisions

Create a current matrix for every root product module. The original refactor3
matrix describes the pre-migration baseline and must not be treated as a current
finding list. For each module record:

```text
role and configuration owner
geometry / runtime / paint / domain owners
constructor, translation, state, connection and render sequence
actual producers and consumers
KEEP / RENAME / MOVE / MERGE / ADAPT / REMOVE decision
preserved calculations and template-visible behavior
focused tests and Pass-B candidates
```

Trace the complete producer-to-consumer route before changing ownership. A field
name or search hit alone is not evidence of duplication. Inspect ordinary tools,
Text, Controls, Sparkline, Horseshoe/Path and support modules together at their
shared interfaces.

Search for old owners and synonyms, including `config.svg`, `runtimeConfig`,
`activeItemConfig`, `effectiveConfig`, `graphConfig`, `pathConfig`,
`numberGeometry`, persistent `newConfig`, child-config mutation and palette
copies. Classify remaining hits as a legitimate local value, a distinct domain
concept, a shared concept with misleading naming, or obsolete architecture.

### Runtime-Config Readiness

`BaseTool` already assigns `this.config` in its constructor. For static tools
that config can also be fully translated before any runtime-config update.
`runtimeConfigInitialized` therefore records completion of the normal
runtime-config phase, not existence or initialization of `this.config`.
For JS-backed tools it also identifies when the first evaluated config is ready
for the existing render/lifecycle consumers. Keep these distinct meanings in
comments and tests. The boolean is lifecycle state, not another config owner.

### Complete Removal of the Development Alias

Treat `horseshoes_v2` as a known removal target rather than inferring public
compatibility from later tests or schema annotations. Implement the complete
cleanup in one working checkpoint:

- Remove its input route from the gauge factory and its layout-section, z-order
  and render-order entries.
- Remove the dedicated YAML definition and references from the layout and
  compound schema sources.
- Regenerate the active schema, authoring metadata and definition-source map
  using the existing schema generator; update the definition map and any
  currently consumed schema/validator copies so no active consumer advertises
  the alias. Do not patch generated artifacts instead of their owning sources.
- Split tests that combine root-level configuration with the development alias:
  preserve the root-level behavior test and remove the false alias expectation.
  Verify ordinary `layout.horseshoes`, section enumeration and active schemas
  without adding an alternative alias or new runtime error policy.
- Remove current documentation that presents the development name as supported
  compatibility. Historical snapshots may retain their historical contents but
  must not be treated or advertised as the active compatibility specification.

The original root-level Horseshoe route is a different input format. Do not
remove it merely because its current test also mentions `horseshoes_v2`.
Schema changes are limited to this alias removal; unrelated generator or
validator defects remain separate findings.

## 4. Pass A and Mandatory Pass B

Pass A performs the smallest ownership and naming corrections. Complete each
shared-interface change across its real callers in one working checkpoint;
leave no transitional alias or partly migrated owner behind.

Pass B then checks every module again, including modules whose Pass-A result was
KEEP. Review repeated merges, intermediates, persistent copies, wrappers,
signatures, lifecycle operations, dead adapters, guards and fallback paths.

Before removal, record the producer guarantee, affected consumers and equivalent
observable result. Consolidate a helper only when the result is simpler linear
logic or removes genuine duplication; do not replace it with more abstractions.
Do not split large render modules merely to reduce individual file lengths.

Classify checks as:

1. Configuration translation or validation.
2. External HA, network or DOM data handling.
3. Lifecycle or measurement readiness.
4. Algorithmic cases reachable with valid config.
5. Consumer-owned semantic conversion.
6. Demonstrably expensive processing or cache reuse.

Remove only proven redundant downstream configuration checks. Retain checks
whose valid runtime purpose remains. Public path defaults, unit conversion,
partial-path boundaries and shape validation need an ownership trace before any
relocation; path calculations themselves remain unchanged.

When removing a cache, signature or equality check, prove that the result does
not add JS evaluations, history requests/processing, geometry calculations,
palette conversions or DOM measurements. Existing reuse assertions are evidence
when they establish that concrete work is avoided, not merely that two internal
objects are identical. Add a controlled before/after measurement where the changed
processing route needs it, rather than profiling every mechanical rename.

For each mechanism ask what produces it, who consumes it, what work or incorrect
behavior it prevents, whether that guarantee already exists earlier, and what
observable result changes on removal. A previous plan, a schema annotation or
an assertion alone is not a reason to preserve accidental architecture.

If an existing behavior cannot fit the architecture without a second general
configuration owner or major functional rewrite, stop that change and document
the conflict for review instead of introducing another lifecycle.

### Boundary With Plan 21

Plan 20 completes ownership/naming consistency and removes proven duplicate
routes, obsolete adapters, dead wrappers and unused state. It does not redesign
the live render/update path.

Generic `presentationSignature`, `cardPresentationSignature` and
`hasPresentationChanged()` chains, paint/style indirection, palette/mapping
signature redesign and exact internal-identity assertions are Plan-21 review
candidates. Leave their current functional behavior intact in Plan 20 unless a
specific mechanism is plainly dead or unused. Do not create new documentation
or tests that make their current structure an immutable architectural rule.

Measurement signatures, async request identity, history/data revisions and
expensive geometry/cache keys have a different purpose: they can avoid real DOM
measurement, network traffic, history processing or costly calculation. Keep
them where the producer/consumer trace demonstrates that purpose. Likewise,
evaluate palette/mapping keys by the actual work they avoid, not by their names.

Plan 21 may reconsider whether ordinary state/theme/config processing should
simply request an update after processing, leaving the browser/Lit to render.
Plan 20 neither implements that redesign nor pre-decides its outcome.

## 7. Verification and Visual Approval

Reuse the architecture and regression suites introduced in Plans 15B-19 and
their corrections. Extend existing suites with narrow cases only where coverage
is missing; do not introduce a generic configuration validator or brittle tests
that merely count helpers.

Verify functional output rather than unnecessarily freezing implementation
shape: rendered/computed styles and precedence, correct theme colors and values,
measurement updates, graph/path results and avoided evaluations/requests/work.
Do not add assertions merely requiring `paint.styles` to exist, a particular
presentation-signature shape or unchanged mapper/object identity. An exact
identity assertion needs a documented correctness or processing-cost purpose.
Existing implementation-specific tests may be reviewed on that basis; broad
render-gating or identity-test redesign remains for Plan 21.

Focused acceptance includes:

- Static and equivalent JS values, template-visible defaults, one evaluation per
  owning expression, avoided repeat translation and the first runtime-config update.
- Outer/part Text contexts, inline and referenced Name/Area/State, child entity
  changes, font-related paint measurement and text-fitting rectangles.
- Control labels/actions/content, parent/child bindings, HA-derived options,
  unavailable values, theme switches and changed group placement.
- Sparkline implicit/explicit/whole-JS series, inherited/explicit palettes,
  derived entities, minmax, radial/day-night, duration changes and history reuse.
- Horseshoe path shapes, scale/mapping modes, zero/negative/end values, marker
  placement, gradients, animation, path measurement and theme-only cache reuse.
- Ordinary `layout.horseshoes` and genuine root-level configuration still work;
  no active runtime section, schema reference or authoring metadata retains the
  accidental `horseshoes_v2` route. Use the existing schema-generation and
  focused schema tests for this explicit cross-boundary cleanup.
- Config replacement, delayed SVG/palette results, disconnect/reconnect and
  nested/view theme cache behavior.

During implementation run focused tests, then build promptly for the user's
visual check. After that check run the full Node/lint/build acceptance and all
configured Chromium, WebKit and Firefox browser projects. `npm run build`
already combines Node tests, lint and Rollup; do not repeat Rollup when the
tested bundle's inputs have not changed. Separately run Node/lint against the
same existing artifact if those checks were deferred until visual approval.

Run independent post-review after implementation. Report BLOCKING / REWORK /
ADAPT findings and their disposition. Product changes from review require a
fresh build and appropriately focused verification; do not weaken behavioral
tests to make a cleanup pass.

## 9. Definition of Done

A maintainer can open any unfamiliar tool and identify its configuration,
geometry, runtime, paint, lifecycle and rendering without learning a private
alternative architecture. Support-module names describe their actual domains.

Every module has a recorded audit and Pass-B result. Remaining signatures,
caches, guards and intermediates have an identifiable purpose. No competing
general config owner, transitional alias or unnecessary adapter remains.

Current generic render gating and paint/style indirection remain subject to the
separate Plan-21 review; completing Plan 20 does not make them permanent rules.

Existing functional behavior, skipped-work guarantees and visual results remain
correct. Full acceptance, independent post-review, source-size reporting and
the user's merge approval are complete before master is updated.
