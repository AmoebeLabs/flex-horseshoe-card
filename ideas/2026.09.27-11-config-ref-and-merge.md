# 11 - Config `ref()` and merge behaviour

## 1. Goal

Preserve the type and contents of referenced constants. Every object or array inserted through `ref()` receives its own deep copy. Existing configuration inheritance keeps its current behaviour.

## 3. Current-code validation

`CardConfig.compileStaticValues()` currently copies a referenced object or array with `Merge.mergeDeep(Array.isArray(constant) ? [] : {}, constant)`. The merge reducer starts with `{}`, so the array at the root becomes an object with numbered properties.

Confirmed reproduction:

```text
source: [{ value: 1 }, [2, 3]]
copy:   { "0": { value: 1 }, "1": [2, 3] }
Array.isArray(copy): false
```

The existing CardConfig test covers scalar references, dotted paths and independent object copies. It does not cover a referenced array or nested-array independence.

Trace the whole configuration route rather than changing the merge utility in isolation:

```text
main.setConfig()
  -> clone incoming configuration
  -> CardTemplates.compile()
  -> CardConfig.compileStaticValues()
  -> ControlTool.compileConfig()
  -> entity-slot normalization
  -> Compounds.compile()
  -> SameAs.compile()
  -> remaining configuration validation/defaults
  -> concrete tool construction
```

Current caller inventory and policies to preserve:

| Owner | Existing behaviour |
| --- | --- |
| `Merge.mergeDeep()` | Deep object merge; existing nested arrays concatenate; a newly inserted array is copied. Root arrays are not a supported merge result. |
| `CardTemplates.mergeTemplateConfig()` | Card arrays replace template arrays; matching object fields merge recursively. Template expansion precedes static references. |
| `SameAs.compileItems()` | Ordinary inherited arrays concatenate. `same_as_replace` removes the selected inherited path before merging. A marked `ref()` override replaces the complete value at that path. |
| `Compounds.compile()` | Child lists match by local id. Explicit replacement and marked references remove the inherited value before merging. Static-reference markers survive compound copying and generated-child expansion. |
| `SparklineSeries.updateConfig()` | Parent graph configuration merges with each series override. The series collection and effective graph settings retain existing inheritance. |
| Controls, tools, actions, masks and filters | Their existing merge calls remain unchanged. They consume compiled configuration without a second reference-copy implementation. |

## 4. Scope

Repair copying at the static-reference boundary, add permanent regression/integration tests and correct misleading comments in the touched code.

Supported referenced values remain scalars, plain objects, arrays and their nested combinations. A referenced value may contain the existing JavaScript-template strings.

## 5. Out of scope

- Global merge algorithm changes or a universal array-replacement rule.
- New reference syntax, recursive reference-alias semantics or changed compilation order.
- A new validation policy, silent coercion, changed error messages or a cycle-aware clone framework.
- Path, animation, history, graph mathematics or rendering algorithm changes.
- Fixing unrelated copy call sites without a separately reproduced defect and approved scope.

## 6. Required design and behaviour

`CardConfig` owns static constant lookup and the copy inserted at each reference. Use one local recursive `copyRefValue()` inside `compileStaticValues()`:

- Scalars are returned with their original value, including zero, false, empty strings and null.
- Arrays remain arrays and every entry is recursively copied.
- Plain objects retain their configured properties and every property value is recursively copied.
- Each insertion is independent of its source constant and every other insertion, including all nested objects/arrays.
- Keep the existing static-reference marker on the inserted structured value. Preserve its existing propagation through calculation and compound compilation.

The marker preserves existing inheritance intent: a referenced override supplies the complete configuration value, while ordinary explicit fields use their current merge policy. It remains non-enumerable and must not become a public YAML field.

Remove CardConfig's Merge import if reference copying was its only use. The merge algorithm itself remains byte-for-byte unchanged; update its inaccurate array-replacement documentation only.

### Complete-chain ownership

The producer is `CardConfig.compileStaticValues()`. Its stored output is the compiled value at the reference's target field. Controls, compounds, same_as and tools consume that output through the existing configuration order.

References are copied once per insertion during configuration compilation. Legitimate later inheritance and constructor merging retain their own existing roles. Rendering and HA updates must not rediscover constants or add reference-copy passes.

Keep the operation local and readable. Add functional English comments explaining copy independence and replacement intent. Add no runtime fallback, new cache, compatibility bridge or generic cloning class.

## 8. Permanent tests and acceptance

Add behaviour tests before the fix and verify their failure reason. Retain them after the implementation:

- Scalar references, including zero, false, empty strings and null.
- Root arrays, empty arrays, object arrays, arrays containing arrays and objects containing nested arrays.
- Two consumers of one structured constant: mutate nested values and append items in one consumer; the other consumer and source remain unchanged.
- Existing dotted lookup, missing-path errors and calc behaviour.
- Static-reference markers survive array calculations and compound expansion and remain non-enumerable.
- Reference overrides replace inherited colour-stop lists/objects through same_as and compounds.
- Ordinary arrays still concatenate; explicit `same_as_replace` still replaces its selected path; compound children still match by id.
- Template arrays still replace template defaults, and Sparkline series retain parent/override inheritance.
- A complete-card Chromium check passes referenced configuration through public `setConfig()` and confirms that a real tool receives and displays the expected value.

Use real neighbouring FHS modules; mock only HA/network/DOM boundaries. Assert output and mutation independence rather than private helper names. Do not multiply screenshot cases for a configuration-only change.

Run focused reproductions first. Build for user validation after the implementation, then complete full Node tests, lint and affected Chromium tests before finishing. Existing WebKit-sensitive algorithms are unchanged; additional WebKit cases are needed only if implementation unexpectedly touches SVG/interaction/lifecycle behaviour. Avoid repeated broad builds or acceptance reruns without a changed result.
