# 04 — Sparkline data processing and geometry

## 1. Goal

Make Sparkline capable of reusing processed data when only scale/layout/geometry/paint changes, while preserving proven graph algorithms.

Permanent functional split:

```text
prepared source data -> processed graph data/statistics
processed graph data + final scale/drawing inputs -> geometry
geometry + theme/palette/style -> paint/presentation
```

## 2. Prerequisites

Plans 01–03 complete. Ownership, History and explicit data state are fixed and must not be revisited here.

## 3. Current-code validation

Verify repeated `SparklineGraph.update()`/`updateCartesianGraphs()` passes, shared-scale/margin calculation, min/max envelope work and current radial/state-band routes. Confirm which blocks are data-only, geometry-only, paint-only or mixed.

Validation on 2026-09-24: `SparklineSeries.updateCartesianGraphs()` and `updateRadialGraphs()` call `SparklineGraph.update()` repeatedly while measuring shared bounds and margins. `SparklineGraph.update()` still combines bucketing, min/max and axis geometry. `SparklineGraphTool.updateRuntimeConfig()` replaces graph instances. `SparklineSeries` owns the effective bin plan, `SparklineHistory` owns history, and the request/data states from plans 02-03 remain separate. Existing Graph, Series and GraphTool tests cover the representative chart families; direct reuse boundaries still need tests before implementation.

## 4. Scope

- expose/reuse one processed-data result per affected series;
- keep whole-period statistics mathematically unchanged;
- fix first-bin regression if still reproduced;
- derive shared Y range from processed results;
- determine final margins/drawing area once;
- calculate geometry from final scale without reaggregation;
- reuse bin/minmax results where semantics are identical;
- preserve separate state_bands/real_time/radial requirements.

## 5. Out of scope

- global event invalidation/render scheduling (Plan 08);
- graph formula redesign;
- radial duplicate cleanup unless necessary for the split (otherwise Plan 13).

## 6. Required behaviour

Processed data must be replaced when its effective inputs change: source/history, period or visible time window, bin membership (including an active bin advancing), effective bin/aggregation plan, missing-data semantics or data-mode config. Unchanged source rows alone do not prove the processed result is still current.

It must be reusable when only the drawing rectangle, margins, scale-to-pixel geometry or paint changes. A resize with `bins.per_hour: auto` can change the effective bin count: reaggregate from retained source rows in that case, without requesting history again unless the required source range has changed. A resize that keeps the effective bin plan and time window unchanged needs geometry only.

Pure color/opacity changes are paint-only. Style changes that affect measured extents, such as line width, dot radius or labels, require geometry and possibly a new shared margin, but not reaggregation when the effective data inputs are unchanged.

Runtime config updates can replace `SparklineGraph` instances. Preserve the processed result across an eligible replacement, or avoid replacing the graph when only geometry or paint changed. Do not introduce a second, independently invalidated cache.

Series coordinates shared scale/layout; Graph owns per-series processing + geometry; GraphTool presents.

### Graph preservation invariant

This plan may separate existing Graph work into reusable data and geometry boundaries, but it must not change the meaning of the calculations themselves. The split is successful when the same prepared data/config still produces the same statistics and geometry while unnecessary repeated work disappears.

```text
same prepared input + same final scale/layout
        -> same processed statistics
        -> same geometry/result
```

Moving an existing calculation to the correct boundary is allowed. Replacing or "improving" its formula is not part of this plan unless a separately reproduced defect requires it.

## 7. Implementation sequence

1. Add direct call-boundary tests around current repeated updates.
2. Lock first-bin and whole-period statistic behaviour.
3. Identify data-only, geometry-only and paint-only blocks without rewriting formulas; record which style changes affect measurements.
4. Define processed-data validity using the effective source range, time window/bin membership and bin/aggregation plan, including `auto` after a resize.
5. Expose/store the existing processed result in a concrete FHS-shaped structure and retain it through eligible Graph replacement.
6. Process all affected series data before deriving shared Y scale.
7. Determine final margins/drawing area.
8. Calculate geometry once from final inputs.
9. Update min/max envelope to reuse the existing bin result when identical.
10. Verify radial/state_bands/real_time independently.
11. Remove only repeated full Graph calls made unnecessary by the stable split.

## 8. Permanent tests

From [TESTING.md](refactor/TESTING.md):

- line/area/bar/dots representative cases;
- minmax envelope;
- multi-series shared/fixed/automatic Y ranges;
- resize with unchanged effective bin plan and time window -> geometry only, zero history/reaggregation;
- resize that changes `auto` bins -> reaggregation from retained rows, no history request while source coverage remains sufficient;
- unchanged rows with a changed window or bin membership -> processed result refreshed;
- eligible Graph replacement -> processed result retained;
- pure color/opacity update -> zero data/geometry rebuild; measurement-affecting style update -> geometry recalculated without reaggregation;
- first bin zero/negative/multiple values;
- state_bands, radial, real_time;
- permanent `SparklineGraph` characterization fixtures remain unchanged for identical prepared input.

## 9. Definition of Done

- historical/raw data processes once per required data update, including effective time-window and bin-plan changes;
- final shared scale/margins use processed results;
- geometry can recalculate without history/bin/statistics work when processed-data inputs are unchanged;
- pure paint can update without data or geometry work;
- eligible graph replacement retains processed data or is avoided;
- whole-period statistics retain existing meaning;
- multi-series shared axes no longer require repeated full data processing;
- representative characterization fixtures prove unchanged Graph statistics/geometry for unchanged prepared inputs;
- no proven `SparklineGraph` formula or calculation semantic changed unless a separately reproduced defect required that change;
- Graph remains algorithmically close to the proven implementation.
